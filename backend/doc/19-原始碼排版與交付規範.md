# 19 原始碼排版與交付規範

> **強制規則：正式原始碼、設定檔與資料庫腳本禁止壓縮成單行。**
>
> 編譯成功只代表語法可能正確，不代表程式具備可讀性、可維護性或已完成交付。任何為了快速產生檔案而把 Java、Vue、TypeScript、SQL、XML、JSON 或 Markdown 擠成一行的作法，均視為未完成。

## 1. 共通原則

1. 開始實作前，必須先讀取同一模組、同一檔案類型的既有檔案，沿用其縮排、換行、import、標籤及空行配置。
2. 禁止提交 minified、壓縮式或刻意省略空白的正式原始碼；只有實際建置產物可以壓縮。
3. 一行只表達一個清楚的結構或動作。不得把多個 import、欄位、statement、HTML 元素或 JSON property 全部串在同一行。
4. 不得使用「可以編譯」「可以 parse」作為排版合格的理由。
5. Formatter 只能協助排版，執行後仍須人工檢查完整 diff，確認沒有改變 SQL、XML、template 或字串語意。
6. 所有文字檔使用 UTF-8 without BOM，中文不得出現亂碼。

## 2. Java

- 一個 import 一行，禁止 wildcard import（例如 `java.util.*`）。
- 一個欄位一行，禁止 `private String oid, tenantId, status;` 形式。
- class、method、constructor、annotation 與控制流程必須正常換行及縮排。
- Service、Logic、Mapper 與參數使用具體名稱，禁止以 `s`、`l`、`t`、`x` 等無法辨識用途的單字母名稱代替核心物件。
- setter 參數使用欄位名稱並以 `this.field = field` 指派。
- 長 method chain、泛型與條件式應依專案既有風格換行，不得犧牲可讀性強塞一行。
- 完成後至少執行 Maven compile/test，並抽查新增及修改的每一個 Java 檔案。

## 3. Vue 與 TypeScript／JavaScript

- `<script setup>`、`<template>` 與 `<style>` 必須分區並正常換行。
- import、變數宣告、function、API request、template element 及 attribute 應依專案 Prettier 規則排版。
- 禁止把整個 `<template>`、表格、表單或 component 塞在單一行。
- 禁止為了縮短程式而大量串接逗號運算式或在同一宣告中建立多個不相關物件。
- 完成後必須通過 Prettier check 與 Nuxt production build，並人工檢查畫面 template 的可讀性。

## 4. SQL

- `INSERT`、`SELECT`、`UPDATE`、`DELETE` 的欄位、條件與值必須依區塊換行。
- 欄位很多時，欄位清單與 `VALUES` 必須分行對齊；不得把完整 SQL 擠成一個超長單行。
- `JOIN`、`WHERE`、`AND`、`ORDER BY` 與 transaction boundary 必須清楚可辨識。
- 程式註冊 SQL 應沿用同模組既有 register SQL 版型，不得自行產生壓縮格式。
- Formatter 執行後必須檢查函式名稱與語法，例如不得將 `UUID()` 意外改成不符合專案慣例的形式。

## 5. MyBatis／BPMN XML

- XML element、attribute、`resultMap`、`if`、`trim`、`set` 與 statement 必須採多行結構。
- 禁止把整個 `resultMap`、動態條件或 SQL statement 壓成單行。
- MyBatis 的 schema `<include>` 與資料表名稱必須依既有 Mapper 寫法保持正確連接，不得因 formatter 插入空白而改變 SQL。
- 通用 XML formatter 可能破壞 mixed content 的空白語意；格式化後必須人工檢查實際組合出的 SQL。
- 完成後必須進行 XML parse，並透過 Spring Context／整合測試確認 Mapper 可以載入。

## 6. JSON／YAML

- 正式維護的 JSON／YAML 必須使用階層式縮排；禁止將大型 schema、設定或測試資料保存為單行。
- Object 與 Array 應依語意分段；巢狀內容不可只為節省行數而壓縮。
- JSON 必須通過 parser；Schema、UI Schema 與 Resolver Config 還必須通過對應 schema validation。
- API response 範例可以精簡，但只要超過少量欄位就必須使用多行 code block。

## 7. Markdown

- 標題、段落、清單、表格及 code block 之間保留必要空行。
- Java、Vue、SQL、XML、JSON 範例必須使用正確語言標記的 fenced code block，並保持與正式程式相同的可讀排版。
- 不得在文件範例中示範單行壓縮程式碼，避免後續實作者複製錯誤格式。

## 8. 強制交付檢查

新增或修改程式後，以下項目全部通過才能宣告完成：

- [ ] 已讀取並比對同類型既有檔案。
- [ ] 正式檔案沒有單行壓縮或超長密集程式碼。
- [ ] Java 沒有 wildcard import、合併欄位宣告或核心單字母命名。
- [ ] Vue／TypeScript 已通過 Prettier check。
- [ ] SQL 已依區塊排版，且 formatter 未改變語法。
- [ ] XML 已 parse，MyBatis mixed content 與 schema include 已人工檢查。
- [ ] JSON／YAML 已 parse，且內容採階層式縮排。
- [ ] `git diff --check` 通過。
- [ ] 已人工閱讀完整 diff，不只查看 build 結果。
- [ ] Backend compile/test 與 frontend production build 依異動範圍通過。

只要任一項未完成，就必須明確標示為「尚未完成」，不得回報已完成或可交付。
