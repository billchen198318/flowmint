# 01 核心資料模型

## 1. 資料邊界

Tenant 是系統資料隔離範圍。一個 Tenant 可以包含多個公司型組織節點，例如台灣總公司、中國分公司與越南分公司。

```text
Tenant
└─ 組織總根
   ├─ 台灣總公司（COMPANY／Approval Root）
   ├─ 中國分公司（COMPANY／Approval Root）
   └─ 越南分公司（COMPANY／Approval Root）
```


分開 Tenant 作法
```text
Tenant-A
└─ 組織總根
   └─ 台灣總公司（COMPANY／Approval Root）

Tenant-B
└─ 組織總根
   └─ 中國分公司（COMPANY／Approval Root）

Tenant-C
└─ 組織總根
   └─ 越南分公司（COMPANY／Approval Root）
   
```



公司型節點與部門都使用組織單位模型，不建立法人或據點主檔。這些 `COMPANY` 節點只代表簽核樹中的組織與核決根，不宣稱是法律實體，也不是尚待補建的法人資料。

若表單需要簽約主體、統編、付款公司、工安廠區或收貨地址，該資料屬於具體業務內容或外部 ERP／HR 主檔，應透過表單欄位或整合介面取得，不擴張 FlowMint 核心 ORG。

## 2. Tenant 與人員

| 資料表 | 用途 |
|---|---|
| `fm_tenant` | 系統組織、預設語系與時區 |
| `fm_tenant_account` | QIFU4 帳號可使用的 Tenant |
| `fm_employee` | 簽核需要的員工基本資料 |

登入帳號以 QIFU4 `tb_account` 為唯一來源。Employee 保存工號、姓名、聯絡資料及有效期間，不保存密碼。

## 3. 組織、職稱與職務

| 資料表 | 用途 |
|---|---|
| `fm_org_unit` | 穩定組織單位 ID 與代碼 |
| `fm_org_unit_version` | 組織名稱、父節點、類型、路徑及有效版本 |
| `fm_org_level_scheme` | 公司型組織適用的簽核職級方案 |
| `fm_org_approval_level` | 一般員工、課長、經理、處長、副總等職級 |
| `fm_org_title` | Tenant 共用職稱及其簽核職級 |
| `fm_org_duty` | 某部門可使用的簽核、審查或通知職務 |
| `fm_employee_org_assignment` | 員工在部門內的職稱、主要任職及直屬主管 |
| `fm_employee_duty` | 員工在該部門承擔的職務 |
| `fm_org_unit_head` | 部門主要主管、副主管及期間代理主管 |

職稱屬於 Tenant 共用主檔；員工在 `fm_employee_org_assignment` 透過 `ORG_UNIT_ID + TITLE_ID` 配置部門任職與職稱。職稱代表位階，職務代表責任，HEAD 代表實際單位主管，三者不可混用。

## 4. 直屬主管

`fm_employee_org_assignment` 保存：

```text
MANAGER_SOURCE
DIRECT_MANAGER_ASSIGNMENT_ID
```

主管來源：

```text
ORG_HEAD      本部門 HEAD
PARENT_HEAD   上層部門 HEAD
EXPLICIT      指定另一筆有效員工任職
NONE          僅最高負責人
```

不得指定自己，不得形成直接或間接主管循環。主管關係依任職有效期間判斷。

## 5. 簽核資源與核決權限

| 資料表 | 用途 |
|---|---|
| `fm_approval_group` | 財務、法務、採購等群組 |
| `fm_approval_group_member` | 群組成員 |
| `fm_workflow_delegation` | 期間代理 |
| `fm_approval_authority` | 表單或流程適用的核決權限 |
| `fm_approval_authority_rule` | 金額、天數、類別等條件及核決終點 |

核決終點可以是簽核職級、部門職稱、部門職務、簽核群組或指定帳號。

### 6.1 `fm_process_start_proxy` 代起單授權

這張表專門管理「發起人替申請人起單」的授權，不可取代簽核代理或待辦轉派。

| 欄位 | 說明 |
|---|---|
| `OID` | 資料列主鍵 |
| `TENANT_ID` | Tenant 邊界，所有查詢必須同時比對 |
| `START_PROXY_ID` | Tenant 內的代起單授權編號 |
| `PRINCIPAL_ACCOUNT` | 申請人，即授權別人代為起單的帳號 |
| `PROXY_ACCOUNT` | 發起人，即實際登入並送出表單的帳號 |
| `SCOPE_TYPE` | `ALL` 代表所有流程；`PROCESS` 代表限定單一流程 |
| `SCOPE_REF_ID` | `SCOPE_TYPE=PROCESS` 時保存 `PROCESS_ID`；`ALL` 時應為 `NULL` |
| `STATUS` | `ACTIVE` 或 `INACTIVE` |
| `EFFECTIVE_FROM` | 授權生效時間 |
| `EFFECTIVE_TO` | 授權終止時間，必須晚於生效時間 |
| `REASON` | 授權原因，不可空白 |
| `CUSERID` / `CDATE` | 建立人與建立時間 |
| `UUSERID` / `UDATE` | 最後異動人與異動時間 |

授權解析規則：

- 發起人與申請人相同時為本人起單，不需這張表的授權資料。
- 兩者不同時，必須存在同 Tenant、申請人、發起人完全相符的 `ACTIVE` 授權。
- 送出時間必須位於 `EFFECTIVE_FROM` 與 `EFFECTIVE_TO` 之間。
- `ALL` 可套用全部流程；`PROCESS` 只能套用於 `SCOPE_REF_ID` 指定的流程。
- 不允許跨 Tenant、遞迴代理或把代起單授權當成簽核權限。
- 建表結構已納入 `backend/doc/flowmint.sql`；部署時以該主 schema 為準。

## 7. 表單與稽核

| 資料表 | 用途 |
|---|---|
| `fm_form_def` | 表單穩定主檔 |
| `fm_form_version` | JSON Schema、UI Schema 與發布版本 |
| `fm_form_data` | 使用者目前填寫內容 |
| `fm_form_snapshot` | 每次流程動作的不可變表單快照 |

| `fm_attachment` | 表單附件中繼資料 |
| `fm_task_action` | 送出及全部簽核操作軌跡 |

共用正式單據編號規劃使用 `fm_document_number_rule` 與
`fm_document_sequence`，並由流程主檔指定穩定的 `DOCUMENT_TYPE`。
這兩張表目前尚未納入既有 Schema；欄位、併發取號、交易及空號政策見
[24 共用單據編號規格](24-共用單據編號規格.md)。

## 8. 外部系統邊界

- `tb_account`：登入身分。
- `tb_role`、`tb_user_role`：程式與 API 權限。
- `tb_sys_prog`：頁面與功能註冊。
- Flowable `ACT_*`：流程引擎資料，由 Flowable 管理。

FlowMint 不建立第二套密碼，不直接更新 Flowable runtime table，不把程式權限 Role 當成組織主管或簽核群組。
