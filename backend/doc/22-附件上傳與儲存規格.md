# 22 附件上傳與儲存規格

## 1. 目標與現況

FlowMint 表單設計器應提供附件上傳元件，讓設計者配置附件欄位，並讓使用者在正式起單、補件或允許編輯的 Task 中上傳及刪除附件。

目前系統只有 `fm_attachment` 資料表、`base.uploadDir` 設定及附件 API 草案；Attachment Entity／Mapper／Service／Logic／Controller、Upload Session、Form.io 專用元件、權限、病毒掃描與清理工作尚未實作。因此即使 Form.io 顯示 File component，也不得宣稱正式附件功能已可使用。

附件內容不得以 Base64 寫入 Form.io submission、`fm_form_data.DATA_CONTENT`、表單快照或 audit log。Form Schema 只保存欄位設定；實體檔案由 FlowMint 附件服務保存，中繼資料由 FlowMint 資料表管理。

## 2. 表單設計器配置

`FM_PROG005D0001` 應提供 FlowMint 專用「附件上傳」元件，不直接依賴 Form.io 預設 File component 的儲存行為。

設計者可設定：

| 設定 | 說明 |
| --- | --- |
| `key` | 表單內唯一 `FIELD_KEY` |
| `label` | 使用者看到的欄位名稱 |
| `required` | 是否至少需要一個有效附件 |
| `multiple` | 單檔或多檔 |
| `maxFiles` | 最大檔案數 |
| `maxFileSize` | 單檔大小上限 |
| `maxTotalSize` | 欄位附件總大小上限 |
| `allowedExtensions` | 允許副檔名白名單 |
| `allowedMimeTypes` | 允許 MIME type 白名單 |
| `allowDelete` | 目前表單階段是否允許刪除 |
| `description` | 上傳限制與用途說明 |

發布檢查必須確認 key 唯一、限制值位於系統上限內、Extension 與 MIME 來自後端允許清單，且 Schema 不得指定實體路徑、任意上傳 URL 或可執行程式。

## 3. 起單前 Upload Session

使用者開啟表單時尚未建立 `FORM_DATA_ID`，因此先使用短效 Upload Session：

```text
開啟表單
  → 建立 UPLOAD_SESSION_ID
  → 上傳、列表、刪除暫存附件
  → 送出表單並建立 fm_form_data
  → 驗證附件
  → 綁定 FORM_DATA_ID
  → 移至正式附件區
```

Session 必須綁定 `TENANT_ID`、登入帳號、`FORM_ID`、`FORM_VERSION_NO`、建立及到期時間與狀態。前端不可指定 Tenant、Owner、正式 `FORM_DATA_ID` 或實體路徑。

建議狀態為 `OPEN`、`BOUND`、`EXPIRED`、`CANCELLED`。重新整理後恢復 Session 時，後端必須再次驗證登入者、Tenant、表單版本及有效期限。

## 4. API

```http
POST   /api/fm/attachments/sessions
POST   /api/fm/attachments/sessions/{sessionId}/files
GET    /api/fm/attachments/sessions/{sessionId}/files
DELETE /api/fm/attachments/sessions/{sessionId}/files/{attachmentId}

GET    /api/fm/form-data/{formDataId}/attachments
GET    /api/fm/form-data/{formDataId}/attachments/{attachmentId}/download
DELETE /api/fm/form-data/{formDataId}/attachments/{attachmentId}
```

上傳使用 `multipart/form-data`，Request 只提供必要的 `FIELD_KEY` 與檔案內容。Tenant 與登入帳號分別由 `X-FlowMint-Tenant` 與 Security Context 取得。API 不得回傳伺服器實體路徑。

回應範例：

```json
{
  "attachmentId": "uuid",
  "fieldKey": "quotationFiles",
  "fileName": "quotation.pdf",
  "contentType": "application/pdf",
  "fileSize": 123456,
  "status": "TEMPORARY"
}
```

## 5. 實體目錄

根目錄固定讀取系統設定：

```properties
base.uploadDir=/var/core-app/upload
```

建議配置：

```text
/var/core-app/upload/
└── flowmint/
    └── {tenantId}/
        ├── temporary/
        │   └── {uploadSessionId}/
        │       └── {fileOid}.bin
        └── attachments/
            └── {yyyy}/{MM}/
                └── {fileOid}.bin
```

儲存規則：

- 磁碟檔名一律使用系統產生的 UUID／`FILE_OID`，不使用原始檔名。
- 原始檔名只保存於中繼資料。
- 所有路徑經 `Path.resolve(...).normalize()` 後，必須仍位於附件根目錄。
- 禁止 `..`、絕對路徑、UNC path、symbolic-link 跳脫與使用者指定路徑。
- 正式環境啟動時確認目錄存在、可寫，且不是 Web 靜態資源目錄。
- Windows 開發環境可覆寫設定，但正式程式不可硬編碼作業系統路徑。

## 6. 資料模型

既有 `fm_attachment` 保存正式附件的 Tenant、附件 ID、`FORM_DATA_ID`、`FIELD_KEY`、`FILE_OID`、原始檔名、Content Type、大小、SHA-256、狀態及 Audit 欄位。

建議另建 `fm_attachment_upload_session` 與暫存附件明細表。正式附件表不應混入未送單、已過期或沒有 `FORM_DATA_ID` 的檔案。

病毒掃描狀態至少包含 `PENDING`、`CLEAN`、`INFECTED`、`FAILED`，並保存掃描時間及不含敏感內容的結果摘要。

## 7. 送單與一致性

送單前必須重新驗證：

1. Session 屬於目前 Tenant、登入者、表單及版本。
2. 附件存在、未刪除且未過期。
3. `FIELD_KEY` 存在於本次發布的 Form Schema。
4. 必填、數量、單檔大小、總大小、Extension 與 MIME 符合 Schema 與系統上限。
5. 實體檔案 SHA-256 與中繼資料一致。
6. 病毒掃描政策允許附件進入正式區。

建立 `fm_form_data` 後才將附件綁定 `FORM_DATA_ID`。Submission 可以保存附件 ID 清單，但不得保存 Base64 或實體路徑。

MariaDB 與檔案系統沒有共同 ACID transaction，必須提供補償機制：DB 失敗時處理暫存檔、搬檔失敗時回滾送單、提交失敗時標記待清理孤兒檔，並由排程清理過期 Session、未綁定檔案及可確認的孤兒檔案。

## 8. 權限與生命週期

附件列表、下載及刪除不能只憑 `ATTACHMENT_ID`，必須驗證：

- Header Tenant 與附件 Tenant 一致。
- 操作者是申請人、實際發起人、目前合法待辦處理人或具權限的營運管理員。
- 流程與 Task 狀態允許操作。
- Task Form Rule／欄位權限允許查看或修改該 `FIELD_KEY`。

送單前的暫存附件可以依規則刪除。正式附件原則上不可立即物理刪除；使用者刪除應改為 `DELETED` 並保存操作者、時間與理由，實體內容由保存政策及受控清理工作處理。

撤回、取消、駁回、完成與管理員終止流程時，不應立即刪除正式附件；保存期限應與表單、快照及稽核政策一致。

## 9. 安全要求

前端 `accept` 只作為提示，後端仍必須檢查：

- 副檔名與 MIME 白名單。
- Magic bytes／檔案 signature 與 MIME 一致性。
- 單檔大小、總大小、數量及帳號／Tenant rate limit。
- SHA-256。
- 病毒掃描與隔離狀態。
- 空檔案、截斷上傳及中斷重試。
- 預設禁止 executable、script、HTML、SVG 等高風險內容。
- Path traversal、zip bomb、檔名覆寫與 Content-Disposition injection。
- 上傳、下載、刪除及管理員操作稽核，log 不得包含附件內容。

下載回應應使用 `X-Content-Type-Options: nosniff`、適當 CSP 與安全的 `Content-Disposition`。非可信內容預設下載，不提供公開、永久且無授權驗證的 URL。

## 10. 前端行為

附件元件至少顯示允許類型、大小及數量限制、上傳進度、錯誤原因、檔名、大小、掃描狀態與刪除操作。頁面離開時若仍在上傳必須提示；Session 過期時要求重新上傳，不得顯示假成功。

Designer 試跑不可把測試附件寫入正式附件區；應使用短效試跑 Session，或在第一階段停用實體上傳並顯示說明。

## 11. 測試與完成條件

至少測試單檔、多檔、必填、數量與大小限制、非法 Extension、MIME／magic bytes 不一致、空檔案、超大檔案、中斷重試、惡意檔名、跨 Tenant、無權下載／刪除、Session 過期、重複送單、併發刪除、DB rollback、搬檔失敗、孤兒清理、病毒掃描各狀態及 Linux 目錄權限。

只有表單設計、暫存上傳、正式綁定、下載、受控刪除、安全檢查及清理流程全部通過後，才能標記 FlowMint 附件功能完成。

## 12. 目前實作進度（2026-08-13）

已完成：

- MariaDB 建立 `fm_attachment_upload_session`、`fm_attachment_upload_file`；正式附件沿用既有 `fm_attachment`。
- 暫存上傳、清單與刪除 API，實體檔使用 `{base.uploadDir}/flowmint`。
- 單檔大小限制、安全路徑、SHA-256、Extension、MIME 與 PDF/JPEG/PNG magic bytes 檢查。
- Runtime 送單接受 `uploadSessionId`，成功送單時綁定 `FORM_DATA_ID`、寫入正式附件並移至年月目錄。
- 正式附件清單與下載 API；目前授權對象為表單擁有者、流程實際發起者，或目前合法待辦候選人／受派人。
- Workspace 會辨識 Form.io `file` 元件，提供上傳、清單、刪除、必填檢查及送單綁定。
- 申請單與待辦頁已提供正式附件清單及下載操作。
- 每小時批次清理已過期 Session 的暫存檔，成功清理後將檔案標為 `DELETED`、Session 標為 `EXPIRED`。

尚未完成，因此附件功能仍不可標記為全部完成：

- 營運管理員及 Task Form Rule 欄位層級的下載授權。
- 正式附件邏輯刪除、病毒掃描引擎、數量／總容量／rate limit。
- 交易失敗孤兒檔偵測，以及跨資料庫／檔案系統的完整補償流程。
- Designer 試跑附件隔離，以及端對端、跨 Tenant、交易失敗與併發測試。
