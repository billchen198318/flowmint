# 23 請購單流程與表單配置規格

## 1. 文件定位

本文件定義 `FM_PURCHASE_REQUEST` 請購申請單的表單配置、專業審查分流、採購與財務權責、金額核決路徑及 BPMN 實作基準。

請購流程不得只依金額分流。採購人員負責詢價、比價、供應商、交期、付款及採購條款，不應被假設能獨立判斷產線設備、資訊安全、品質檢測、工安環保或工程規格。流程必須同時使用兩個維度：

```text
採購類別／風險屬性 → 決定專業審查單位
totalAmount          → 決定最終核決層級
```

第一版金額與重大投資門檻及必要群組已於 2026-08-20 確認並寫入 A01 流程草稿；正式上線仍須完成 Java 正式發布及多帳號 E2E。

## 2. 表單現況與發布前置

- Tenant：`A01`
- Form Code：`FM_PURCHASE_REQUEST`
- 表單名稱：請購申請單
- 目前版本：Version 1 `PUBLISHED`
- 主要金額欄位：`totalAmount`，代表含稅總金額

### 2.1 2026-08-20 實作狀態

- `FM_PURCHASE_APPROVAL／Version 1`：`DRAFT`，尚未建立 Flowable deployment。
- BPMN：15 個 User Task、31 條 Sequence Flow，SHA-256 為 `103c77e03844cb61a5cda2052511ebbf80b9e3488cb8deeb30cfff64d9eee958`。
- `contractReview`、`applicantCorrection`、`investmentReview` 及其表單、政策、指派設定均已建立。
- 發布前 Java BPMN、Gateway 欄位、Task 設定、Resolver、群組成員、Start Policy 與 SHA 檢查均已通過。
- 下一步是經 user 明確授權後呼叫 Java 正式發布服務；不得以 SQL 直接把版本改為 `PUBLISHED`。
- 附件欄位：`attachments`，允許多檔、單檔 8 MB、最多 10 件、合計 20 MB

流程 User Task 只能綁定已發布表單版本，因此建立正式流程前必須先完成表單檢查並發布 Version 1。已發布表單不得直接修改；後續欄位調整須建立新版本，再建立或更新流程版本的表單綁定。

## 3. 權責分離

| 階段 | 責任 | 不應承擔的責任 |
| --- | --- | --- |
| 申請部門 | 說明需求、用途、規格與驗收標準 | 自行決定供應商及付款條件 |
| 部門主管 | 確認必要性、部門優先序與需求合理性 | 取代專業技術與財務審查 |
| 專業審查單位 | 確認技術、安全、法規、相容性與驗收要求 | 詢比議價及最終付款安排 |
| 採購部 | 詢價、比價、供應商、交期及商務條款 | 獨立判斷所有專業設備規格 |
| 財務 | 預算、CAPEX／OPEX、會計科目及資金安排 | 取代需求與技術可行性判斷 |
| 高階主管 | 依金額、風險及公司授權做最終核決 | 補做前段缺少的專業審查 |

## 4. 採購類別與專業審查

### 4.1 建議類別代碼

現有 `purchaseCategory` 僅有 `GENERAL`、`IT_EQUIPMENT`、`OFFICE_SUPPLIES`、`SERVICE`、`OTHER`，不足以安全分流。下一版表單建議擴充為：

| 代碼 | 類別 | 必要專業審查 |
| --- | --- | --- |
| `PRODUCTION_EQUIPMENT` | 產線設備 | 製程工程及設備工程 |
| `IT_EQUIPMENT` | 資訊設備 | 資訊部 |
| `SOFTWARE_SERVICE` | 軟體、雲端及資訊服務 | 資訊部；涉及合約時加合約審查 |
| `QUALITY_EQUIPMENT` | 品質與檢測設備 | 品質保證單位 |
| `EHS_EQUIPMENT` | 工安與環保設備 | 環安衛單位 |
| `RAW_MATERIAL` | 原物料 | 需求單位、品質及必要時研發 |
| `CONSTRUCTION` | 工程與修繕 | 設備工程；涉及施工時加環安衛 |
| `OFFICE_SUPPLIES` | 辦公設備與用品 | 總務部 |
| `PROFESSIONAL_SERVICE` | 顧問、委外與專業服務 | 需求單位；涉及合約時加合約審查 |
| `GENERAL` | 一般採購 | 依申請部門主管確認，必要時由採購分類 |
| `OTHER` | 其他 | 先由採購分類確認，不得直接略過專業審查 |

### 4.2 風險屬性

單一類別不足以涵蓋複合案件。例如產線設備可能同時涉及資訊連線、施工及工安。因此表單應另提供布林風險屬性：

- 是否涉及公司網路、帳號、系統或資料。
- 是否涉及施工、動火、高處、用電或其他工安風險。
- 是否涉及環保、排放、化學品或法規許可。
- 是否需要合約、保密條款或個人資料處理。
- 是否屬資本支出 `CAPEX`。
- 是否為緊急採購或指定供應商。

必要時以平行專業會簽處理多個風險，不可只取第一個命中的類別分支。

## 5. 建議 BPMN 主流程

```text
開始
  ↓
申請部門主管簽核
  ↓
類別與風險判斷
  ↓
一個或多個專業審查（必要時平行會簽）
  ↓
採購部商務審查
  ↓
財務／預算審查
  ↓
金額核決 Gateway
  ├─ totalAmount <= 300,000 → 完成
  ├─ 300,000 < totalAmount <= 500,000 → 總經理核准 → 完成
  └─ totalAmount > 500,000 → 總經理核准 → 董事長核准 → 完成
```

所有請購案都必須經過財務審查；金額只決定財務之後是否需要總經理及董事長核准。

建議流程基本資料：

- Process Key：`FM_PURCHASE_APPROVAL`
- Process Name：請購簽核流程
- Category：`PURCHASE`

| Task Definition Key | 節點名稱 | Resolver／群組 |
| --- | --- | --- |
| `departmentApproval` | 申請部門主管簽核 | `INITIATOR_ORG_HEAD` |
| `productionEquipmentReview` | 產線設備專業審查 | `PURCHASE_TECH_EQUIPMENT` |
| `itReview` | 資訊與資安審查 | `PURCHASE_IT_REVIEW` |
| `qualityReview` | 品質與檢測審查 | `PURCHASE_QUALITY_REVIEW` |
| `ehsReview` | 工安環保審查 | `PURCHASE_EHS_REVIEW` |
| `generalAffairsReview` | 總務審查 | `PURCHASE_GENERAL_AFFAIRS` |
| `contractReview` | 合約審查 | `PURCHASE_CONTRACT_REVIEW` |
| `purchaseReview` | 採購部商務審查 | `PURCHASE_COMMERCIAL_REVIEW` |
| `financeApproval` | 財務與預算審查 | `PURCHASE_FINANCE_REVIEW` |
| `generalManagerApproval` | 總經理核准 | 專用群組或 `FIXED_ACCOUNT` |

組織或人員異動頻繁的節點應優先使用 `APPROVAL_GROUP`，不要把姓名、中文部門名稱或個人帳號直接寫在 BPMN 條件中。總經理與董事長即使初期使用 `FIXED_ACCOUNT`，也必須保存穩定登入帳號，不得使用顯示姓名。

目前既有 `FIN01／財務通知` 為 `SEQUENTIAL` 且用途為通知，不應未經確認直接當作財務核准群組。

## 7. Gateway 條件

### 7.1 金額路徑

```text
totalAmount <= 300000
totalAmount > 300000 && totalAmount <= 500000
totalAmount > 500000
```

`totalAmount` 必須由後端重新驗證品項、稅額及合計，流程不可只信任前端計算值。Gateway 必須具有 default flow，異常、缺值、負數或非數值時不得自動完成流程，應建立 Incident 或退回修正。

### 7.2 類別與風險路徑

- 類別決定基本專業審查。
- 風險屬性增加額外審查，不得覆蓋基本審查。
- 多個審查同時適用時，使用平行 Gateway 或 `ALL` 模式，全部完成後才匯流。
- `OTHER` 必須進入採購分類確認，不得作為免審查捷徑。

## 8. 表單欄位補強

除現有申請資訊、品項、金額與附件外，建議下一版增加：

- 採購大類、次分類。
- `CAPEX`／`OPEX`。
- 是否已編列預算、預算編號及可用預算。
- 使用部門、安裝或交付地點。
- 技術規格及驗收標準。
- 緊急採購、指定供應商及理由。
- 資訊、施工、工安、環保、合約及個資風險欄位。
- 建議供應商只能作為申請資訊，不代表採購部免除詢比價責任。
- 報價單、規格書、圖面、合約草案及其他佐證附件。

## 9. Task Policy 與欄位權限

- `applicantCorrection`：表單及附件可編輯，重送時重新執行 Schema 與金額驗證。
- 其他簽核節點：原始申請內容與附件唯讀，只允許簽核意見及節點專屬審查欄位。
- 退回與駁回必須填寫意見。
- 部門主管、專業審查、採購及財務可依公司政策開放轉派或循序前加簽。
- 總經理及董事長預設不允許任意轉派與加簽。
- 自簽政策建議使用 `SKIP_TO_NEXT`；董事長等唯一核決人若無替代者可使用 `INCIDENT`。
- 建議 SLA：部門主管 24 小時、專業審查 48 小時、採購 48 小時、財務 24 小時、高階核決 48 小時。

## 10. 退回、補件與駁回

- 專業審查、採購或財務發現資料不足時，退回 `applicantCorrection`。
- 補件可修改需求、品項、金額、分類、風險屬性與附件；重送後必須重新計算完整路徑，不得沿用舊金額或舊專業審查判斷。
- 若補件改變類別、風險或金額，舊審查結果保留於稽核軌跡，但不得直接視為新版本申請的有效核准。
- 駁回代表本次請購終止，必須保存表單快照、附件關聯、意見及 Task Action。

## 11. 發布與驗收條件

1. 發布 `FM_PURCHASE_REQUEST` 表單版本。
2. 建立並確認各專業、採購、財務及高階核決群組成員。
3. 建立 BPMN 草稿及各 User Task 的表單綁定。
4. 完成 Task Policy、Assignment Rule 與 Gateway default flow。
5. 使用不同部門申請人執行 Resolver Preview。
6. 分別測試產線設備、資訊設備、一般用品、複合風險與 `OTHER`。
7. 測試 `300,000`、`300,000.01`、`500,000`、`500,000.01` 邊界。
8. 測試退回補件後類別及金額改變時重新分流。
9. 測試附件上傳、送單綁定、簽核人下載及跨 Tenant 禁止存取。
10. 所有 Resolver、表單、政策及 BPMN 發布檢查通過後才可部署。

## 12. 完整流程邊界

前述類別與金額流程只代表第一版主幹，正式實作必須使用本節之後的完整決策模型，不得直接以單一採購類別加單一金額 Gateway 當作正式流程。

採購生命週期應拆成三個階段：

```text
請購申請與授權
  ↓
採購執行／詢比議價／簽約／下單
  ↓
到貨／驗收／資產建檔／付款
```

`FM_PURCHASE_APPROVAL` 的終點是公司正式授權採購部開始採購或下單，不代表已完成採購、驗收、付款或固定資產建檔。大型設備的 FAT、SAT、安裝試車、驗收及尾款應由後續採購履約流程管理，不得全部混入請購 BPMN。

## 13. 五維決策模型

正式分流至少同時考慮：

1. 採購類別。
2. 風險屬性。
3. 預算與支出性質。
4. 採購方式與例外。
5. 金額與重大投資門檻。

```text
必要專業審查 = 採購類別 + 風險屬性
最終核決層級 = 金額 + CAPEX/OPEX + 預算內外 + 重大投資 + 採購例外
```

申請人只能填寫客觀業務資料與風險問卷，不得直接選擇要略過哪一個審查單位。後端依受控規則產生必要審查清單；找不到有效簽核人時建立 Incident，不得自動略過。

## 14. 完整 BPMN 建議

```text
開始
  ↓
申請資料完整性檢查
  ↓
申請部門主管簽核
  ↓
預算有效性預檢
  ↓
類別與風險決策
  ↓
一個或多個平行專業會簽
  ├─ 製程／設備
  ├─ 品質
  ├─ 資訊／資安
  ├─ 環安衛
  ├─ 廠務
  └─ 合約／法務
  ↓
專業審查匯流
  ↓
採購商務審查
  ↓
財務最終審查
  ↓
核決權限矩陣
  ├─ 一般授權層級
  ├─ 總經理
  ├─ 董事長
  └─ 重大投資／董事會或投資審議
  ↓
請購核准
  ↓
交接採購執行
  ↓
結束
```

預算預檢用來提早攔截沒有預算或基本資料無效的案件；採購審查後的財務最終審查則依當時金額、會計分類與付款條件做正式核決。兩者目的不同，不視為重複簽核。

## 15. 採購方式與例外控制

流程必須區分：

- 一般詢比價。
- 單一來源或指定供應商。
- 緊急採購。
- 新供應商。
- 關係人交易。
- 招標。
- 進口採購。
- 租賃。
- 框架合約或重複採購。

單一來源必填原因並增加採購主管核准；緊急採購必填緊急原因與不採購的影響，但不得略過財務、資訊安全、工安或法定專業審查。關係人交易、重大預付款及例外付款條件應提高核決層級或增加法務／財務審查。

## 16. 預算與財務控制

流程至少區分：

- `CAPEX`／`OPEX`。
- 預算內／預算外。
- 預算編號、成本中心及可用餘額。
- 是否跨年度。
- 是否外幣及換算匯率。
- 是否需要預付款及預付款比例。
- 單張請購金額及整體專案總額。

核決金額使用後端驗證的 TWD 含稅金額，不信任前端可修改的合計。系統必須以專案總額或可識別的關聯請購檢查疑似拆單，不得只按單張請購規避核決門檻。

## 17. 核決權限與重大投資

目前討論的金額門檻僅作一般請購初步基準：

| TWD 含稅金額 | 一般基本核決 |
| ---: | --- |
| `<= 300,000` | 財務後完成 |
| `> 300,000 且 <= 500,000` | 加總經理 |
| `> 500,000` | 加總經理及董事長 |

此表不足以直接處理數千萬元設備。正式權限矩陣仍須增加：

- 重大投資門檻。
- 董事會或投資審議門檻。
- 預算外提高核決層級。
- CAPEX 與 OPEX 的不同授權。
- 專案總額與累計金額。
- 緊急、單一來源、關係人及重大預付款等例外。

重大投資及董事會門檻屬公司治理參數，不得由開發人員自行假設。未經權責單位確認前，相關 BPMN 與 `APPROVAL_AUTHORITY` 規則不得發布為正式版本。

A01 租戶於 2026-08-20 確認第一版重大投資審議條件為：`expenseType == "CAPEX"` 且 `projectTotalAmount > 10000000`。`10,000,000` 元整不觸發，`10,000,000.01` 元起進入 `PURCHASE_INVESTMENT_REVIEW`，由群組內所有有效成員完成審議。

## 18. 退回、補件與核准失效

補件後不可一律沿用舊核准。系統應依變更內容判定重新審查範圍：

| 補件變更 | 必須重新審查 |
| --- | --- |
| 文字說明或補附件，且規格與金額不變 | 原退回節點 |
| 品項、規格或數量 | 部門主管及相關專業審查 |
| 採購類別 | 重新執行完整類別分流 |
| 風險旗標 | 新增對應專業審查 |
| 金額 | 財務及核決層級重新判斷 |
| 預算編號或 CAPEX／OPEX | 預算預檢及財務重新審查 |
| 供應商或採購方式 | 採購、法務及必要高階核決 |
| 合約或付款條件 | 採購、財務及法務 |

每次補件都必須遞增 Form Revision、建立不可變快照、保留舊核准紀錄，並標示哪些舊核准因重大變更而失效。重送時重新計算類別、風險、金額與核決路徑。

## 20. 表單版本策略

MariaDB 中 `FM_PURCHASE_REQUEST` Version 1 目前仍為 `DRAFT`，且尚未配對正式 BPMN。若確認從未正式使用，可先備份目前 Schema 與 Script，再直接完善 Version 1 後發布，避免留下沒有業務價值的半成品版本。

若 Version 1 已被測試資料、外部介接或驗收腳本引用，則保留 Version 1 並建立 Version 2。無論採哪一種方式，都不得直接修改已發布版本。

### 20.1 目前實作狀態

`A01` 的 Version 1 草稿已完成兩批欄位補強。第一批加入採購分類、支出與預算、採購方式與例外及風險問卷；第二批加入設備／工程與驗收、外幣與付款及 CAPEX 投資效益。Schema 與 Custom Script 已在 MariaDB 更新並重算 SHA-256，但尚未完成瀏覽器驗收與發布。

申請資訊使用平台共用的唯讀 `documentNumber／請購單編號` 欄位。欄位不接受使用者輸入，也不保存為可修改的 submission data；實際單號由共用單據編號服務產生並由 Runtime 注入。表單設計者可從設計器一鍵加入此系統欄位，詳細規格見 [24 共用單據編號規格](24-共用單據編號規格.md)。

附件用途分類仍未完成。現有附件服務只保存欄位 key 與檔案 metadata；若要讓同一附件欄位中的每一個檔案分別標示報價單、規格書、合約草案等用途，必須同步擴充附件資料模型、API 與 Workspace UI，不得只新增無法與檔案一一對應的表單欄位。

## 24. 2026-08-31 Form Runtime 修正與 BPMN 複核

共用待辦頁原先將 `APPROVE／REJECT／RETURN／RESUBMIT` 全部視為完整表單提交，造成資料不完整時
可能連退回或駁回都被 Form.io required、格式驗證或 Custom JavaScript `beforeSubmit` 阻擋。
目前已改為只有 `APPROVE／RESUBMIT` 提交並驗證表單；`REJECT／RETURN` 不修改表單資料，仍由
既有前後端檢查意見、理由、權限及退回目標。Nuxt Client、SSR 與 Nitro production build 已通過。

`A01／FM_PURCHASE_REQUEST` 已由已發布 Version 1 建立 Version 2 草稿。Version 2 的
`onFormLoad` 在 `RUNTIME_TASK` 不再重新查詢或改寫申請人、員工、任職及部門，避免兼任部門在
主管開啟待辦時被切回主要部門；金額、稅額、匯率及台幣總額重算仍保留。Script 已完成編譯及
mock 驗證：起單模式正常呼叫目前員工、員工選項與任職 Data Action；待辦模式 Data Action 呼叫為
0 次、原任職保持不變且金額重算正確。Version 2 SHA-256 與即時計算一致，目前仍為 `DRAFT`，
Version 1 保持 `PUBLISHED`，正式 Process Form Binding 尚未變更。

請購 Process Version 2 與公司名片 Process Version 1 已重新進行 BPMN graph、Gateway、Task
Policy、Form Rule 及 Resolver 唯讀複核。請購流程所有節點均可由 Start 到達，Inclusive Gateway
具有 Default Flow，9 條條件審查路徑會在實際啟動路徑全部完成後匯流，再依序進採購、財務及金額
核決。`OTHER` 與無法分類案件走 `applicantCorrection`，補件後回 `departmentApproval` 重新分流，
這是本文件既定治理規則，不是缺漏。BPMN／發布 Validator 共 10 項測試通過，未發現確定的 flow bug。

複核另確認 Process Version 2 的資料庫 `BPMN_SHA256` 與 Flowable deployment resource 完整 XML
SHA 不一致；逐條比較目前 User Task、Gateway、Sequence Flow、source／target 及 condition 均相同，
尚未發現 Runtime 路由差異，差異可能位於 BPMN DI 版面或 XML metadata。此項仍列為發布完整性
待辦，下一個 Process Version 發布時必須重新部署並確認兩端 SHA 完全一致。
