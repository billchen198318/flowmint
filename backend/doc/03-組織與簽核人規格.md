# 03 組織與簽核人規格

## 1. 部門樹

每個 Tenant 有一棵主要部門樹，根節點通常命名為「總公司」。根節點不是法人主檔。

`TREE_DEPTH` 與 `PATH` 由後端計算。部門本身不保存人員簽核 Level；簽核 Level 由 Tenant 共用職稱定義，員工任職再組合部門與職稱。

## 2. 組織簽核層級

管理者可維護層級方案。範本：

| Order | Code | 台灣 | 中國大陸 |
|---:|---|---|---|
| 0 | COMPANY | 公司層 | 公司层 |
| 10 | GM | 總經理層 | 总经理层 |
| 20 | VP | 副總層 | 分管副总层 |
| 30 | DIVISION | 處／中心級 | 事业部／中心级 |
| 40 | DEPARTMENT | 部級 | 部门级 |
| 50 | SECTION | 課級 | 科室级 |
| 60 | TEAM | 組／班級 | 组／班级 |

名稱可修改，Resolver 使用 ID／Code，不依賴中文文字。

## 3. Tenant 職稱與部門職務

- 每個 Tenant 共用職稱主檔，例如一般員工、課長、經理、處長、副總，避免每個部門重複建立相同職稱。
- 每個職稱對應 `fm_org_approval_level`。`fm_org_title` 不保存 `ORG_UNIT_ID`。
- 每個部門可自訂職務，例如成本審核人、品質會簽人。
- 部門職務與擔任人為選配功能；一般主管簽核或跨部門群組可不設定，只有流程需依部門尋找固定專責人員時才使用。
- 職稱表示位階；職務表示簽核責任。
- `FM_PROG002D0004` 維護 Tenant 共用的職稱與簽核 Level。
- `FM_PROG002D0001` 的員工任職功能配置 `EMPLOYEE_ID + ORG_UNIT_ID + TITLE_ID`。
- `FM_PROG002D0005` 從有效員工任職指定 HEAD／DEPUTY_HEAD／ACTING_HEAD。
- `ORG_TITLE` Resolver 以目標部門及指定 `TITLE_ID` 查詢有效的 `fm_employee_org_assignment`。

## 4. 人員與部門

- Employee 對應一個 QIFU4 Account。
- 一個 Employee 同時間必須有且只有一個主要部門。
- 每筆部門任職必須設定直屬主管來源；預設 ORG_HEAD 自動取得本部門 HEAD。
- EXPLICIT 時保存 DIRECT_MANAGER_ASSIGNMENT_ID，指向主管在特定部門的有效任職。
- 部門 HEAD 預設由 PARENT_HEAD 找上層部門 HEAD；最高負責人才允許 NONE。
- 不得指定自己或形成任何直接／間接主管循環。
- 可有多個兼任部門。
- 停用 Employee 前必須處理其主管角色與待辦。
- 工號在 Tenant 內唯一。

## 5. 主管

主管類型：

- `HEAD`：主要主管，同一部門同時間一人。
- `DEPUTY_HEAD`：副主管，可多人並以 Priority 排序。
- `ACTING_HEAD`：期間代理主管，可設定短期生效。

「總經理」是主管職務；「總經理室」只有真實存在時才建立成部門。

### 6.0.1 核決權限條件格式

`fm_approval_authority_rule.CONDITION_CONFIG` 使用受控 JSON 條件，不允許 JavaScript、SQL 或其他可執行運算式。格式如下：

```json
{
  "match": "ALL",
  "conditions": [
    {
      "field": "form.totalAmount",
      "operator": "GTE",
      "value": 100000
    },
    {
      "field": "form.category",
      "operator": "IN",
      "value": ["MANUFACTURING_EQUIPMENT", "IT_EQUIPMENT"]
    }
  ]
}
```

`match` 僅允許 `ALL` 或 `ANY`。`operator` 僅允許 `EQ`、`NE`、`GT`、`GTE`、`LT`、`LTE`、`IN`、`NOT_IN`。`field` 使用以點分隔的資料路徑；條件設計 UI 必須以欄位、運算子與值的結構化元件產生此 JSON，不讓使用者手寫或執行任意程式碼。
### 6.1 簽核群組

簽核群組用於跨部門或無法由組織主管、職稱、職務解析的固定人員集合，由 `FM_PROG003D0001` 維護。流程設定選擇 `APPROVAL_GROUP` 時，應保存群組識別資料，執行時再依群組的啟用成員解析簽核人；一般部門主管簽核仍應使用 `ORG_HEAD`，不需要另外建立群組。

群組提供三種派送方式：

- `CANDIDATE`：所有成員都是候選人，由其中一人承接或完成工作。
- `ALL`：所有成員都必須處理，適合固定成員會簽。
- `SEQUENTIAL`：依成員優先順序逐一處理；優先順序數字越小越先處理。

群組代碼是建立後不可變更的業務識別碼；後續流程設定與資料關聯一律保存 `APPROVAL_GROUP_ID`，不可使用可能顯示於畫面的群組名稱作為關聯鍵。成員只能選擇同一 Tenant 的啟用員工，並可設定生效起迄日。群組或成員停用後，不應再被新的簽核工作解析；已建立的流程工作則依流程快照與執行規則處理。

解析順序：

```text
登入申請人
  → 有效 Employee
  → 有效主要部門
  → 依父鏈與簽核層級找目標部門
  → HEAD
  → ACTING_HEAD / DEPUTY_HEAD
  → Workflow Delegation
  → 自簽與去重政策
  → Snapshot / Flowable assignment
```

### 6.2 工作代理

`FM_PROG003D0002` 用於設定員工在固定期間內，將原本應由自己處理的簽核工作交由另一位員工代理。這是請假、出差或臨時職務交接時使用的必要設定；它不會改變部門主管、職稱或簽核群組的原始組織資料。

- 被代理人與代理人必須是同一個 Tenant 內的有效帳號，且不可為同一人。
- 代理期間必須同時填寫開始與結束時間，結束時間必須晚於開始時間。
- 同一被代理人、同一代理範圍的啟用期間不可重疊，避免同一工作同時解析出多位代理人。
- 代理範圍可設定為全部流程、指定流程或指定簽核群組。指定簽核群組使用不可變的 `APPROVAL_GROUP_ID`；指定流程在流程定義管理功能完成前，先填寫流程識別碼。
- 「允許再次轉代理」決定代理人是否可把收到的代理工作再交給其他人，預設為否。
- 編輯時 Tenant 與被代理人不可修改；如選錯，應停用原設定後另行新增，避免既有簽核追蹤對象改變。
- 代理規則只影響簽核人解析。已建立且已指定處理人的工作是否重新套用代理，應由工作建立／重新指派流程明確決定，不直接改寫歷史工作。

資料以 `DELEGATION_ID` 作為穩定業務識別，資料庫主鍵 `OID` 僅供內部關聯使用。
## 7. 自簽、重複與缺位

自簽政策：`ALLOW`、`SKIP_TO_NEXT`、`REQUIRE_ALTERNATE`、`INCIDENT`。  
重複政策：`KEEP_EACH_LEVEL`、`MERGE_CONSECUTIVE`、`SKIP_ALREADY_APPROVED`。

主管缺位依規則嘗試 ACTING、DEPUTY、上一層或管理群組；最後仍無人必須建立 Incident，禁止自動通過。

## 8. 組織樹拖拉

- 拖拉前呼叫 Preview。
- Preview 顯示舊／新父節點、層級衝突、深度與受影響子樹。
- 儲存時後端重新檢查 Tenant、循環、版本與層級。
- 整個子樹單一 Transaction。
- 舊待辦不自動改派；新待辦使用新組織。
- 管理員若需重新解析舊待辦，必須透過有理由與稽核的管理功能。
