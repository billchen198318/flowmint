# 30 採購單與驗收單表單流程配置規劃

日期：2026-08-28  
狀態：設計規劃  
實作方式：FlowMint 表單設計、流程設計、Task Policy、Assignment Resolver 與 Data Action 配置

## 1. 目的與實作原則

本文件規劃「採購單」及「驗收單」如何完全使用 FlowMint 既有低程式碼能力建置，
不為這兩張單據新增 Java Controller、Service、Mapper、Vue 頁面或其他專用程式。

使用的管理功能如下：

| 功能 | FlowMint 操作入口 | 用途 |
| --- | --- | --- |
| 表單與版本 | `FM_PROG005D0001` | 使用 Form.io 建立採購單、驗收單與版本 |
| 流程與版本 | `FM_PROG004D0001` | 使用 BPMN Designer 建立流程、Gateway、Task Policy 與 Resolver |
| 關卡欄位權限 | 流程設計器的 User Task 屬性 | 設定各節點 Hidden／Read／Edit |
| 動態資料 | `FM_PROG006D0001`、`FM_PROG006D0002` | 查詢已核准請購、採購單、供應商及累計驗收資料 |
| 單據編號 | 共用單據編號設定 | 產生不可由使用者修改的採購單號及驗收單號 |
| 簽核人 | Approval Group／Resolver／核決權限 | 動態解析採購、法務、財務、驗收及主管人員 |

本案只配置已發布的 Form、Data Action 與 BPMN Version。不得在 BPMN 使用 Script Task、
直接 SQL、寫死人員姓名或帳號；不得在表單中直接呼叫未發布或任意外部 URL。

## 2. 單據邊界與關聯

完整生命週期固定拆分為：

```text
請購單 FM_PURCHASE_REQUEST（需求及預算授權）
  1 ── N
採購單 FM_PURCHASE_ORDER（供應商、價格、交期及下單授權）
  1 ── N
驗收單 FM_GOODS_ACCEPTANCE（實際到貨、品質及數量驗收）
  ↓
通知財務／外部 ERP 進行應付與付款作業
```

第一版採取以下限制，以維持關聯清楚且可稽核：

- 一張採購單只能引用一張已核准且未關閉的請購單。
- 一張請購單可以拆成多張採購單，但所有採購單累計數量及金額不得超過核准值。
- 一張驗收單只能引用一張已核准／已下單的採購單。
- 一張採購單可以分批建立多張驗收單。
- 驗收累計不得超過採購數量；超收必須先辦理採購變更，不得在驗收流程放行。
- 單據間使用不可變的 Business Key 關聯，不使用資料庫 OID、單據顯示名稱或畫面名稱。FlowMint
  Runtime 的 Business Key 是 UUID，單據編號另存於 `documentNumber`；畫面顯示及人工查找使用
  Document Number，授權、載入及跨單關聯使用 Business Key，兩者不得混用。
- 採購單核准不等於驗收完成；驗收完成也不等於付款完成。

## 3. 共用代碼與狀態

### 3.1 建議表單及流程代碼

| 類型 | 代碼 | 名稱 |
| --- | --- | --- |
| Form | `FM_PURCHASE_ORDER` | 採購單 |
| Process | `FM_PURCHASE_ORDER_APPROVAL` | 採購單審核流程 |
| Document Type | `PURCHASE_ORDER` | 採購單號規則 |
| Form | `FM_GOODS_ACCEPTANCE` | 驗收單 |
| Process | `FM_GOODS_ACCEPTANCE_APPROVAL` | 驗收審核流程 |
| Document Type | `GOODS_ACCEPTANCE` | 驗收單號規則 |

### 3.2 採購單業務狀態

| 代碼 | 意義 | 進入條件 |
| --- | --- | --- |
| `DRAFT` | 草稿 | 採購承辦尚未送出 |
| `IN_APPROVAL` | 審核中 | 已啟動採購流程 |
| `RETURNED` | 補件中 | 任一審查節點退回採購承辦 |
| `APPROVED` | 已核准 | 所有必要審查與核決完成 |
| `ORDERED` | 已下單 | 採購完成對外下單登錄 |
| `PARTIALLY_RECEIVED` | 部分到貨／驗收 | 至少一張驗收單完成，但尚未全數驗收 |
| `FULLY_ACCEPTED` | 全數驗收 | 採購品項全部完成驗收 |
| `CLOSED` | 結案 | 無待交貨、退貨、索賠或尾款條件 |
| `CANCELLED` | 取消 | 核准後依取消流程終止 |

狀態由流程結果或受控 Data Action 回填；一般表單使用者不得直接編輯。

### 3.3 驗收結果代碼

| 代碼 | 顯示名稱 | 後續處理 |
| --- | --- | --- |
| `PASS` | 合格 | 可累計合格數量 |
| `CONDITIONAL_PASS` | 條件式驗收 | 必填缺失、改善期限及保留款建議 |
| `PARTIAL_PASS` | 部分合格 | 每個品項分別記錄合格與不合格數量 |
| `REJECT` | 不合格 | 進入退貨／重交／改善路徑 |

## 5. 採購單 BPMN 流程設計

### 5.1 主流程

```text
Start
  ↓
purchasePreparation（採購承辦建單／補件）
  ↓
purchaseValidationGateway
  ↓
parallelReviewSplit
  ├─ contractReview（需要合約、單一來源、關係人或例外條款）
  ├─ technicalConfirmation（規格被採購內容變更）
  └─ supplierReview（新供應商或供應商例外）
  ↓
parallelReviewJoin
  ↓
purchaseManagerApproval
  ↓
financeVarianceReview（有金額、預付款、幣別或預算差異時）
  ↓
purchaseAuthorityGateway
  ├─ 一般授權 → orderConfirmation
  └─ 超門檻／例外 → higherManagementApproval → orderConfirmation
  ↓
orderConfirmation（採購登錄正式下單資訊）
  ↓
End：ORDERED
```

`parallelReviewSplit／Join` 為業務圖的概念名稱，實際 BPMN 必須使用成對的
**Inclusive Gateway**，因三條專業審查路徑均為條件式且可能同時成立。FlowMint 禁止在
Parallel Gateway outgoing Sequence Flow 設定條件；不得直接以 Parallel Gateway 實作本段。
Inclusive Split 必須另設 Default Flow，代表本案不需要任何專業審查，並直接進入匯流後節點。

### 5.2 User Task 與 Resolver

| Task Key | 名稱 | Resolver 建議 |
| --- | --- | --- |
| `purchasePreparation` | 採購承辦建單／補件 | `APPROVAL_GROUP: PURCHASE_BUYER` 或指定目前承辦 |
| `contractReview` | 合約／法務審查 | `APPROVAL_GROUP: PURCHASE_CONTRACT_REVIEW` |
| `technicalConfirmation` | 需求與技術規格確認 | 來源請購申請部門主管＋原專業群組 |
| `supplierReview` | 供應商資格審查 | `APPROVAL_GROUP: PURCHASE_SUPPLIER_REVIEW` |
| `purchaseManagerApproval` | 採購主管審核 | `APPROVAL_GROUP: PURCHASE_MANAGER` |
| `financeVarianceReview` | 財務差異與付款條件審查 | `APPROVAL_GROUP: PURCHASE_FINANCE_REVIEW` |
| `higherManagementApproval` | 例外／高額核決 | `APPROVAL_AUTHORITY` |
| `orderConfirmation` | 正式下單登錄 | 原採購承辦帳號 |

所有 Resolver 必須在流程設計器完成 Preview；無有效人員時建立 Assignment Incident，
不得自動略過。採購承辦不得同時作為採購主管最終核准人。

### 5.3 Gateway 條件

下列為條件方向，正式門檻由公司採購及財務權責確認後在結構化條件設計器配置：

- `requiresContract == "Y"`、`sourcingMethod == "SINGLE_SOURCE"`、`relatedParty == "Y"`
  或 `nonStandardContractTerms == "Y"`：加入法務。
- `specificationChanged == "Y"` 或驗收標準改變：加入需求／專業確認。
- `newSupplier == "Y"` 或供應商狀態例外：加入供應商審查。
- `varianceAmountTwd != 0`、有預付款、外幣或預算條件改變：加入財務差異審查。
- 超過採購授權門檻、單一來源、緊急採購、關係人交易或重大預付款：提高核決層級。

每個 Exclusive Gateway 都必須有 default flow，將缺值或無法分類的案件退回採購承辦，
不可把 default flow 接到自動核准。

表單必須補上以下唯讀路由欄位，值由已發布的 Before Submit Data Action 依來源快照及本次內容
重新計算，使用者不得直接編輯：`specificationChanged`、`acceptanceCriteriaChanged`、
`nonStandardContractTerms`、`paymentTermsChanged`、`budgetConditionChanged`、
`requiresLegalReview`、`requiresTechnicalReview`、`requiresSupplierReview`、
`requiresFinanceReview`、`requiresHigherApproval`。BPMN 優先使用最後五個受控旗標，避免在
Sequence Flow 重複實作複雜政策。

### 5.4 Task Policy 與欄位權限

| 節點 | 可編輯欄位 | 其餘欄位 |
| --- | --- | --- |
| `purchasePreparation` | 供應商、採購方式、品項採購數量／價格、付款、交期、附件 | 來源請購及系統欄位唯讀 |
| `contractReview` | `legalReviewResult`、`legalReviewComment`、合約附件 | 唯讀 |
| `technicalConfirmation` | `technicalConfirmResult`、`technicalComment` | 唯讀 |
| `supplierReview` | `supplierReviewResult`、`supplierReviewComment` | 唯讀 |
| `purchaseManagerApproval` | `managerReviewComment` | 唯讀 |
| `financeVarianceReview` | 財務確認欄位、會計／預算意見 | 原採購內容唯讀 |
| `higherManagementApproval` | 核決意見 | 全部業務欄位唯讀 |
| `orderConfirmation` | ERP 採購單號、實際下單日、最終承諾交期 | 核准內容唯讀 |

退回或駁回必填意見。採購內容、供應商、金額、付款條件或交期在核准後變更時，不可直接
修改已完成快照，應建立採購變更版本並重新走受影響的審查路徑。

## 6. 驗收單 Form.io 表單設計

### 6.1 版面配置

使用六區：

### 6.2 表頭與來源欄位

| Label | Component Key | 元件 | 規則 |

| 供應商代碼／名稱 | `supplierCode`／`supplierName` | Text | 唯讀回填 |
| 到貨批次／送貨單號 | `deliveryNoteNo` | Text | 必填 |
| 發票號碼 | `invoiceNo` | Text | 選填；驗收不以有發票作為前提 |
| 到貨日期 | `deliveryDate` | Date | 必填，不得晚於驗收日期 |
| 驗收日期 | `acceptanceDate` | Date | 必填，預設當日 |
| 驗收地點 | `acceptanceLocation` | Text | 必填 |
| 驗收類型 | `acceptanceType` | Select | `PARTIAL`、`FINAL`、`MILESTONE`、`SERVICE` |
| 驗收主辦帳號 | `acceptanceOwnerAccount` | Hidden | Server Context／Resolver |
| 本次是否為末次驗收 | `finalAcceptance` | Radio | `Y/N` |

採購單選擇後，以 Data Action 載入核准採購快照、尚未驗收明細、驗收標準、保固、附件
需求及歷次驗收累計。來源採購單一旦首次送出即不可更換。

### 6.3 驗收明細 DataGrid

Component Key：`acceptanceItems`。

| Label | Key | 規則 |
| --- | --- | --- |

| 本次不合格數量 | `rejectedQuantity` | 計算／驗證欄位 |

```text
acceptedQuantity + rejectedQuantity = receivedQuantity
receivedQuantity <= remainingQuantity
finalAcceptance = Y 時，每一列驗收後剩餘數量必須為 0，或有核准的短交結案原因
```

`BEFORE_SUBMIT` 必須重新查詢已完成與進行中的驗收累計，避免兩張驗收單並行超收。

## 7. 驗收單 BPMN 流程設計

### 7.1 主流程

```text
Start
  ↓
receiptRegistration（收貨／到貨登錄）
  ↓
requesterAcceptance（需求單位驗收）
  ↓
professionalReviewSplit
  ├─ qualityAcceptance（品質／檢驗必要時）
  ├─ technicalAcceptance（設備、資訊、工程必要時）
  └─ ehsAcceptance（施工／工安必要時）
  ↓
professionalReviewJoin
  ↓
acceptanceResultGateway
  ├─ REJECT → nonconformanceDisposition → 等待重交／重驗 → requesterAcceptance
  ├─ CONDITIONAL_PASS → conditionalApproval
  └─ PASS／PARTIAL_PASS → acceptanceManagerApproval
  ↓
assetOrWarehouseGateway
  ├─ 資產 → assetRegistration
  ├─ 庫存 → warehouseConfirmation
  └─ 服務 → 直接匯流
  ↓
financeNotification（財務唯讀確認／付款條件通知）
  ↓
End：部分驗收或全數驗收
```

不得用 Timer 或自動節點把逾期改善視為合格。改善期限到期只能提醒或升級，仍須人工重驗。

### 7.2 User Task 與 Resolver

| Task Key | 名稱 | Resolver 建議 |
| --- | --- | --- |
| `receiptRegistration` | 收貨／到貨登錄 | `APPROVAL_GROUP: PURCHASE_RECEIVING`；無倉儲時由採購承辦 |
| `requesterAcceptance` | 需求單位驗收 | 來源請購申請人＋需求部門指定驗收人 |
| `qualityAcceptance` | 品質驗收 | `APPROVAL_GROUP: PURCHASE_QUALITY_REVIEW` |
| `technicalAcceptance` | 技術／功能驗收 | 依採購類別解析原專業審查群組 |
| `ehsAcceptance` | 工安／施工驗收 | `APPROVAL_GROUP: PURCHASE_EHS_REVIEW` |
| `nonconformanceDisposition` | 不合格處置 | 採購承辦＋供應商管理責任群組 |
| `conditionalApproval` | 條件式驗收核准 | 需求主管＋採購主管；有付款風險時加財務 |
| `acceptanceManagerApproval` | 驗收主管核准 | 需求單位主管 |
| `assetRegistration` | 資產建檔確認 | `APPROVAL_GROUP: ASSET_ADMIN` |
| `warehouseConfirmation` | 入庫確認 | `APPROVAL_GROUP: PURCHASE_RECEIVING` |
| `financeNotification` | 財務付款條件確認 | `APPROVAL_GROUP: PURCHASE_FINANCE_REVIEW` |

驗收人不得是供應商；FlowMint 僅解析 Tenant 內有效員工帳號。採購承辦可協調不合格處置，
但不得單獨取代需求、品質或技術單位判定合格。

「A＋B」不得配置成由任一候選人 Claim 即完成的單一 Candidate Task。若政策要求各責任方都核准，
必須拆成多個 User Task，以 Inclusive／Parallel 路徑匯流，或使用完成條件為 `ALL` 的正式會簽。
`nonconformanceDisposition`、`conditionalApproval` 及來源申請人加指定驗收人的責任方式，建置前
必須明確標示為「任一人處理」或「全部人核准」。

### 7.3 專業審查條件

- 原請購／採購類別為原物料、品質設備或需檢驗報告：加入 `qualityAcceptance`。
- 資訊設備、軟體、產線設備、工程、安裝試車：加入 `technicalAcceptance`。
- 涉及施工、環安或法規許可：加入 `ehsAcceptance`。
- 多個條件同時成立時使用成對的 Inclusive Gateway，啟動所有符合條件的路徑並等待實際啟動的
  路徑完成；不得使用帶條件的 Parallel Gateway。
- 專業審查清單必須由來源採購快照的客觀欄位決定，不讓收貨人勾選免審。

### 7.4 驗收 Task Policy

| 節點 | 可編輯內容 |
| --- | --- |
| `receiptRegistration` | 送貨資料、到貨數量、送貨附件 |
| `requesterAcceptance` | 合格／不合格數量、驗收結果、缺失、照片、驗收總結 |
| 專業驗收節點 | 各專業結果、測試紀錄與附件 |
| `nonconformanceDisposition` | 退貨、重工、換貨、折讓、改善期限及供應商回覆 |
| `conditionalApproval` | 條件式驗收核准意見、保留款建議 |
| `acceptanceManagerApproval` | 主管意見，不得改驗收數量 |
| `assetRegistration` | 資產標籤及建檔確認，不得改驗收結果 |
| `warehouseConfirmation` | 入庫單號及入庫確認 |
| `financeNotification` | 應付參考、付款／保留款確認；不得改原驗收內容 |

## 9. Form.io 條件、驗證與計算

優先使用 Form.io Builder 的 Required、Conditional、Validation、Calculated Value 及 FlowMint
Data Action Binding，不依賴專案原始碼。

### 9.1 採購單

- `sourcingMethod = SINGLE_SOURCE` 時顯示並必填 `singleSourceReason`。
- `sourcingMethod = EMERGENCY` 時顯示並必填 `emergencyReason`。
- `prepaymentRequired = Y` 時顯示預付款比例。
- `requiresContract = Y` 時顯示合約資料及附件。
- 外幣時顯示匯率及原幣金額。
- 明細改變時重新計算未稅、稅額、含稅及 TWD 金額。
- 前端計算不是安全邊界；Before Submit Action 必須重新驗證。

### 9.2 驗收單

- 不合格數量大於 0 時顯示缺失、處置及改善期限。
- `CONDITIONAL_PASS` 時必填保留條件、改善期限及建議保留款。
- `finalAcceptance = Y` 且仍有剩餘數量時，必填短交結案原因並走例外核准。
- 設備類顯示序號、保固、功能測試及資產欄位。
- 服務類隱藏實體收貨欄位，改顯示里程碑、成果文件及服務期間。
- 工程類顯示完工、試車、工安及缺失改善欄位。

若需要跨列複雜計算，可使用隨 Form Version 保存的表單級 Custom Script，但僅限計算、
顯示與呼叫已發布 Data Action；不可藉此直接存取資料庫、任意外部 API 或變更 Tenant。

## 10. 退回、駁回、取消與變更

### 10.1 採購單

- 法務、技術、供應商、採購主管或財務退回時，一律回 `purchasePreparation`。
- 補件後重新判斷所有 Gateway；不得沿用已不符合新內容的舊核准。
- 更換供應商、提高金額、修改付款條件或重要規格，至少重跑採購主管及受影響專業節點。
- 採購單核准後取消，須填原因並由採購主管核准；已有驗收資料時禁止直接取消。

### 10.2 驗收單

- 資料不足可退回 `receiptRegistration` 或 `requesterAcceptance`。
- 不合格不是一般補件；必須保留原驗收快照，經 `nonconformanceDisposition` 後建立重驗紀錄。
- 重驗不得覆寫原不合格數量、照片、意見及附件。
- 已通知財務的驗收若需撤銷，必須走更正流程並通知財務，不可刪除單據。

每次重送都遞增 Form Revision 並保留 Snapshot、Task Action、操作者、時間與意見。

## 11. 權限與職責分離

- 表單／流程設計者只能設計及發布，不等於採購核准人。
- 採購承辦可以建採購單，不可核准自己承辦的採購主管節點。
- 需求人員負責需求與實際使用驗收；採購負責商務及供應商處置。
- 財務負責預算、付款與會計條件，不取代技術驗收。
- 資產或倉儲只確認建檔／入庫，不改寫驗收結論。
- 高額、單一來源、關係人及條件式驗收使用結構化核決權限，不用 QIFU4 `TB_ROLE`
  代替 BPMN Assignment Resolver。
- 跨 Tenant 查詢、附件讀取、Business Key 載入全部拒絕。

## 12. 單據編號配置

在共用單據編號管理建立兩組規則，格式由公司確認。建議：

```text
PURCHASE_ORDER：PO-{yyyyMM}-{00000}
GOODS_ACCEPTANCE：GA-{yyyyMM}-{00000}
```

單號在正式送單交易產生，但不作為 Business Key。Runtime 另產生不可變 UUID Business Key；
草稿不預占正式號碼，重送、退回、重驗、駁回及更正均沿用原 Business Key 與 Document Number。
部分驗收的每張驗收單取得獨立 GA 單號及 Business Key，但共同引用來源 PO Business Key。

## 12.1 併發占用要求

`PO_VALIDATE_BEFORE_SUBMIT` 與 `GA_VALIDATE_BEFORE_SUBMIT` 不得只做 SELECT 後由前端判斷。
單純查詢無法阻止兩個交易同時通過剩餘量檢查。正式建置必須在同一後端交易內以版本欄位、
條件式 UPDATE 或專用占用資料完成「檢查並占用」；受影響筆數不符時整筆送單回滾。採購須原子
保留請購明細的數量與金額，驗收須原子保留採購明細的本次到貨／驗收數量，流程撤回、駁回、
取消或送單失敗時亦須定義釋放政策。

## 13. 設計與發布順序

1. 由採購、財務、需求、品質、資產及法務確認門檻、代碼與權責。
2. 建立所需 Approval Group、有效成員及代理規則。
3. 在 `FM_PROG006D0001` 確認資料來源；在 `FM_PROG006D0002` 建立、Preview 並發布唯讀
   Options／Lookup／Validation Actions。
4. 在 `FM_PROG005D0001` 建立 `FM_PURCHASE_ORDER` 草稿，配置 Form.io Schema、條件、
   Data Action Binding、附件與試跑資料。
5. 完成採購單欄位驗證及多帳號 Preview 後發布 Form Version 1。
6. 在 `FM_PROG004D0001` 建立 `FM_PURCHASE_ORDER_APPROVAL`，逐一設定 Form Binding、
   Task Policy、Resolver、Gateway default flow、退回目標及 SLA。
7. 執行流程 Validation Report 與 Resolver Preview，再發布流程 Version 1。
8. 以相同步驟建立及發布 `FM_GOODS_ACCEPTANCE` Form Version 1。
9. 建立及發布 `FM_GOODS_ACCEPTANCE_APPROVAL` Process Version 1。
10. 完成端到端驗收後才開放正式發起權限。

已發布 Form、Process 或 Data Action 不直接修改；調整時一律建立新版本。進行中的流程仍
使用原發布版本及快照，新案件才使用新版本。

## 14. 最低端到端驗收案例

### 14.1 採購單

1. 一般詢比價，金額及數量未超過請購核准值。
2. 一張請購拆兩張採購單，第二張只能使用剩餘數量與金額。
3. 兩位承辦同時對同一請購送單，系統阻止累計超額。
4. 單一來源、緊急採購、新供應商及關係人交易正確增加節點。
5. 規格改變時重新由需求／技術單位確認。
6. 外幣、預付款及金額差異正確進入財務審查。
7. 退回補件後更換供應商或提高金額，重新計算路徑。
8. Resolver 無有效人員時建立 Incident，不自動略過。
9. 跨 Tenant 無法查詢來源請購或附件。
10. 採購承辦不能核准自己的主管節點。

### 14.2 驗收單

1. 一次全數合格驗收。
2. 分兩批到貨及驗收，累計數量正確。
3. 兩張驗收單並行送出時不得超過採購量。
4. 部分合格：合格與不合格數量、處置及剩餘量正確。
5. 全數不合格：退貨／換貨後保留原快照並可重驗。
6. 條件式驗收：改善期限與保留款必填且增加主管／財務確認。
7. 設備案正確進入技術、試車及資產建檔。
8. 原物料正確進入品質檢驗及倉儲確認。
9. 工程案正確進入技術、工安及完工驗收。
10. 服務案依里程碑及成果文件驗收，不要求實體收貨欄位。
11. 末次驗收仍有短交數量時，不得直接完成或必須走短交例外核准。
12. 不合格或條件式驗收通知財務時，付款／保留款條件正確。

### 14.3 版本與稽核

- 已發布表單、流程及 Data Action 不可直接修改。
- 每個 User Task 都綁定一個已發布 Form Version。
- 每次送出、核准、退回、駁回、重驗及更正都有 Action、Snapshot、Actor 與時間。
- 附件只能由有權限的流程參與者下載。
- 單據編號在併發、退回及重送情況下不重號也不換號。

## 17. 2026-08-29 可執行性盤查修正

本節是建置約束，若與前述概念圖文字不一致，以本節為準：

1. 採購及驗收的條件式多路審查均使用 Inclusive Split／Join；Parallel Gateway 只用於無條件
   全部啟動的固定路徑。
2. 採購表單另補 `erpPurchaseOrderNo`、`actualOrderDate`、`confirmedDeliveryDate`、
   `orderConfirmationRemark`、`orderConfirmationAttachments`，供 `orderConfirmation` 使用。
3. 驗收表單另補 `purchaseCategory`、`itemNature`、`requiresQualityAcceptance`、
   `requiresTechnicalAcceptance`、`requiresEhsAcceptance`、`requiresAssetRegistration`、
   `requiresWarehouseConfirmation`、`requiresFinanceReview`、`hasPaymentRisk`、
   `shortCloseRequested`、`shortCloseApproved` 等唯讀路由欄位。
4. 服務及工程驗收另補服務期間、里程碑、成果文件、完工日、完成比例、重驗日、改善措施及
   改善證據附件欄位，不得只以顯示條件描述而沒有 Component Key。
5. `PARTIAL_PASS` 同時具有合格與不合格數量時，合格部分可續行核准，但不合格部分仍須完成
   `nonconformanceDisposition`；不得把 `PARTIAL_PASS` 視為沒有不合格處置的 PASS。
6. 「等待重交／重驗」以明確 User Task（例如 `redeliveryRegistration`）實作；目前受控 BPMN
   元件不使用 Receive Task、任意 Message Event 或 Script Task。
7. 末次驗收仍有餘量時增加 `shortCloseApproval` 例外核准，不得只有
   `shortCloseReason` 欄位就直接結束。
8. `financeNotification` 若需要財務輸入或核准，正式 Task Key 改為
   `financePaymentReview`；若只是通知，則不得建立會阻塞流程的 User Task。
9. 只要流程任何 Task 開放 RETURN，指定的補件節點必須配置
   `assignmentMode = APPLICANT_CORRECTION`，並逐節點設定允許的 Return Target，否則發布檢查
   會失敗。採購通常以 `purchasePreparation` 為補件節點；驗收須依退回內容明確選擇
   `receiptRegistration` 或 `requesterAcceptance`，不可同時存在兩個未定義的通用補件目標。
10. 通用 Runtime 的表單完成狀態是 `COMPLETED`。`ORDERED`、`PARTIALLY_RECEIVED`、
    `FULLY_ACCEPTED`、`CLOSED`、`CANCELLED` 屬業務狀態，應另存唯讀 `purchaseStatus` 並由受控
    交易轉換，不得假設流程完成會自動寫入 `ORDERED`。
11. 採購起單與 `purchasePreparation` 的責任邊界必須二選一：若採購承辦已在起單畫面完成建單，
    Start 後直接進審查；若起單人只提交來源需求，才保留採購承辦建單 Task，避免重複建單。
12. 以上項目修正、發布並完成併發、多帳號、跨 Tenant E2E 前，兩張表單仍維持「設計規劃」，
    不得標示為已完成。
