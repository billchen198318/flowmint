# FlowMint 動態資料服務規格

日期：2026-08-03  
狀態：規劃中  
適用範圍：Form.io 表單、FlowMint 內部簽核整合、外部業務資料庫

## 1. 目標

建立 FlowMint 共用的低程式碼資料層，讓表單設計者可以配置 DataSource Pool、SQL Action、JSON Request 參數、查詢回傳、多步驟資料異動與交易，不需要為每張表單另外開發專用 Controller。

主要能力：

- 管理一個或多個資料庫連線池。
- 使用代碼註冊可被表單呼叫的 Data Action。
- 一個 Data Action 可依順序執行多個 SQL Step。
- 公用 API 接收 JSON Body，並將內容轉為 SQL Named Parameter。
- 支援單筆查詢、清單查詢、新增、修改、刪除與批次處理。
- 支援同一 DataSource 內的多步驟 Transaction。
- 將各 Step 結果組合成一致的 JSON Response。
- Form.io 可透過 JavaScript `fetch()` 或 FlowMint 專用綁定介面呼叫。

## 2. 整體架構

```text
Form.io 表單
    ↓ POST JSON Body
FlowMint Data Action API
    ↓
Data Action 定義
    ↓
DataSource Pool Registry
    ↓
依序執行 SQL Step
    ↓
Transaction／Batch／Result Assembly
    ↓
統一 JSON Response
```

DataSource、SQL 與交易執行屬於共用基礎功能，不全部放入 `FM_PROG005D0001`。表單設計程式只負責選擇 Data Action、配置觸發事件及 Request／Response Mapping。

## 3. 程式切分

| 程式代碼 | 名稱 | 主要職責 |
|---|---|---|
| `FM_PROG005D0001` | 表單設計與版本 | Form.io 設計、事件、Data Action 綁定、Request／Response Mapping |
| `FM_PROG006D0001` | DataSource Pool 管理 | 資料庫連線、Pool 參數、連線測試與啟停 |
| `FM_PROG006D0002` | Data Action 設計 | Action 主檔、SQL Step、參數、Preview、發布與版本 |

後端核心元件建議：

```text
FmDataSourcePoolRegistry
FmDataActionExecutor
FmDataActionTransactionService
FmDataActionParameterResolver
FmDataActionResultAssembler
FmDataActionAuditService
```

## 4. DataSource Pool

### 4.1 資料表

建議建立 `fm_data_source_pool`：

```text
OID
TENANT_ID
POOL_ID
POOL_CODE
POOL_NAME
DB_TYPE
DRIVER_CLASS
JDBC_URL
USERNAME
PASSWORD_CONTENT
POOL_CONFIG
STATUS
LOCK_VERSION
CUSERID
CDATE
UUSERID
UDATE
```

規則：

- `POOL_CODE` 在 Tenant 內唯一，建立後不可修改。
- `PASSWORD_CONTENT` 使用既有加密機制保存，不回傳前端明文。
- `POOL_CONFIG` 保存 HikariCP 可配置項目，例如最大連線數、Timeout 與 Lifetime。
- 第一版支援 MariaDB；後續可擴充 MySQL、PostgreSQL、SQL Server 與 Oracle。
- Connection Pool 由 Registry 依啟用設定建立並快取；設定更新後安全重建。
- 管理頁提供 Connection Test，但不得輸出密碼與完整連線錯誤堆疊。

### 4.2 第一版限制

- 一個 Data Action 的所有交易 Step 必須使用同一個 Pool。
- 跨 Pool Transaction 不納入第一版。
- 跨 Pool 原子性若有需求，另行採用 XA 或補償交易，不以一般 Spring Transaction 假裝保證。

## 5. Data Action

### 5.1 主檔

建議建立 `fm_data_action`：

```text
OID
TENANT_ID
ACTION_ID
ACTION_CODE
ACTION_NAME
POOL_ID
ACTION_TYPE
REQUEST_SCHEMA
RESPONSE_MODE
STATUS
CURRENT_VERSION_NO
DESCRIPTION
LOCK_VERSION
AUDIT 欄位
```

`ACTION_TYPE`：

- `QUERY`：只允許查詢 Step。
- `COMMAND`：執行單一或多個異動 Step。
- `TRANSACTION`：所有 Step 在同一交易內執行，任一步失敗即 Rollback。

### 5.2 版本

SQL Action 應採草稿／發布版本，避免已發布表單因 Action 被直接修改而改變行為。建議建立 `fm_data_action_version`，保存版本狀態、內容 SHA-256、發布人與發布時間。

流程或表單正式發布時，應保存引用的 `ACTION_ID + VERSION_NO`；不可只保存可能移動的 Current Version。

## 6. SQL Step

建議建立 `fm_data_action_step`：

```text
OID
TENANT_ID
ACTION_ID
VERSION_NO
STEP_ID
STEP_CODE
STEP_NAME
EXECUTION_ORDER
STATEMENT_TYPE
EXECUTION_MODE
SQL_CONTENT
ARRAY_PATH
RESULT_KEY
RESULT_MODE
EXPECT_AFFECTED_ROWS
CONTINUE_CONDITION
STATUS
AUDIT 欄位
```

`STATEMENT_TYPE`：

- `SELECT_ONE`
- `SELECT_LIST`
- `INSERT`
- `UPDATE`
- `DELETE`

`EXECUTION_MODE`：

- `ONCE`：執行一次。
- `FOR_EACH`：針對 JSON Array 逐筆或 Batch 執行。

SQL 使用 Named Parameter：

```sql
SELECT EMPLOYEE_ID,
       EMPLOYEE_NO,
       DISPLAY_NAME,
       EMAIL
  FROM fm_employee
 WHERE TENANT_ID = :tenantId
   AND ACCOUNT = :account
```

後端使用 Spring `NamedParameterJdbcTemplate`，JSON Value 只作為 Parameter Value，不使用字串串接代入 SQL。

## 7. Request Parameter

### 7.1 公用 API

```http
POST /api/fm/data-actions/{actionCode}/execute
Content-Type: application/json
```

範例：

```http
POST /api/fm/data-actions/EMPLOYEE_PROFILE/execute
```

Request Body：

```json
{
  "account": "user01"
}
```

執行參數由三個來源合併：

1. Server Context：`tenantId`、登入帳號、時區、Business Key、Process Instance ID。
2. Request Body：Form.io 傳入的 JSON。
3. Step Context：前面 Step 的查詢結果、Affected Rows 與 Generated Key。

Server Context 優先於同名 Request 欄位，前端不可覆蓋 Tenant 與登入帳號。

### 7.2 參數 Mapping

第一版支援 JSON Path Mapping：

```json
{
  "account": "$.account",
  "businessKey": "$.businessKey",
  "amount": "$.formData.amount"
}
```

保留參數：

```text
:tenantId
:loginAccount
:businessKey
:processInstanceId
:now
```

List Parameter 可直接用於：

```sql
WHERE EMPLOYEE_ID IN (:employeeIds)
```

欄位名稱、資料表名稱與 SQL Keyword 不可使用 JDBC Parameter 動態替換；如需不同結構，應拆為不同 Step 或不同 Action Version。

## 8. Result Assembly

每一個 Step 設定唯一 `RESULT_KEY`，公用 API 將結果組合到 `data`：

```json
{
  "success": "Y",
  "message": "執行成功",
  "data": {
    "employee": {
      "employeeId": "EMP001",
      "employeeNo": "A0001",
      "displayName": "王小明"
    },
    "assignments": [
      {
        "orgUnitId": "D001",
        "orgUnitName": "資訊部"
      }
    ],
    "updateResult": {
      "affectedRows": 1
    }
  }
}
```

`RESULT_MODE`：

- `OBJECT`：單筆資料，不存在時回傳 `null`。
- `LIST`：資料陣列，不存在時回傳空陣列。
- `AFFECTED_ROWS`：回傳異動筆數。
- `GENERATED_KEY`：回傳新增鍵值。
- `NONE`：執行但不放入 Response。

欄位名稱預設由資料庫欄位轉為 lower camel case；Step 可另外配置 Response Alias。

## 9. 多筆異動與交易

### 9.1 多 SQL Step

範例：建立申請表頭與明細。

| 順序 | Step Code | Statement | Result Key |
|---:|---|---|---|
| 10 | `CREATE_HEADER` | `INSERT` | `header` |
| 20 | `CREATE_ITEMS` | `INSERT FOR_EACH` | `items` |
| 30 | `UPDATE_EXTERNAL_NO` | `UPDATE` | `externalUpdate` |
| 40 | `LOAD_RESULT` | `SELECT_ONE` | `application` |

Action Type 設為 `TRANSACTION`。任何 Step 發生錯誤、Affected Rows 不符或必要結果不存在時，整組 Rollback。

### 9.2 FOR_EACH／Batch

Request：

```json
{
  "businessKey": "REQ-001",
  "items": [
    {
      "itemCode": "A01",
      "quantity": 2
    },
    {
      "itemCode": "A02",
      "quantity": 5
    }
  ]
}
```

Step 設定：

```text
EXECUTION_MODE = FOR_EACH
ARRAY_PATH = $.items
```

SQL：

```sql
INSERT INTO request_item
    (TENANT_ID,
     BUSINESS_KEY,
     ITEM_CODE,
     QUANTITY)
VALUES
    (:tenantId,
     :businessKey,
     :itemCode,
     :quantity)
```

後端應轉成 JDBC Batch，並保留每筆索引與錯誤位置。

### 9.3 Step 結果引用

後續 Step 可以引用前面結果：

```text
${steps.header.generatedKey}
${steps.employee.employeeId}
${steps.validation.rows[0].status}
${item.itemCode}
```

Mapping 範例：

```json
{
  "headerId": "${steps.header.generatedKey}",
  "itemCode": "${item.itemCode}",
  "quantity": "${item.quantity}"
}
```

## 10. Form.io 整合

### 10.1 JavaScript 呼叫

```javascript
fetch("/api/fm/data-actions/EMPLOYEE_PROFILE/execute", {
  method: "POST",
  credentials: "include",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    account: data.employeeAccount,
  }),
})
  .then((response) => response.json())
  .then((response) => {
    data.employeeName = response.data.employee.displayName;
    data.departmentName =
      response.data.assignments[0]?.orgUnitName || "";

    instance.root.setSubmission({ data });
  });
```

### 10.2 視覺化綁定

`FM_PROG005D0001` 後續增加 FlowMint Data Action 設定：

```text
觸發事件：FIELD_CHANGE
監聽欄位：employeeAccount
Data Action：EMPLOYEE_PROFILE

Request Mapping：
  account ← employeeAccount

Response Mapping：
  employeeName ← employee.displayName
  departmentName ← assignments[0].orgUnitName
```

觸發事件：

- `FORM_LOAD`
- `FIELD_CHANGE`
- `BUTTON_CLICK`
- `BEFORE_SUBMIT`
- `AFTER_SUBMIT`
- `SELECT_OPTIONS`

表單設計者可選擇視覺化 Binding，也可直接使用 Form.io JavaScript `fetch()` 呼叫公用 API。

## 11. Preview 與發布

Data Action 草稿頁提供 Preview：

1. 輸入測試 JSON Body。
2. 顯示解析後參數，但遮蔽密碼與敏感欄位。
3. 顯示每個 Step 的 Result、Affected Rows 與耗時。
4. Transaction Preview 預設 Rollback；管理者明確選擇正式執行才 Commit。
5. 發布前解析所有 SQL，檢查 Named Parameter 是否有定義來源。
6. 發布後 SQL 內容鎖定；修改必須建立新版本。

表單發布檢查：

- 引用的 Data Action 必須存在且已發布。
- DataSource Pool 必須啟用。
- Request／Response Mapping 引用的表單欄位必須存在。
- `BEFORE_SUBMIT` Action 失敗時必須阻止表單送出。
- Published Form 保存 Data Action Version，避免 Current Version 變更造成既有流程漂移。

## 12. 執行與稽核

建議建立 `fm_data_action_execution`：

```text
OID
TENANT_ID
EXECUTION_ID
ACTION_ID
ACTION_VERSION_NO
FORM_ID
FORM_VERSION_NO
BUSINESS_KEY
PROCESS_INSTANCE_ID
TRIGGER_EVENT
EXECUTED_BY
START_DATE
END_DATE
EXECUTION_STATUS
TOTAL_ROWS
ERROR_CODE
ERROR_MESSAGE
REQUEST_DIGEST
RESPONSE_DIGEST
```

稽核原則：

- 保存 Action、版本、執行者、表單、流程與 Business Key。
- 預設不保存完整 Request／Response，避免大量資料；保存 Digest 與必要摘要。
- SQL 錯誤回傳 Action Code、Step Code 與可理解訊息，不回傳密碼或完整 JDBC Stack Trace。
- 每個 Step 設定 Timeout、最大回傳列數與 Batch 上限。
- 提供執行中止與 Timeout 狀態，避免前端無限等待。

## 13. 後端分層

Controller 只處理 HTTP 契約：

```text
FmDataActionController
    ↓
IFmDataActionLogicService
    ↓
FmDataActionExecutor
    ├─ FmDataSourcePoolRegistry
    ├─ FmDataActionParameterResolver
    ├─ NamedParameterJdbcTemplate
    ├─ FmDataActionResultAssembler
    └─ FmDataActionAuditService
```

交易邊界放在 Logic／Transaction Service，不放 Controller、Entity Service 或 Mapper。Data Action 動態 SQL 不寫入一般 MyBatis Mapper XML；一般 FlowMint 主檔仍遵守既有 Entity、Mapper、Service 與 Logic 分層。

## 14. API 契約

### 14.1 Execute

```http
POST /api/fm/data-actions/{actionCode}/execute
```

成功：

```json
{
  "success": "Y",
  "message": "執行成功",
  "executionId": "EXE-001",
  "data": {}

```

失敗：

```json
{
  "success": "N",
  "message": "資料更新失敗",
  "executionId": "EXE-001",
  "error": {
    "actionCode": "CREATE_REQUEST",
    "stepCode": "CREATE_ITEMS",
    "itemIndex": 2
  }
}
```

### 14.2 Preview

```http
POST /api/fm/data-actions/{actionId}/versions/{versionNo}/preview
```

Preview 只允許草稿版本，並由管理程式權限控制。

### 14.3 Metadata

```http
POST /api/fm/data-actions/options
POST /api/fm/data-actions/{actionCode}/metadata
```

Metadata 提供 Request 欄位、Response Result Key 與版本資訊，供 FM_PROG005D0001 建立視覺化 Mapping。

## 15. 測試與驗收

最低測試案例：

- JSON Body 正確轉為 Named Parameter。
- Nested JSON Path、List Parameter 與空值處理。
- `SELECT_ONE` 查無資料、單筆與超過一筆。
- `SELECT_LIST` 空清單與最大列數。
- Insert Generated Key 可被後續 Step 引用。
- Update／Delete Affected Rows 符合與不符合預期。
- `FOR_EACH` 成功、指定索引失敗與完整 Rollback。
- 多 Step Transaction 任一步失敗全部 Rollback。
- 同 Tenant Action Code 唯一及跨 Tenant 不可載入。
- Action Version 發布後不可修改。
- Published Form 固定引用 Published Action Version。
- Preview 預設 Rollback。
- Connection Timeout、Query Timeout 與 Batch 上限。
- Form.io `FORM_LOAD`、`FIELD_CHANGE`、`BUTTON_CLICK`、`BEFORE_SUBMIT` Mapping。
- Request／Response Mapping 引用不存在欄位時阻擋發布。

## 16. 分階段交付

### Phase 1：執行核心

- MariaDB DataSource Pool。
- Data Action／Version／SQL Step 資料模型。
- `SELECT_ONE`、`SELECT_LIST`、`INSERT`、`UPDATE`、`DELETE`。
- Named Parameter 與統一 Response。
- 單一 Pool Transaction。
- Preview API。

### Phase 2：批次與結果引用

- `FOR_EACH`／JDBC Batch。
- Generated Key。
- Step Result Context。
- Affected Rows 條件。
- Execution Audit。

### Phase 3：Form.io 整合

- FM_PROG005D0001 Data Action Metadata 選擇。
- 觸發事件。
- Request／Response 視覺化 Mapping。
- Published Form 固定 Action Version。
- 正式 Form Renderer 執行 Binding。

### Phase 4：進階能力

- 多 DB Type。
- 條件式 Step。
- 分頁查詢與 Streaming。
- 補償交易。
- 共用 Action Template 與匯入／匯出。

## 17. 規格衝突與必要修訂

現有 [流程與表單規格](04-流程與表單規格.md) 禁止直接 SQL 與任意 HTTP。本規格若核准，必須同步修改該文件，區分：

- BPMN Script Task／直接 SQL：仍不作為流程節點執行方式。
- 已發布 Data Action：允許由 Form.io 或 FlowMint Runtime 透過公用 API 執行。
- Form.io 自訂 JavaScript：依內部客製化需求開放，但正式行為必須隨 Form Version 保存。

在規格衝突尚未修訂前，本文件為規劃案，不代表既有禁止規則已自動失效。

## 18. 第一版結論

第一版採用「DataSource Pool + Versioned Data Action + Ordered SQL Step + Public Execute API」。同一 Action 支援查詢、異動、批次、多 Step 與單一 Pool Transaction；Form.io 可直接以 JavaScript 呼叫，也可使用後續新增的視覺化 Binding。

不在第一版承諾跨 Pool 原子交易。所有正式表單引用已發布 Action Version，確保流程執行期間 SQL 行為可追蹤且不會因主檔 Current Version 更新而漂移。
