# 31 公司名片申請單表單流程配置規劃

日期：2026-08-28  
狀態：設計規劃  
實作方式：FlowMint 表單設計、流程設計、Task Policy、Assignment Resolver 與 Data Action 配置

## 1. 目的與範圍

本文件規劃「公司名片申請單」如何使用 FlowMint 既有低程式碼能力建置，不新增名片專用
Java Controller、Service、Mapper 或 Vue 頁面。

流程負責確認申請資格、名片內容、主管同意、品牌格式及印製授權。印刷廠下單、採購、
收貨與付款屬外部採購履約範圍；流程完成只代表行政／總務可以依核准內容辦理印製。

## 2. 代碼與申請類型

| 類型 | 代碼 | 名稱 |
| --- | --- | --- |
| Form | `FM_BUSINESS_CARD_REQUEST` | 公司名片申請單 |
| Process | `FM_BUSINESS_CARD_APPROVAL` | 公司名片申請流程 |
| Document Type | `BUSINESS_CARD_REQUEST` | 名片申請單號 |
| Process Category | `ADMIN` | 行政申請 |

申請類型固定為：

| 代碼 | 顯示名稱 | 審查原則 |
| --- | --- | --- |
| `NEW` | 首次申請 | 完整資格、資料及版面審查 |
| `CHANGE` | 資料變更重印 | 必須說明異動欄位，重新審查名片內容 |
| `REPRINT` | 原樣補印 | 必須引用最近核准版本；內容有變更時不得使用 |
| `DAMAGE_LOSS` | 損毀／遺失補印 | 引用最近核准版本並填寫原因 |

## 3. 表單設計

表單使用 Panel 或 Tabs 分為「申請資訊」、「名片內容」、「印製需求」、「校稿與附件」四區。

### 3.1 申請資訊

| Label | Component Key | 元件 | 必填 | 規則 |
| --- | --- | --- | --- | --- |
| 申請單號 | `documentNumber` | 共用系統欄位 | 系統 | Runtime 產生、唯讀 |
| 申請類型 | `requestType` | Select | 是 | 只接受受控代碼 |
| 申請人帳號 | `applicantAccount` | 申請人情境欄位 | 系統 | Server Context 注入，不接受自由輸入 |
| 申請人姓名 | `applicantName` | Text Field | 系統 | 唯讀顯示 |
| 所屬部門代碼 | `departmentId` | Hidden | 系統 | 由有效 Primary Org Assignment 取得 |
| 所屬部門 | `departmentName` | Text Field | 系統 | 唯讀顯示 |
| 申請日期 | `requestDate` | Date | 是 | 預設當日，格式 `yyyy-MM-dd` |
| 期望領取日 | `requiredDate` | Date | 是 | 不得早於申請日；交期不足時提示 |
| 申請原因 | `requestReason` | Text Area | 條件 | `CHANGE`、`DAMAGE_LOSS` 必填 |
| 原核准申請單 | `sourceRequestBusinessKey` | Select | 條件 | `REPRINT`、`DAMAGE_LOSS` 必填 |

原核准申請單以 Data Action 查詢目前申請人在同 Tenant 最近完成的名片申請，只回傳必要欄位；
不得由前端直接帶入其他員工或其他 Tenant 的資料。

### 3.2 名片內容

| Label | Component Key | 元件 | 必填／規則 |
| --- | --- | --- | --- |
| 中文姓名 | `nameZh` | Text Field | 必填；預設員工姓名 |
| 英文姓名 | `nameEn` | Text Field | 依公司政策必填；限制英文字母、空白、連字號及句點 |
| 中文部門 | `departmentNameZh` | Text Field | 系統預填；修改需行政確認 |
| 英文部門 | `departmentNameEn` | Text Field | 必填；由組織主檔或受控對照帶入 |
| 中文職稱 | `titleZh` | Text Field | 必填；應由有效職稱／職務帶入 |
| 英文職稱 | `titleEn` | Text Field | 必填；由受控職稱翻譯對照帶入 |
| 公司名稱 | `companyNameZh` | Text Field | 系統預填、唯讀 |
| 英文公司名稱 | `companyNameEn` | Text Field | 系統預填、唯讀 |
| 公司地址 | `officeAddressZh` | Text Area | 由辦公地點對照帶入、唯讀 |
| 英文地址 | `officeAddressEn` | Text Area | 由受控對照帶入、唯讀 |
| 公司電話 | `companyPhone` | Text Field | 系統預填 |
| 分機 | `extension` | Text Field | 選填；僅數字及公司允許格式 |
| 行動電話 | `mobilePhone` | Text Field | 依政策選填；顯示告知同意 |
| 公司 Email | `email` | Email | 必填；預設公司帳號，不接受私人信箱 |
| 公司網站 | `website` | URL/Text | 系統預填、唯讀 |

公司名稱、地址、電話與網站不建立 FlowMint 核心法人／據點主檔。第一版由已發布 Data Action
讀取公司既有受控資料來源；無外部來源時，以 Tenant 級配置資料提供，不能寫死於 Vue。

申請人不得自行輸入不存在的組織職稱。若需要對外職稱與內部職稱不同，新增
`externalTitleReason` 並必填理由，交由部門主管及行政／品牌審查。

### 3.3 印製需求

| Label | Component Key | 元件 | 必填／規則 |
| --- | --- | --- | --- |
| 版型代碼 | `templateCode` | Select | 必填；只列有效公司版型 |
| 語言版本 | `languageMode` | Select | `ZH`、`ZH_EN`、`EN`，依公司政策限制 |
| 印製數量 | `printQuantity` | Select | 只允許公司核准批量，例如 100／200／300 張 |
| 紙材／特殊規格 | `materialOption` | Select | 預設標準；特殊選項需填原因並提高審查 |
| QR Code 類型 | `qrCodeType` | Select | `NONE`、公司網站、公司聯絡頁；不得任意 URL |
| 配送／領取方式 | `deliveryMethod` | Select | `PICKUP`、`INTERNAL_DELIVERY` |
| 領取地點 | `pickupLocation` | Select | 必填；由受控地點清單取得 |
| 特殊需求 | `specialRequirement` | Text Area | 選填；不得作為繞過標準版型的指示 |

第一版不讓使用者上傳自製名片版型或 Logo。品牌資產由有效版型決定，避免未授權商標、
色碼或版面流入正式印刷。

### 3.4 校稿與附件

| Label | Component Key | 規則 |
| --- | --- | --- |
| 申請人校稿確認 | `applicantProofConfirmed` | 首次送出必須為 `Y` |
| 個資揭露確認 | `personalDataConsent` | 填寫行動電話等非必要資料時必須為 `Y` |
| 異動欄位摘要 | `changeSummary` | `CHANGE` 必填 |
| 佐證附件 | `supportingAttachments` | 特殊職稱、特殊版型或例外申請時必填 |
| 行政校稿檔 | `proofAttachments` | 行政校稿節點上傳；只接受 PDF／圖片及容量限制 |
| 最終校稿確認 | `finalProofConfirmed` | 有行政校稿檔時由申請人確認 |

附件沿用 FlowMint Attachment component，只保存附件 ID；不得把 Base64、實體路徑或任意
外部下載 URL 放入 submission。

## 4. Data Action 配置

本案不新增專用 API，建議在 `FM_PROG006D0002` 建立以下版本化 Data Action：

| Action Code | 觸發點 | 用途 |
| --- | --- | --- |
| `BUSINESS_CARD_PROFILE_LOAD` | `FORM_LOAD` | 載入員工、主要部門、職稱、公司 Email 與聯絡資料 |
| `BUSINESS_CARD_COMPANY_PROFILE` | `FORM_LOAD` | 載入公司中英文名稱、地址、電話、網站與允許領取點 |
| `BUSINESS_CARD_TEMPLATE_LIST` | `FORM_LOAD` | 列出目前有效版型、語言與印量限制 |
| `BUSINESS_CARD_APPROVED_HISTORY` | `FIELD_CHANGE` | 查詢申請人最近核准且可補印的名片版本 |
| `BUSINESS_CARD_SOURCE_LOAD` | `FIELD_CHANGE` | 選取原申請後回填不可變的核准內容 |
| `BUSINESS_CARD_SUBMIT_VALIDATE` | `BEFORE_SUBMIT` | 重驗任職、membership、職稱、Email、版型、數量及來源版本 |

所有 Action 固定 Tenant 範圍並使用參數化 SQL。前端傳入的姓名、帳號、部門、職稱與公司資料
都不是授權依據；送出時必須重新由後端資料來源驗證。

## 5. BPMN 流程

### 5.1 主流程

```text
Start
  ↓
requestValidationGateway
  ├─ 無有效任職／資料不完整 → applicantCorrection
  └─ 通過 → departmentManagerApproval
                   ↓
             requestTypeGateway
              ├─ 原樣補印且無例外 ─────────────┐
              └─ 新申請／變更／特殊需求 → adminBrandReview
                                                  ↓
                                         proofRequiredGateway
                                          ├─ 需校稿 → applicantProofConfirmation
                                          └─ 不需校稿 ─────────┐
                                                               ↓
                                                    printAuthorization
                                                               ↓
                                                              End
```

`applicantCorrection` 重送後回到 `requestValidationGateway`，重新判斷完整路徑。任何預設或無法
分類的 Gateway flow 都進入補件或 Incident，不得自動核准。

### 5.2 User Task 與 Resolver

| Task Key | 名稱 | Resolver | 派送模式 |
| --- | --- | --- | --- |
| `applicantCorrection` | 申請人補件 | 流程申請人本人 | `ASSIGNEE` |
| `departmentManagerApproval` | 部門主管審核 | `INITIATOR_ORG_HEAD` 或 `DIRECT_MANAGER` | `ASSIGNEE` |
| `adminBrandReview` | 行政／品牌審查 | `APPROVAL_GROUP: BUSINESS_CARD_ADMIN` | `CANDIDATE` |
| `applicantProofConfirmation` | 申請人確認校稿 | 流程申請人本人 | `ASSIGNEE` |
| `printAuthorization` | 印製授權 | `APPROVAL_GROUP: BUSINESS_CARD_PRINT` | `CANDIDATE` |

若行政審查與印製授權由同一單位負責，可由同一群組處理，但仍保留兩個 Task 及快照：前者確認
內容與版型，後者確認最終校稿與印量。找不到有效簽核人時建立 Assignment Incident，不跳過。

### 5.3 路由規則

- `NEW`、`CHANGE`：主管核准後必經行政／品牌審查。
- `REPRINT`、`DAMAGE_LOSS`：只有來源為已完成、本人、內容完全相同且標準版型仍有效時，
  才可略過內容審查；有任何差異即轉為 `CHANGE` 路徑。
- 非標準版型、非標準印量、外部職稱、個人手機或特殊 QR Code 必經行政／品牌審查。
- 申請人已離職、停用、無有效 Tenant membership 或無主要組織時禁止送出。
- 申請人與主管為同一人時，依 Task Policy `SELF_APPROVAL_POLICY` 尋找下一級主管，不得自簽。

## 6. Task Policy 與欄位權限

| 節點 | 可編輯欄位 | 允許動作 |
| --- | --- | --- |
| 起單／`applicantCorrection` | 申請類型、允許的名片內容、印製需求、附件 | 送出／補件重送、撤回 |
| `departmentManagerApproval` | 主管意見 | 核准、退回、駁回；不得改名片內容 |
| `adminBrandReview` | 受控公司資料、標準譯名、版型、行政意見、校稿附件 | 核准、退回、駁回 |
| `applicantProofConfirmation` | 最終校稿確認、校稿意見 | 確認或退回行政修正 |
| `printAuthorization` | 授權批量、承辦註記 | 核准、退回、駁回 |

退回與駁回原因必填。主管不得替申請人改姓名、電話或 Email；行政修改受控公司資訊後必須留下
新 Form Revision，若影響校稿內容則重新取得申請人確認。

## 7. 通知、SLA 與完成結果

- 送達主管、行政審查、校稿確認及印製授權時發送站內通知；Email 依 Tenant 通知設定。
- 建議 SLA：主管 2 個工作日、行政／品牌 2 個工作日、申請人校稿 2 個工作日、印製授權 1 個工作日。
- 逾期只提醒目前待辦人及營運角色，不自動核准。
- 流程完成通知申請人與行政／印製群組，內容包含申請單號、核准版面資料、印量與領取方式。
- 如需把核准資料交給印刷供應商，應由受控整合或人工匯出處理；不得在通知中夾帶 API Key、
  未遮罩個資或無權限附件 URL。

## 8. 單據編號與版本

建議單號格式：`BC-{TENANT}-{YYYY}{MM}-{SEQ}`，Document Type 為
`BUSINESS_CARD_REQUEST`，按月重設、流水號六碼。正式格式須由公司確認。

重送、退回及冪等重試不得換號；撤回、駁回或取消後不回收單號。補印建立新的申請單及單號，
並以 `sourceRequestBusinessKey` 保留與原核准版本的關聯，不覆寫歷史資料。

已發布 Form、Process、Data Action 不直接修改；欄位、版型或流程調整一律建立新版本。

## 9. 最低驗收案例

1. 新進員工首次申請：載入正確部門、職稱與公司 Email，主管及行政完成核准。
2. 原樣補印：引用本人最近核准版本，內容完全相同，走精簡路徑並產生新單號。
3. 資料變更：職稱或分機改變，禁止偽裝成補印，重新執行內容審查與校稿。
4. 特殊申請：外部職稱、非標準印量或特殊版型，必經行政／品牌審查。
5. 補件：行政退回修正英文職稱，重送後保留歷史快照並重新校稿。
6. 自簽：申請人就是部門主管時，依政策解析下一級主管。
7. 無簽核人：主管或行政群組無有效成員時建立 Incident，不自動通過。
8. 權限：其他員工不能讀取申請內容、附件或校稿檔；營運人員依權限查閱。
9. 跨 Tenant：無法載入其他 Tenant 的員工、原申請、版型或附件。
10. 冪等與併發：重複送出只建立一個流程與單號；同一 Task 重複核准不重複寫 Action。
11. 生命週期：離職或 membership 失效者不能送出；審核中失效時由 Incident 處理。
12. 通知：每個待辦、退回、駁回、完成與逾期事件只產生預期通知。

## 10. 上線前必須確認的公司政策

- 哪些員工、職務或聘僱類型可以申請名片。
- 中英文公司名稱、地址、部門及職稱的正式對照來源與維護責任。
- 是否允許個人手機、外部職稱、QR Code，以及個資告知文字。
- 標準版型、Logo、色彩、紙材、語言版本與每批允許印量。
- 行政／品牌審查與印製承辦群組成員。
- 補印可略過內容審查的有效期限及最高累計數量。
- 正常製作天數、急件條件、領取地點及通知方式。
- 印刷廠下單、費用歸屬、採購與收貨的外部作業責任。
- 申請、校稿檔與個人聯絡資料的保存期限。

## 11. 建置與完成定義

建議順序：

1. 確認公司政策、翻譯對照、版型與簽核群組。
2. 建立並發布所需 Data Action。
3. 以 `FM_PROG005D0001` 建立表單、欄位規則、附件及試跑資料後發布。
4. 建立單據編號規則與流程分類。
5. 以 `FM_PROG004D0001` 建立 BPMN、Form Binding、Task Policy、Resolver、Gateway default
   flow、退回目標與 SLA，執行發布檢查及 Resolver Preview 後發布。
6. 以申請人、主管、行政、印製承辦及營運角色完成多帳號瀏覽器／MariaDB／Flowable E2E。

只有表單、Data Action、流程與編號均已發布，且上述正常、補印、異動、補件、自簽、Incident、
附件、通知、冪等及跨 Tenant 案例全部通過，才能標示「公司名片申請單已完成」。本文件完成
僅代表設計規劃完成，不代表功能已建立或上線。
