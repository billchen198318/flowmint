# 02 系統架構

## 1. 邏輯模組

```text
Identity Adapter
  └─ QIFU4 Account / Tenant Context

Organization
  ├─ Employee
  ├─ Approval Level
  ├─ Department Tree
  ├─ Department Head
  └─ Approval Group / Delegation

Design Time
  ├─ Form Designer
  ├─ BPMN Designer
  ├─ Task Policy
  └─ Assignment Rule + Preview

Runtime
  ├─ Request Service
  ├─ Assignment Resolver
  ├─ Task Service
  ├─ Flowable Adapter
  ├─ Snapshot / Audit
  └─ Incident / Notification
```

## 2. 分層

### Controller

- 驗證 HTTP 輸入格式與權限。
- 從登入狀態取得 Account 與 Tenant。
- 呼叫 Logic Service。
- 不直接使用 Mapper，不組織交易。

### Logic Service

- 一個使用案例一個公開方法。
- 管理 Transaction。
- 執行跨表驗證、版本控制與狀態轉換。
- 回傳統一 `DefaultResult<T>`。

### Domain Service

- 放置可重用的部門樹、Resolver、表單快照及狀態機規則。
- 不依賴 HTTP。
- Preview 與 Runtime 必須共用 Resolver Domain Service。

### Entity Service / Mapper

- 單表 CRUD 與明確查詢。
- Mapper SQL 必須帶 `TENANT_ID`。
- 不在 Mapper XML 藏業務狀態機。

### Flowable Adapter

- 封裝 deploy、start、task claim/complete、change state 與 history。
- 業務程式不得直接更新 `ACT_*`。
- Flowable ID 必須回寫 FlowMint 業務索引與稽核表。

## 3. 交易邊界

下列操作必須單一交易：

- 建立／版本化部門。
- 移動整個部門子樹。
- 設定主管並關閉重疊期間。
- 發布表單版本。
- 發布流程版本與所有 Task Policy／Assignment Rule。
- 發起申請：鎖表單、建立流程、寫 instance、snapshot、action。
- 完成任務：驗證 actor、保存 snapshot、完成 Flowable task、寫 action。
- 管理員重新解析及改派。

Flowable 操作與業務表若不能共用本地交易，必須採失敗補償與 Incident，不得只成功一半。

## 4. 租戶隔離

- Tenant 由 server-side session/context 決定。
- API body 中的 `tenantId` 只可用於系統管理，不可信任一般使用者輸入。
- 每個唯一鍵、查詢、更新及刪除條件都包含 Tenant。
- Cache key 必須包含 Tenant。
- Flowable process definition tenant ID 與 FlowMint Tenant 一致。

## 5. 版本

- 部門：穩定 `ORG_UNIT_ID` + append-only version。
- 表單：穩定 `FORM_ID` + immutable published version。
- 流程：穩定 `PROCESS_DEF_ID` + immutable published version。
- 已發布版本不得原地修改。
- Runtime instance 固定引用啟動時的流程與表單版本。

## 6. 時間

- DB 使用 `datetime(3)`，應用程式以 `Instant`／UTC 處理。
- UI 依 Tenant timezone 顯示。
- 生效期間採 `[EFFECTIVE_FROM, EFFECTIVE_TO)`；`EFFECTIVE_TO` 為 NULL 表示無期限。
- 同一角色或主要部門的有效期間不得重疊。
