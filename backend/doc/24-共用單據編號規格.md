# 24 共用單據編號規格

## 1. 目的與狀態

本規格定義 FlowMint 共用的正式單據編號能力，供請購、請假、費用、合約及後續表單共用。編號不得綁定單一表單、流程或中文名稱。

本機 `flowmint` MariaDB 與 `flowmint.sql` 已建立兩張資料表，Entity、Mapper、Service、流程綁定與 Runtime 取號亦已實作。`A01／FM_PURCHASE_APPROVAL` 已綁定 `PURCHASE_REQUEST` 規則；請購流程與表單目前仍為 `DRAFT`，完成發布及真實送單 E2E 前不得宣稱正式單據編號已上線。

## 2. 核心原則

- 正式單號由後端產生，前端只能顯示，不得輸入或修改。
- Tenant、單據類型與計號週期各自獨立計號。
- 不使用 `SELECT MAX(...) + 1`，避免併發送單取得相同號碼。
- 單號首次產生後不可因退回、補件、重送或 Form Revision 改變。
- `BUSINESS_KEY` 是流程與表單共用的正式業務單號。
- `fm_form_data` 與 `fm_process_instance` 繼續保留 `UNIQUE (TENANT_ID, BUSINESS_KEY)`。
- 年月切換依 Tenant 時區計算，不使用伺服器預設時區。
- 穩定代碼使用 `DOCUMENT_TYPE`，不得使用表單名稱或流程名稱。

## 3. 資料模型

完整能力使用兩張表：

| 資料表 | 用途 |
|---|---|
| `fm_document_number_rule` | 定義單據類型、格式、週期與啟用狀態 |
| `fm_document_sequence` | 保存各 Tenant、單據類型及週期目前流水號 |

### 3.1 `fm_document_number_rule`

| 欄位 | 型別建議 | 必填 | 說明 |
|---|---|---:|---|
| `OID` | `char(36)` | 是 | 技術主鍵 |
| `TENANT_ID` | `varchar(64)` | 是 | Tenant 邊界 |
| `DOCUMENT_TYPE` | `varchar(50)` | 是 | 穩定單據類型，例如 `PURCHASE_REQUEST` |
| `PREFIX` | `varchar(20)` | 是 | 單號前綴，例如 `PR` |
| `PERIOD_TYPE` | `varchar(10)` | 是 | `NONE`、`YEAR` 或 `MONTH` |
| `SEQUENCE_LENGTH` | `smallint` | 是 | 流水號補零長度，建議 4 至 12 |
| `FORMAT_PATTERN` | `varchar(200)` | 是 | 受控格式範本 |
| `STATUS` | `varchar(16)` | 是 | `ACTIVE` 或 `INACTIVE` |
| `CUSERID` / `CDATE` | 共通 Audit | 是 | 建立資訊 |
| `UUSERID` / `UDATE` | 共通 Audit | 否 | 最後異動資訊 |

唯一鍵：

```sql
UNIQUE KEY UK_FM_DOC_NO_RULE (
    TENANT_ID,
    DOCUMENT_TYPE
)
```

第一版 `FORMAT_PATTERN` 只允許下列 token，不允許執行任意 expression：

| Token | 說明 |
|---|---|
| `{PREFIX}` | 規則前綴 |
| `{TENANT}` | Tenant 代碼 |
| `{YYYY}` | Tenant 當地年份 |
| `{MM}` | Tenant 當地月份 |
| `{SEQ}` | 依 `SEQUENCE_LENGTH` 左補零的流水號 |

請購單建議規則：

```text
DOCUMENT_TYPE  = PURCHASE_REQUEST
PREFIX         = PR
PERIOD_TYPE    = MONTH
SEQUENCE_LENGTH = 6
FORMAT_PATTERN = {PREFIX}-{TENANT}-{YYYY}{MM}-{SEQ}
```

範例：`PR-A01-202608-000001`。

### 3.2 `fm_document_sequence`

| 欄位 | 型別建議 | 必填 | 說明 |
|---|---|---:|---|
| `OID` | `char(36)` | 是 | 技術主鍵 |
| `TENANT_ID` | `varchar(64)` | 是 | Tenant 邊界 |
| `DOCUMENT_TYPE` | `varchar(50)` | 是 | 對應編號規則的穩定類型 |
| `PERIOD_KEY` | `varchar(12)` | 是 | `NONE`、`yyyy` 或 `yyyyMM` |
| `CURRENT_NO` | `bigint` | 是 | 已配置的最大流水號，必須大於等於 0 |
| `LOCK_VERSION` | `bigint` | 是 | 樂觀鎖版本；即使採 row lock 仍保留稽核與防誤更新能力 |
| `CUSERID` / `CDATE` | 共通 Audit | 是 | 建立資訊 |
| `UUSERID` / `UDATE` | 共通 Audit | 否 | 最後取號資訊 |

唯一鍵：

```sql
UNIQUE KEY UK_FM_DOC_SEQUENCE (
    TENANT_ID,
    DOCUMENT_TYPE,
    PERIOD_KEY
)
```

必要檢查：

- `CURRENT_NO` 不得小於 0。
- `PERIOD_TYPE=NONE` 時固定使用 `PERIOD_KEY=NONE`。
- `YEAR` 使用 `yyyy`；`MONTH` 使用 `yyyyMM`。
- `CURRENT_NO` 超過 `SEQUENCE_LENGTH` 可表示的位數時必須拒絕取號並建立營運錯誤，不得截斷或回到 1。

## 4. 表單與流程綁定

每個需要正式單號的流程必須指定一個 `DOCUMENT_TYPE`。第一版建議在 `fm_process_def` 增加可空的 `DOCUMENT_TYPE`：

- 有值：送單時必須找到同 Tenant 的有效規則並成功取號。
- 無值：代表流程未啟用正式編號；非正式或技術流程可沿用 UUID。
- 正式業務流程不得在規則缺漏時悄悄降級為 UUID。
- 多個流程可以共用相同 `DOCUMENT_TYPE`，共用同一號碼區間。
- 同一流程建立的新版本沿用流程主檔的 `DOCUMENT_TYPE`，不得因版本變更重設序號。

請購流程設定：

```text
PROCESS_KEY   = FM_PURCHASE_APPROVAL
DOCUMENT_TYPE = PURCHASE_REQUEST
```

表單畫面以平台共用欄位代碼 `documentNumber` 顯示單據編號。表單設計者可在 Form.io 設計器按「加入單據編號欄位」建立唯讀、`persistent=false` 的標準欄位，並依單據種類將標籤改為「請購單編號」、「請款單編號」等，但不得修改欄位代碼。尚未送出時為空值，送出成功後由 Runtime Renderer Context 注入單據編號；不得為每一種表單在 Vue 硬編碼專用欄位。

`businessKey` 是系統技術唯一識別，所有新流程一律使用獨立 UUID，並保存於 Flowable、`fm_process_instance` 與 `fm_form_data`；不得因單據顯示格式改變。`documentNumber` 是使用者查詢、溝通、列印與記憶用的可讀編號，另存於兩張 FlowMint Runtime 表的 `DOCUMENT_NUMBER`，以 Tenant 複合唯一索引保護，未配置 `DOCUMENT_TYPE` 的流程允許為 `NULL`。

Task、申請追蹤與送單結果 API 必須分別回傳 `businessKey` 與 `documentNumber`。一般使用者畫面優先顯示 `documentNumber`，無單據編號時才顯示 business key；維運畫面可同時查詢兩者。`documentNumber` 僅供 Renderer 顯示，起單與補件送出前必須由共用前端工具移除，不寫入一般表單 submission data。

FlowMint 系統表單欄位集中定義如下，不得在各流程頁面重複宣告字串：

| 欄位代碼 | 用途 | 保存方式 |
| --- | --- | --- |
| `documentNumber` | 單據編號顯示 | Renderer only，不保存 |
| `applicantAccount` | 申請人帳號 | 保存，後端重新驗證 |
| `applicantAssignmentId` | 申請人任職指派 | 可選保存，後端重新驗證 |
| `applicantOrgId` | 申請人組織 | 可選保存，後端重新驗證 |

## 5. 併發安全取號

取號不得先查最大業務單號。Logic 必須依 Tenant、單據類型與週期鎖定唯一的 sequence row：

```sql
SELECT CURRENT_NO
  FROM fm_document_sequence
 WHERE TENANT_ID = :tenantId
   AND DOCUMENT_TYPE = :documentType
   AND PERIOD_KEY = :periodKey
 FOR UPDATE
```

在同一交易內將 `CURRENT_NO` 加一並取得新值。當期資料不存在時：

1. 嘗試以 `CURRENT_NO=0` 建立 sequence row。
2. 若唯一鍵衝突，表示另一交易已建立，重新讀取並鎖定該 row。
3. 執行條件更新，把 `CURRENT_NO` 原子加一。
4. 以更新後的值產生單號。

禁止：

- `SELECT MAX(BUSINESS_KEY)`。
- 在 Java 記憶體保存全域 counter。
- 依前端時間計算 `PERIOD_KEY`。
- 捕捉唯一鍵衝突後改用 UUID。
- 未限制 Tenant 的 sequence 查詢或更新。

## 6. 交易與空號政策

第一版採「送單與取號共用交易」：

```text
驗證送單資料與權限
  → 鎖定／建立 sequence
  → 取得下一號
  → 寫入 fm_form_data
  → 啟動 Flowable
  → 寫入 fm_process_instance 與稽核快照
  → 提交交易
```

送單失敗時 sequence 更新一起回滾，因此該號碼可以由下一次成功交易使用。若日後法規或公司政策要求「取號後永不重用」，必須改成獨立交易並接受合理跳號；不得在未確認政策前自行更改。

已提交交易不因後續流程撤回、取消、駁回或終止而回收單號。

## 7. 編號規則異動

- 已使用的 `DOCUMENT_TYPE` 不得改名。
- 修改前綴或格式只影響後續新單號，不回寫歷史資料。
- 已有 sequence 資料時，不得縮短 `SEQUENCE_LENGTH` 至無法容納 `CURRENT_NO`。
- `PERIOD_TYPE` 變更須經 migration 與重複單號檢查，不提供一般畫面直接修改。
- 停用規則後，新送單拒絕取號；既有流程仍保留原單號並可繼續簽核。
- 管理員不得任意調小 `CURRENT_NO`；人工調整必須具備專用權限、原因與不可變稽核紀錄。

## 8. API 與回傳契約

送單 Request 不應要求一般使用者提供正式 `businessKey`。正式流程由後端依 `DOCUMENT_TYPE` 產生，成功回傳：

```json
{
  "businessKey": "PR-A01-202608-000001",
  "processInstanceId": "...",
  "formDataId": "...",
  "processStatus": "RUNNING"
}
```

為相容既有內部或資料遷移用途，若 API 保留輸入 `businessKey`：

- 一般 Workspace 送單必須忽略或拒絕呼叫端輸入。
- 只有具備專用 migration/import 權限的受控 API 可指定外部單號。
- 指定單號仍須驗證 Tenant 唯一性、格式、來源與稽核理由。

## 9. 稽核與權限

- 規則查詢可開放流程設計者唯讀使用。
- 建立、修改與停用規則屬高風險管理操作，必須具備專用權限。
- sequence 不提供一般 CRUD 頁面或 delete API。
- 每次人工調整 sequence 必須保存調整前後值、操作者、時間與原因。
- Runtime Action 與 Snapshot 使用同一 `BUSINESS_KEY`，不另建第二套可變單號。

## 10. 驗收條件

至少完成下列測試後才能上線：

1. 同 Tenant、同單據、同月份連續取號。
2. 不同 Tenant 的號碼互不影響。
3. 不同 `DOCUMENT_TYPE` 的號碼互不影響。
4. 月、年與不重設三種週期切換。
5. Tenant 時區跨月邊界。
6. 多執行緒同時送單不重號。
7. 當期第一筆併發建立 sequence 不重號。
8. 送單交易回滾時 sequence 一起回滾。
9. Idempotency Key 重送回傳原單號，不再取新號。
10. 補件、退回、駁回、撤回及取消不更換單號。
11. 規則缺漏或停用時，正式流程拒絕送單且不降級 UUID。
12. sequence 位數耗盡時拒絕取號並產生可監控錯誤。
13. `fm_form_data`、`fm_process_instance` 與 Flowable business key 完全一致。

## 11. 建議實作順序

1. 核准本規格及空號政策。
2. 新增兩張表與 `fm_process_def.DOCUMENT_TYPE` migration。
3. 建立 Entity、Mapper、Service 與具 row lock 的 Domain Service。
4. 建立併發、回滾、時區與冪等測試。
5. 接入正式送單 Runtime，移除正式流程的 UUID fallback。
6. 為 `PURCHASE_REQUEST` 建立規則 Seed。
7. Workspace 與列印畫面加入唯讀單號。
8. 完成 MariaDB 與瀏覽器 E2E 後更新開發進度。
