# 11 遷移與重建計畫

## 1. 策略

不直接在現有 schema 上邊改邊猜。建立平行的新 schema／新表集合，完成資料轉換與雙跑驗證後切換。

## 2. 現況保護

1. 備份 DB、舊 DDL、程式 commit 與部署版本。
2. 列出每張舊 `fm_*` 表筆數、引用與資料擁有者。
3. 凍結非必要舊主資料異動窗口。
4. 不使用 `DROP`，直到 rollback rehearsal 完成。

## 3. 資料映射

| 舊資料 | 新資料 |
|---|---|
| Tenant | `fm_tenant` |
| Tenant Account | `fm_tenant_account` |
| Person + Employment | `fm_employee` |
| Org Unit + Version | 新 Org Unit + Version |
| Org Approval Level | Scheme + Approval Level |
| Assignment primary org | Employee Org Assignment |
| Org Role HEAD | Org Unit Head |
| Approval Group | Approval Group |
| Process/Form/Runtime | 依 Business ID 與版本轉換 |

Legal Entity、Location、Enterprise Group 不轉入新核心。

## 4. 部門回填

- 移除 `LEGAL_ENTITY_ID`、`LOCATION_ID` 依賴。
- `LEVEL_NO` 只作為 tree depth 參考，不能直接當簽核層級。
- 每個 Active 部門必須由管理者確認 `APPROVAL_LEVEL_ID`。
- 無法確認的部門進入 migration exception report。
- 主管角色必須完成後才允許對該部門發起需要主管的流程。

## 5. 雙跑

使用固定測試帳號與申請資料，舊 Resolver 與新 Resolver 同時執行：

- 比對起始部門。
- 比對主管與層級路徑。
- 比對代理與去重。
- 差異由產品／組織管理者確認。

不允許用「新系統能跑」取代結果正確性比對。

## 6. 切換

1. 停止新申請短暫窗口。
2. 完成最後增量同步。
3. 切換 API／UI 至新表。
4. 驗證登入、組織、Preview、發起、待辦、簽核與稽核。
5. 恢復服務並監控 Incident。

進行中的舊流程建議留在舊 runtime 完成；若必須遷移，需逐流程設計專用策略。

## 7. 移除舊資料

穩定觀察期後：

- 移除舊頁面、Controller、Logic、Service、Mapper、Entity。
- 移除舊選單與權限。
- Drop `fm_enterprise_group`、`fm_legal_entity`、`fm_location` 及其他刪除清單表。
- 封存 migration export 與 checksum。

## 8. Rollback

- 切換前保留舊應用與 DB read/write 能力。
- 新系統寫入期間若需回退，須有新舊雙寫或反向轉換；沒有反向方案時不得宣稱可無損 rollback。
- 回退決策、時間點、資料差異及補正動作必須留存。
