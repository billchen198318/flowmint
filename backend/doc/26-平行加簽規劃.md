# FlowMint 平行加簽規劃

## 1. 目的

本文件規劃簽核人處理待辦時，臨時增加一位或多位加簽人的 Runtime 能力。此功能正式命名為「平行加簽」，不等同既有循序加簽，也不取代流程設計時已配置的 Approval Group `ALL` 正式全員會簽或 `SEQUENTIAL` 依序簽核。

第一版建議語意：原簽核人發起平行加簽後保留原 Task，但暫時不能核准、駁回、退回、轉派或再次發起加簽；系統同時建立多筆加簽子工作。所有加簽人完成回覆後，原 Task 解除鎖定，由原簽核人參考各方意見做最後核決。加簽人不直接推進 BPMN，也不能代替原簽核人核准整張申請。

## 2. 現況與能力邊界

FlowMint 目前已有：

- 流程設計時固定會簽：Task Policy 使用 `ALL`，由 Flowable parallel multi-instance 建立所有成員的正式核決 Task，全員完成後流程才前進。
- 流程設計時循序簽核：Task Policy 使用 `SEQUENTIAL`，依 Resolver 結果逐一建立正式核決 Task。
- Runtime 循序前加簽：Task Policy `ALLOW_ADD_SIGN=Y` 時，原 Task 透過 Flowable delegation 暫交一位加簽人；加簽人完成後還給原 owner。

目前沒有：

- 在一般待辦中一次選取多位臨時加簽人。
- 同一時間建立多筆平行的臨時會簽工作。
- 原 Task 等待所有臨時會簽回覆後再解鎖的狀態模型。
- 平行加簽批次、成員結果與未完成名單的畫面及稽核資料。

## 3. 第一版產品決策

### 3.1 名稱與操作

- 既有「加簽」改以「循序加簽」描述，保留既有行為及 API 相容性。
- 新增「平行加簽」操作，可一次選擇 1～20 位同 Tenant 有效員工。
- 已是原處理人、同批重複人員、停用員工、無有效 membership 的人員不得加入。
- 原 Task 處於代理、既有循序加簽、平行加簽等待或已完成狀態時，不得再發起平行加簽。
- 是否允許平行加簽由發布版 Task Policy 控制，預設關閉。

### 3.2 加簽人的權限

- 加簽人可查看當次表單快照、正式附件、流程摘要及 BPMN 進度。
- 加簽人必須選擇「同意」或「不同意」並填寫意見；第一版意見一律必填。
- 加簽人不能修改表單、附件或流程變數。
- 加簽人不能核准、駁回、退回、轉派、代理、再加簽或再發起平行加簽。
- 單一加簽人完成只結束自己的子工作，不推進 BPMN 主流程。

### 3.3 原簽核人的權限

- 平行加簽進行中，原簽核人的 Task 保留並顯示等待進度，例如 `2 / 3 已回覆`。
- 平行加簽未全數完成前，原簽核人只能查看、留言；不能執行會改變流程狀態的動作。
- 全數完成後，原 Task 自動解除等待，原簽核人可查看每位加簽人的結果與意見，再執行原關卡允許的核准、駁回或退回。
- 第一版不因任一加簽人選擇「不同意」而自動駁回流程；最終決策仍由原簽核人負責，並完整保留不同意意見。

### 3.4 取消與逾時

- 第一版只允許平行加簽發起人在尚無任何成員回覆前取消整批加簽，取消理由必填。
- 任一成員已回覆後不得取消或刪除該成員，避免改寫稽核事實；若人員無法處理，交由具權限的營運管理員執行受控 Reassign。
- 加簽子工作沿用原 Task 剩餘 due date；不得因平行加簽無限制延長 SLA。
- 到期與逾時通知應送給尚未完成的加簽人，原簽核人仍可看到整批逾時狀態。

## 4. Task Policy

在 `fm_task_policy` 增加：

| 欄位 | 建議值 | 說明 |
|---|---|---|
| `ALLOW_PARALLEL_ADD_SIGN` | `Y`／`N` | 是否允許原處理人發起平行加簽 |
| `PARALLEL_ADD_SIGN_MAX_MEMBERS` | `1`～`20` | 單批人數上限，預設 10 |
| `PARALLEL_ADD_SIGN_COMMENT_REQUIRED` | `Y` | 第一版固定為必填，欄位保留未來配置能力 |

流程設計器 User Task Policy 面板新增「允許平行加簽」及人數上限。已發布版本不可變；Runtime 必須讀取該流程實例固定的發布版政策，不能讀目前草稿。

## 5. 資料模型

不建議只依賴 Flowable runtime local variable，因流程完成後不足以完整還原批次及成員稽核。新增兩張 Tenant-scoped 表：

### 5.1 `fm_task_parallel_add_sign`

- `OID`
- `TENANT_ID`
- `PROCESS_INSTANCE_ID`
- `PARENT_TASK_ID`
- `TASK_DEFINITION_KEY`
- `BATCH_NO`
- `STATUS`：`WAITING`、`COMPLETED`、`CANCELLED`
- `INITIATOR_ACCOUNT`
- `REASON`
- `TOTAL_COUNT`
- `COMPLETED_COUNT`
- `AGREE_COUNT`
- `DISAGREE_COUNT`
- `FORM_SNAPSHOT_OID`
- `STARTED_DATE`、`COMPLETED_DATE`、`CANCELLED_DATE`
- 標準 Audit 與 lock version 欄位

同一 Parent Task 同時間只允許一筆 `WAITING` 批次，避免重複點擊建立兩批會簽。

### 5.2 `fm_task_parallel_add_sign_member`

- `OID`
- `TENANT_ID`
- `PARALLEL_ADD_SIGN_OID`
- `MEMBER_ACCOUNT`
- `FLOWABLE_TASK_ID`
- `STATUS`：`PENDING`、`AGREED`、`DISAGREED`、`REASSIGNED`、`CANCELLED`
- `COMMENT`
- `COMPLETED_DATE`
- `ORIGINAL_MEMBER_ACCOUNT`，管理員改派時保留原人員
- 標準 Audit 與 lock version 欄位

同一批次 `MEMBER_ACCOUNT` 唯一。所有查詢與異動必須同時限制 `TENANT_ID`、批次及 Parent Task。

## 6. Flowable 實作策略

第一版建議採「Parent Task + Flowable subtask」：

1. 原 Task 保留 assignee／owner，不完成、不離開目前 BPMN User Task。
2. 建立平行加簽批次及不可變表單快照。
3. 以 Flowable TaskService 建立多筆具 Parent Task ID 的子工作，每位加簽人一筆 assignee Task。
4. Parent Task 設定受控 local variable／category，供 Inbox 與 Action Guard 快速判斷正在等待會簽；資料庫批次表才是正式狀態來源。
5. 每位加簽人完成時，條件更新 member 狀態並原子遞增批次統計，再完成自己的 Flowable subtask。
6. 最後一位完成時將批次轉為 `COMPLETED`、清除 Parent Task 等待旗標並通知原處理人。
7. Parent Task 仍由既有 approve／reject／return Runtime 完成，BPMN 路徑不因子工作直接改變。

不要在執行中的一般 User Task 臨時改寫已發布 BPMN XML，也不要把平行加簽人加入既有 fixed multi-instance collection；這會混淆發布版流程語意、歷史 execution 與 Incident Retry。

## 7. API 規劃

沿用 `/api/fm/requests/tasks` Runtime 邊界：

| API | 用途 |
|---|---|
| `POST /parallel-add-sign-options` | 查詢同 Tenant 可選員工，排除不合法對象 |
| `POST /start-parallel-add-sign` | 原簽核人以 `taskId`、成員帳號陣列及原因建立平行加簽批次 |
| `POST /complete-parallel-add-sign` | 加簽人提交 `AGREE`／`DISAGREE` 與意見 |
| `POST /cancel-parallel-add-sign` | 尚無回覆時由發起人取消整批 |
| `POST /parallel-add-sign-detail` | Parent Task、加簽子 Task 與申請追蹤頁取得批次進度及結果 |

所有 API 從 Spring Security Context 取得操作者，Tenant 從 `X-FlowMint-Tenant` 取得；body 不接受操作者或 Tenant 覆寫。`start-parallel-add-sign` 必須支援 idempotency token 或 Parent Task + request key 唯一限制，避免連點建立重複子工作。

## 8. 稽核、快照與通知

新增 Task Action 類型：

- `PARALLEL_ADD_SIGN_START`
- `PARALLEL_ADD_SIGN_AGREE`
- `PARALLEL_ADD_SIGN_DISAGREE`
- `PARALLEL_ADD_SIGN_COMPLETE`
- `PARALLEL_ADD_SIGN_CANCEL`
- `PARALLEL_ADD_SIGN_REASSIGN`

發起時固定一份表單快照，所有加簽人查看同一 revision；每個成員回覆建立獨立 Action。最後一人完成時另建批次完成 Action。申請追蹤、流程監控及稽核明細需能顯示批次、成員、結果、意見與時間，不能只留下通用 COMMENT。

新增通知事件：

- `PARALLEL_ADD_SIGN_ASSIGNED`：送給每位加簽人。
- `PARALLEL_ADD_SIGN_COMPLETED`：全數完成後送給原簽核人。
- `PARALLEL_ADD_SIGN_CANCELLED`：取消時送給原簽核人及原加簽人。
- due soon／overdue 沿用既有 Task SLA 通知管線。

## 9. 前端規劃

### 9.1 原簽核人待辦

- Task Policy 允許且狀態合法時，在既有「循序加簽」旁顯示「平行加簽」。
- 點擊後開啟對話框，提供多人搜尋／選取、已選人員清單、原因及人數上限提示。
- 送出前再次確認「所有加簽人回覆前，本關卡將暫停核決」。
- 平行加簽進行中顯示進度卡：總數、已完成、同意、不同意、尚未回覆及期限。
- 全數完成後顯示每位人員的結果與意見，並恢復原 Task 動作按鈕。

### 9.2 加簽人待辦

- Inbox 以「會簽」標籤和一般核決 Task 區分。
- 明細表單唯讀，附件可依權限下載。
- 僅顯示「同意」「不同意」、必填意見及送出按鈕。
- 清楚提示「此回覆不會直接核准或駁回整張申請」。

### 9.3 申請追蹤與 BPMN

- 申請詳情目前關卡下增加會簽進度摘要。
- BPMN 仍標示 Parent User Task 為進行中，不為每位平行加簽人偽造 BPMN 節點。
- 點選目前節點或進度卡可查看加簽人與狀態；一般申請人可查看進度與結果，但是否顯示完整意見應沿用流程稽核權限政策。

## 10. 後端防線

- Parent Task 進入 `WAITING` 會簽狀態時，既有 action、transfer、delegate、add-sign、withdraw／cancel 相關處理須明確定義並由後端阻擋或受控結束，不能只隱藏前端按鈕。
- 平行加簽子工作不可進入一般 `action()` 核准路徑。
- 發起、成員完成、最後一人解鎖及取消均需交易處理與條件更新，防止兩人同時送出造成計數錯誤。
- 成員清單必須重新驗證 Tenant、員工、membership、狀態與有效期間。
- 附件下載沿用正式附件授權，不因知道 process／attachment ID 即可下載。
- Process 已結束、Parent Task 不存在或批次不是 `WAITING` 時，所有會簽異動拒絕。

## 11. 實作階段

### Phase A：契約與資料模型

1. 確認產品語意、取消規則、不同意處理與最大人數。
2. 增加 Task Policy 欄位、平行加簽批次／成員表、Entity、Mapper、Service 與狀態常數。
3. 增加資料庫 migration、完整 `flowmint.sql` 及 Mapper 契約測試。

### Phase B：Runtime

1. 建立 options、start、complete、cancel、detail API。
2. 建立 Flowable subtask、Parent Task lock 與交易／併發防線。
3. 整合表單快照、Task Action、附件授權及流程參與者權限。
4. 補齊通知與 SLA。

### Phase C：Vue

1. 原簽核人多人選擇對話框與會簽進度卡。
2. 加簽人專用唯讀 Task 明細與回覆操作。
3. Inbox 標籤、申請追蹤與流程進度整合。
4. 桌面及手機版操作與錯誤狀態。

### Phase D：驗收

1. 單人、多人及 20 人上限會簽。
2. 平行同時完成最後兩筆的併發測試，只能解鎖一次。
3. 一人不同意後仍等待其他人，最後由原簽核人決策。
4. 重複送出、跨 Tenant、停用帳號、自己、重複成員均拒絕。
5. 會簽中不得核准、駁回、退回、轉派、代理或再次加／會簽。
6. 取消、管理員 Reassign、due soon、overdue 與流程提前終止。
7. 表單唯讀、附件顯示／下載、快照及完整稽核。
8. 申請詳情、Task 頁及 BPMN 進度在首次與重複開啟時一致。
9. MariaDB／Flowable 多帳號瀏覽器 E2E 與行動版驗收。

## 12. 不納入第一版

- 加簽人自行再加簽或再發起下一層平行加簽。
- 平行加簽進行中任意增刪成員。
- 任一不同意自動駁回整個流程。
- 百分比、多數決、一票否決等自訂完成條件。
- 動態修改已發布 BPMN 或把臨時會簽永久寫回流程設計。
- 跨 Tenant、外部訪客或無 QIFU4 帳號會簽。

若未來確實需要「多位簽核人共同決定流程結果」，應使用或擴充正式 Approval Multi-instance，不能把平行加簽直接當成正式會簽，因其流程推進、退回、駁回、SLA 與稽核語意完全不同。
