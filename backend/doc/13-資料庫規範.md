# 13 資料庫規範

## 1. 基準

- MariaDB 10.11+。
- Table：lowercase snake_case。
- Column：UPPER_SNAKE_CASE。
- Engine：InnoDB。
- Charset：utf8mb4。
- Collation：utf8mb4_unicode_ci。
- 業務時間：`datetime(3)`，保存 UTC。

## 2. 主鍵與業務 ID

每張表：

```sql
OID char(36) NOT NULL PRIMARY KEY
```

OID 是資料庫技術主鍵；`TENANT_ID + *_ID` 是 API 與關聯使用的業務唯一鍵。不得把自增數字暴露成跨系統 ID。

正式單據流水號不得以 `SELECT MAX(...) + 1` 產生。共用編號須使用
Tenant-scoped sequence row、唯一鍵及交易鎖；詳細規格見
[24 共用單據編號規格](24-共用單據編號規格.md)。

## 3. Audit 欄位

所有業務表必須有：

```sql
CUSERID varchar(24) NOT NULL
CDATE   datetime(3) NOT NULL
UUSERID varchar(24) NULL
UDATE   datetime(3) NULL
```

Insert 設定 CUSERID/CDATE；Update 設定 UUSERID/UDATE。不可覆寫建立者與建立時間。

## 4. Tenant

- 所有 `fm_*` 表必須有 `TENANT_ID`。
- 每個業務 unique key 第一欄為 Tenant。
- 查詢、更新、停用都帶 Tenant。
- 全域 notification delivery worker 例外查詢仍須在取出後依 Tenant context 處理。

## 5. 狀態與刪除

- 主資料使用 `ACTIVE/INACTIVE`。
- 不提供一般 physical delete API。
- 已被發布版本、instance、snapshot 或 action 引用的資料不得刪除。
- Draft 若允許刪除，也必須由 Logic 驗證無引用並寫 audit。

## 6. JSON

- JSON Schema、BPMN XML、Resolver Config、Context 使用 `longtext`。
- 寫入前由應用程式 parse 與 schema validate。
- Runtime 常用查詢欄位不得只藏在 JSON，應有正常欄位與索引。
- Snapshot JSON 不更新。

## 7. Index

- Index 依實際 where/order 設計，不為每個欄位建立索引。
- 待辦、instance、employee primary org、head resolve 必須有覆蓋前綴。
- 上線前以真實量級執行 `EXPLAIN`。
- `%keyword%` 大量搜尋若成為瓶頸，再評估全文索引，不先增加複雜度。

## 8. Foreign Key

新核心 DDL以 Business ID 與 Service validation 為主，暫不建立跨 `tb_*`／`ACT_*` 的 physical FK。是否為 `fm_*` 增加 FK，須在 migration 與 QIFU4 BaseService 相容性測試後一次決定，不可部分隨意增加。

## 9. Migration

- 每支 migration 有唯一版本、說明、forward 與必要 rollback。
- 禁止修改已部署 migration。
- DDL 與資料回填分段。
- Drop table／column 前先做引用、筆數、備份與 rollback 檢查。
- Production migration 不使用未限制範圍的大型單一 Update。
