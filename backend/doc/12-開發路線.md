# 12 開發路線

## Phase 0：基準與 Schema

- 核准 `newdoc`。
- 在隔離 DB 執行 `flowmint-core-schema.sql`。
- 建立 Entity、Mapper、Service 骨架。
- 建立 schema 靜態檢查。

完成：空 DB 可重建，表數與約束一致。

## Phase 1：組織垂直切片

- Tenant context。
- Employee。
- Approval Level Scheme。
- Department CRUD／version／tree drag。
- Employee primary org。
- HEAD／DEPUTY／ACTING。
- Resolver Preview。

完成：不建立法人與據點也能找到逐級主管。

## Phase 2：設計時

- Form Designer／version／publish。
- BPMN Designer／version／publish。
- Task Policy。
- Assignment Rule。
- Publish validation。

完成：非工程人員可設定一個部門主管簽核流程。

## Phase 3：最小 Runtime

- Draft／Submit。
- Inbox／Task Detail。
- Approve／Reject／Return／Resubmit。
- Process／Form／Assignment snapshot。
- Process trace。

完成：第一個端到端案例通過。

## Phase 4：完整操作

- Withdraw／Cancel。
- Transfer。
- Delegation／Resolve。
- Add Sign。
- Approval Group 多人模式。
- Incident operations。

## Phase 5：營運

- Notification。
- 管理員 Reassign／Terminate。
- Audit query。
- 基本報表與效能調校。
- 台灣／中國大陸完整 E2E。

開發優先序調整：Phase 4 完成後，優先開發 Phase 5 營運功能；正式請購單與 Grid 品項明細延後至 Phase 5 核心營運能力完成之後。

## 核心明確排除（不是未完成 Backlog）

- 集團、法人、據點。
- Job、Grade、Position。
- Project Organization。

上述項目不屬於 FlowMint 簽核核心，不納入完成度、Release Gate 或產品評分。公司、分公司、廠區與辦公室若只用於尋找簽核路徑，以組織樹節點表達；Title、Approval Level、Duty 與有效任職已足以處理目前確認的主管及核決案例。

只有具體業務案例需要簽約法人、統編、付款主體、工安廠區、收貨據點或專案型簽核時，才另案評估表單欄位或外部主檔整合，不預先建立核心主檔。

## 需求驅動的非核心擴充

- HR／ERP 同步平台。
- SLA 工作日曆。
- 外部低代碼 Script。

這些能力只有在已確認的簽核案例需要時才排程；未實作不妨礙核心簽核完成，但可能影響特定客戶的整合或 SLA 需求。任何新增項目都必須回答：「它解決哪一個已確認的簽核案例？」否則不進核心。
