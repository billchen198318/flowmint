# FlowMint 流程簽核改派規格與完成紀錄

> 目前狀態（2026-08-24）：本文件原始規劃已完成實作。正常 active Task、Incident Task 與平行加簽成員均有受控管理員改派路徑；後端 options／preview／reassign、權限與安全驗證、冪等、快照、Action、通知及流程監控操作畫面均已完成。剩餘工作僅為部署環境多人 UAT，不是待開發程式。下文保留原始設計內容作為契約與驗收依據。

## 1. 目的

本文件原始目的為規劃營運功能「流程簽核改派」；該功能目前已完成。流程管理員可針對某一個執行中流程實例的某一張 active Task，將原簽核責任人改派給另一位有效人員，並完整保存原因、前後人員、操作者、表單快照與指派快照。

此功能用於離職、長期請假、帳號停用、組織資料錯誤、緊急營運處理或明確的人工作業修正。它不是讓管理員任意改寫已完成歷史，也不是繞過流程設計及核決權限的日常操作捷徑。

## 2. 與既有功能的差異

| 功能 | 操作者 | 適用對象 | Task Policy | 現況 |
|---|---|---|---|---|
| 使用者轉派 `TRANSFER` | 目前 assignee／candidate | 自己正在處理的正常 Task | 必須 `ALLOW_TRANSFER=Y` | 已實作 |
| Incident Reassign | 系統管理員／`FLOWMINT_OPERATIONS` | Resolver 失敗且有 `OPEN` Incident 的 Task | 不依 `ALLOW_TRANSFER` | 已實作 |
| 流程簽核改派 `ADMIN_REASSIGN` | 受權限流程管理員 | 正常執行中的指定 active Task | 不依 `ALLOW_TRANSFER` | 已實作，待多人 UAT |
| 工作代理 `DELEGATE` | 原責任人 | 有期間代理授權的 Task | 依代理授權 | 已實作 |

流程簽核改派是例外管理操作。一般簽核人可維持 `ALLOW_TRANSFER=N`，管理員仍可在具備新權限、合法狀態及強制理由的情況下執行改派。

## 3. 產品入口

第一版整合於既有流程實例監控 `/operations/processes`，不另建立與流程監控重複的清單頁。

操作路徑：

```text
流程實例監控
→ 查詢 RUNNING 流程
→ 查看流程明細
→ 目前簽核工作
→ 選擇精確 Task
→ 流程簽核改派
→ 選擇新簽核人、填寫原因
→ 二次確認
→ 改派完成並重新載入明細
```

流程明細新增「目前簽核工作」區塊，每張 active Task 至少顯示：

- Task ID。
- BPMN Task Definition Key 與節點名稱。
- assignment mode。
- assignee、owner、candidate users／groups。
- 是否為 multi-instance 與目前 instance 狀態。
- 建立時間、due date、逾時狀態。
- delegation state、Task category。
- 是否允許管理員改派，以及不可改派原因。

不能只顯示節點名稱後讓管理員改派，因為 `ALL` 會簽在同一節點可能同時存在多張 active Task，必須精確選擇其中一張 Task。

## 4. 權限模型

### 4.1 建議新增專用權限

基於最小權限原則，建議新增 FlowMint 業務角色：

```text
FLOWMINT_REASSIGN
```

後端允許：

- QIFU4 系統管理員；或
- 具有 `FLOWMINT_REASSIGN` 的帳號。

不建議只因帳號可查看 `/operations/processes` 或具有廣泛 `FLOWMINT_OPERATIONS` 就自動取得改派能力。若為相容既有部署，第一版可暫時允許 `FLOWMINT_OPERATIONS`，但正式上線前應拆分 Query 與 Action 權限。

### 4.2 Program 與 API 必須雙重檢查

- QIFU4 Program／Role 控制頁面與按鈕入口。
- 後端 API 重新檢查系統管理員或 `FLOWMINT_REASSIGN`。
- Tenant 從 `X-FlowMint-Tenant` 取得。
- Actor 從 Spring Security Context 取得。
- Request body 不接受 Tenant、管理員帳號或原簽核人帳號覆寫。

隱藏按鈕不是授權。直接呼叫 API 仍必須被後端拒絕。

## 5. 第一版支援範圍

### 5.1 一般單一 assignee Task

支援。將目前 assignee 由 bill 改為新帳號，Task ID 與 BPMN execution 不變，流程不前進。

### 5.2 尚未 claim 的 `CANDIDATE` Task

支援。管理員選擇一位新責任人後：

1. 清除原 candidate user／group identity links。
2. 設定唯一 assignee。
3. Task 從候選池轉為明確指派。

此操作不是把新帳號加入候選名單，而是將這張 Task 明確改派給指定人員。

### 5.3 `ALL` parallel multi-instance 正式會簽

支援改派其中一張指定 active Task：

- 只替換該 Task 的 assignee。
- 不新增或刪除 multi-instance execution。
- 不改變總會簽人數及 completion condition。
- 其他會簽人的 Task 不受影響。
- 新簽核人完成後，仍計入原本該 instance 的一份正式核決。

如果目標帳號已是同一流程、同一 Task Definition Key 的 active 會簽人，第一版拒絕，避免同一人持有兩張平行正式會簽 Task。

### 5.4 `SEQUENTIAL` multi-instance

只支援改派目前已建立且 active 的那一張 Task。尚未建立的後續簽核人仍由原 multi-instance collection 與流程版本決定，第一版不修改未來成員順序。

### 5.5 已 claim 的 candidate Task

視同一般 assignee Task 處理；稽核仍應保存其原始 candidate resolution snapshot，不得把歷史改寫成從未存在候選人。

## 6. 第一版明確不支援

下列 Task 不得由一般「流程簽核改派」直接處理：

- 已完成、刪除或不存在的 Task。
- 非 `RUNNING` 流程的 Task。
- 有 `OPEN` Assignment Incident 的 Task；必須走既有 Incident Reassign／Retry。
- `DelegationState.PENDING` 的代理 Task；應先依代理語意 Resolve 或另建專用管理操作。
- 既有循序加簽中的 Task。
- 規劃中的平行加簽子 Task。
- `APPLICANT_CORRECTION` 申請人補件 Task；不得把申請人的補件責任改給其他人。
- Flowable system／service／receive Task。
- 已在同一 request key 下完成過改派的重複請求。

第一版也不提供：

- 批次改派某員工名下所有 Task。
- 依部門、流程或日期一次大量改派。
- 修改已完成歷史 assignee。
- 新增或刪除 `ALL` multi-instance 的會簽份數。
- 改寫 `SEQUENTIAL` 尚未建立的未來簽核名單。
- 在管理員改派時直接完成、核准、駁回或跳過 Task。

批次改派的影響範圍大，應在單筆功能穩定、具備 Preview 與四眼覆核後另案規劃。

## 7. 目標人員驗證

改派目標必須全部符合：

- 與流程及 Task 相同 Tenant。
- FlowMint Employee 為有效狀態及有效期間。
- 具有非空 QIFU4 account。
- 具有有效 Tenant membership。
- 不是目前 assignee。
- 不是管理員僅輸入的顯示名稱；API 必須使用正式 account value。
- 若為 `ALL` 會簽，不是同節點另一張 active Task 的 assignee。

建議同時執行發布版 Task Policy 的治理檢查：

- `selfApprovalPolicy != ALLOW` 時，不得改派給表單 Owner／申請人。
- `duplicatePolicy == SKIP_ALREADY_APPROVED` 時，不得改派給已在本流程核准的人員。
- 若目標人員不在原 Assignment Rule 解析範圍，畫面顯示明確警告，但管理員可在填寫加強理由後改派；否則本功能無法處理原 Resolver 範圍外的例外情況。

第一版建議採「硬性安全條件拒絕、治理範圍差異警告」：跨 Tenant、失效帳號、自己、補件 Task、重複 active 會簽人等直接拒絕；不在原 Resolver 結果則警告並要求管理員確認。

## 8. 改派表單

對話框欄位：

| 欄位 | 必填 | 說明 |
|---|---|---|
| 流程／單據 | 唯讀 | process name、document number、process instance ID |
| 目前節點 | 唯讀 | task name、task definition key、task ID |
| 原簽核人 | 唯讀 | account 與員工顯示名稱 |
| 新簽核人 | 是 | 後端 options API 回傳的有效員工 |
| 改派原因分類 | 是 | 離職、請假、帳號異常、指派錯誤、緊急處理、其他 |
| 詳細原因 | 是 | 10～1000 字；「其他」不得只填分類名稱 |
| 影響警告 | 唯讀 | 是否會簽、是否逾時、是否不在原 Resolver 範圍 |
| Request Key | 隱藏 | 防止連點及網路重送 |

送出前二次確認文字應包含原簽核人、新簽核人及節點：

```text
確定將「財務審核」Task 從 bill 改派給 fm00830？
此操作會立即移除 bill 的處理權，並留下不可變稽核紀錄。
```

## 9. API 規劃

Base path 沿用 `/api/fm/operations`：

### 9.1 查詢 active Tasks

```text
POST /process-instances/active-tasks
```

Request：

```json
{
  "processInstanceId": "..."
}
```

回傳每張 active Task 的精確識別、指派狀態、政策摘要及 `reassignable`／`blockedReason`。

### 9.2 改派 Preview

```text
POST /tasks/reassign-preview
```

Request：

```json
{
  "taskId": "...",
  "targetAccount": "fm00830"
}
```

Preview 重新讀取 Task、流程、表單、發布版 Policy、Assignment Rule 與目標人員，回傳：

- 原簽核人與新簽核人。
- Task 類型及 assignment mode。
- 是否 multi-instance。
- 是否命中原 Resolver 結果。
- 自簽／重複簽核警告。
- 是否可執行及阻擋原因。

### 9.3 改派選項

```text
POST /tasks/reassign-options
```

Request 包含 `taskId`，後端只回傳同 Tenant 的有效員工，並排除明確不合法對象。不得回傳所有 Tenant 的帳號後交給 Vue 自行過濾。

### 9.4 正式改派

```text
POST /tasks/reassign
```

Headers：

```text
X-FlowMint-Tenant: A01
Idempotency-Key: <UUID>
```

Request：

```json
{
  "taskId": "...",
  "targetAccount": "fm00830",
  "reasonCode": "EMPLOYEE_LEAVE",
  "reason": "原簽核人長期請假，依財務主管核准改派。"
}
```

Response 應包含 process instance、Task、原帳號、新帳號、action type、處理時間及最新 Task 狀態。

## 10. 後端交易流程

正式改派必須在單一交易內執行：

1. 驗證 request、理由長度及 idempotency key。
2. 從 Security Context 取得管理員帳號並驗證 `FLOWMINT_REASSIGN`。
3. 依 `taskId` 鎖定或取得具 optimistic concurrency 保障的 active Flowable Task。
4. 依 Tenant + process instance ID 取得 `RUNNING` FlowMint process index。
5. 讀取該流程實例固定版本的 Task Policy 與 Assignment Rule。
6. 拒絕 Incident、代理、加簽、補件及不支援 Task。
7. 驗證目標員工、membership、自簽、重複核准及 multi-instance 重複人員。
8. 保存改派前 assignee、owner、candidates、delegation state、due date 與 Resolver context。
9. 若為 candidate Task，移除原 candidate identity links。
10. 設定新 assignee；Task ID、execution、task definition key、due date 及流程 token 不變。
11. 建立 resolver type `ADMIN_REASSIGN` 的新 Assignment Snapshot。
12. 建立不可變表單快照。
13. 建立 `ADMIN_REASSIGN` Task Action，保存原／新帳號、原因分類、理由與管理員。
14. 建立通知事件。
15. 寫入 idempotency 結果或受控操作紀錄。
16. Commit 後回傳結果；任一步失敗則整筆回滾。

管理員載入 Preview 後，原簽核人可能同時完成 Task。因此正式 POST 不可相信 Preview，必須重新驗證 active Task；若 Task 已完成，回傳明確衝突，不得把下一關 Task 誤改派。

## 11. 資料與稽核

### 11.1 沿用既有資料

第一版可沿用：

- `fm_task_assignment_snapshot`：保存改派後正式指派及來源 context。
- `fm_form_snapshot`：保存改派當下的表單 revision 與 digest。
- `fm_task_action`：保存 `ADMIN_REASSIGN` 動作。
- Flowable Task／Historic Task：保存實際 assignee 變更及生命週期。

### 11.2 建議補強的 Action context

若現有 `outcome`、`comment`、`reason` 欄位不足以結構化查詢，建議為 `fm_task_action` 增加受控 `ACTION_CONTEXT` JSON，或新增通用營運操作紀錄表。至少保存：

```json
{
  "source": "PROCESS_OPERATIONS",
  "previousAssignee": "bill",
  "targetAssignee": "fm00830",
  "reasonCode": "EMPLOYEE_LEAVE",
  "assignmentMode": "ASSIGNEE",
  "multiInstance": false,
  "targetInOriginalResolver": false
}
```

不能只保存「已改派」文字，否則日後無法可靠回答誰把誰改給誰。

### 11.3 不可變原則

- 不更新或刪除原 Assignment Snapshot。
- 不修改歷史 Task Action。
- 新增一份 `ADMIN_REASSIGN` Snapshot／Action 表達狀態改變。
- 流程監控時間軸同時顯示原始指派與管理員改派。

## 12. 通知

新增通知事件：

```text
TASK_ADMIN_REASSIGNED
```

收件人：

- 新簽核人：通知取得待辦、流程／單號、節點、期限及管理員改派說明。
- 原簽核人：通知待辦已被管理員移除及原因。
- 可選：流程 Owner／Starter；依 Tenant 通知政策決定，預設不寄送以避免資訊噪音。

站內通知與 Email 共用 Template Manager 範本及穩定事件 ID。相同 idempotency key 不得重複寄送。

## 13. SLA 與期限

第一版改派不重設 due date，沿用原 Task 剩餘期限：

- 避免用改派規避逾時統計。
- 新簽核人可能收到已接近期限或已逾時的 Task，畫面必須明確警告。
- 原簽核人的未讀 Task Assigned 通知不刪除，但新增「已改派」通知說明失去處理權。
- SLA 報表仍以原 Task 建立至完成計算，管理員改派不切斷處理時間。

未來若需要重設期限，必須另設專用權限、原因與原／新 due date 稽核，不能隨改派自動重算。

## 14. Vue 畫面規劃

### 14.1 流程監控清單

保留目前 `/operations/processes` 清單及篩選。只有 `RUNNING` 流程顯示可進入「目前簽核工作」的操作提示。

### 14.2 流程明細

在既有稽核軌跡前新增：

```text
目前簽核工作（3）
┌─────────────────────────────────────────────────────┐
│ 財務會簽 │ Task ...01 │ bill │ 期限 ... │ [管理員改派] │
│ 法務會簽 │ Task ...02 │ mary │ 期限 ... │ [管理員改派] │
│ 資安會簽 │ Task ...03 │ john │ 期限 ... │ [管理員改派] │
└─────────────────────────────────────────────────────┘
```

同一節點多張 Task 必須逐張顯示，不能合併成單一「目前節點」。

### 14.3 改派對話框

- 顯示流程、單號、節點、Task ID、原簽核人與期限。
- 可搜尋新簽核人，選項顯示姓名、account、部門。
- 選擇後呼叫 Preview。
- 呈現阻擋原因或治理警告。
- 原因分類及詳細原因必填。
- 二次確認後送出。
- 成功後關閉對話框、重新載入 active Tasks 及稽核時間軸。
- API 衝突時明確提示「Task 已由其他人完成或改派」，不得假裝成功。

桌面使用 table，手機改為逐張 card，Task ID 可複製但不作為主要辨識文字。

### 14.4 前端檔案與元件目錄

本功能不把所有程式繼續堆進既有 `pages/operations/processes.vue`。建議檔案配置如下：

```text
frontend-v-nx/
├─ pages/
│  └─ operations/
│     └─ processes.vue
│        # 保留流程查詢、選取流程及組裝明細；掛載改派元件
├─ components/
│  └─ flowmint/
│     └─ operations/
│        ├─ ActiveTaskList.vue
│        │  # 顯示目前 active Tasks、狀態與改派入口
│        ├─ TaskReassignModal.vue
│        │  # 新簽核人、原因、Preview、二次確認與送出
│        └─ TaskAssignmentSummary.vue
│           # assignee、owner、candidate、會簽及期限摘要
└─ composables/
   └─ useTaskReassignmentOperations.ts
      # active-tasks、options、preview、reassign API 與 loading/error state
```

責任分界：

- `processes.vue` 只管理 Tenant、流程清單、選取的 process instance 及重新載入。
- `ActiveTaskList.vue` 不自行取得 Tenant，必須由 page 傳入目前 Tenant 與 process instance ID。
- `TaskReassignModal.vue` 不直接操作流程清單；成功後 emit `reassigned`，由 page 重新載入 active Tasks 與稽核明細。
- `useTaskReassignmentOperations.ts` 統一附加 `X-FlowMint-Tenant`，但不保存全域可跨 Tenant 重用的 options cache。
- API DTO 應建立明確 TypeScript interface，不使用大量 `any` 隱藏契約。

第一版不新增 `/operations/reassignments` 路由，也不建立另一套流程搜尋頁。若未來增加批次改派、待覆核佇列或改派申請單，才評估獨立頁面。

### 14.5 選單與 Program 掛載位置

本功能掛在既有 FlowMint 營運目錄下的流程實例監控：

```text
FlowMint 營運
└─ FH01 - 流程實例監控
   └─ /operations/processes
      └─ 流程明細／目前簽核工作／管理員改派
```

既有 Program ID：

```text
FM_PROG008D0001Q
```

因此第一版：

- 不新增左側選單項目。
- 不新增新的 page route 或重複 Program。
- `FM_PROG008D-register.sql` 只在需要補充 action permission metadata 時更新，不重新註冊另一張流程監控頁。
- 能進入 `FM_PROG008D0001Q` 只代表可查看流程；「管理員改派」按鈕及 API 仍需額外 `FLOWMINT_REASSIGN` 權限。
- 沒有改派權限的人仍能依原 Program 權限查看稽核，但看不到改派按鈕，直接呼叫 API 亦被拒絕。

若 QIFU4 現行 Program 模型無法對單一按鈕配置獨立 action permission，後端角色檢查仍是必要安全邊界；前端可由後端回傳 `canReassign` capability 控制顯示，不能在 Vue 寫死帳號或角色名稱。

### 14.6 後端檔案與套件位置

建議新增專責類別，不把一般 active Task 改派混入只處理 Incident 的 Logic：

```text
backend/app/src/main/java/org/qifu/fm/
├─ controller/
│  └─ FmTaskReassignmentOperationsController.java
├─ logic/
│  ├─ IFmTaskReassignmentOperationsLogicService.java
│  └─ impl/
│     └─ FmTaskReassignmentOperationsLogicServiceImpl.java
├─ domain/runtime/
│  └─ FmTaskReassignmentValidator.java
```

API base path 仍為 `/api/fm/operations`。Controller 只做 request mapping、欄位檢核入口及標準 response；權限、Tenant、Flowable 狀態、目標人員、交易、Snapshot 與 Action 都放在 Logic／Domain，不在 Controller 拼裝。

現有類別的調整邊界：

- `FmProcessMonitorLogicServiceImpl`：擴充或委派 active Task 唯讀查詢，不承擔改派交易。
- `FmIncidentOperationsLogicServiceImpl`：維持既有 Incident Retry／Reassign／Terminate，不吸收正常 Task 改派。
- 共用的有效員工、membership、Assignment Snapshot 與 audit 能力應抽取／沿用，避免複製一套不同驗證。
- Mapper 只有在增加 `ACTION_CONTEXT` 或操作 idempotency persistence 時新增；Flowable active Task 仍由 TaskService 查詢。

## 15. 特殊情境

### 15.1 `ALL` 會簽

若 bill 是三張會簽 Task 其中之一，只改派 bill 對應的 Task。畫面需顯示「這是 3 人會簽中的 1 張」，並列出其他 active 會簽人，避免管理員誤以為會替換整個節點。

### 15.2 `CANDIDATE`

若 Task 尚未 claim，管理員改派代表從候選池指定一位新 assignee。原 candidates 失去處理權，必須通知或至少在稽核中可見。

### 15.3 代理

代理中的 Task 同時有 owner、assignee 及 delegation state。直接改 assignee 可能破壞 `RESOLVE` 語意，第一版拒絕。未來如需支援，應提供「管理員取消代理後改派」的複合受控操作。

### 15.4 循序加簽

加簽中的 Task 使用 delegation 及 `flowMintAddSign` local variable。第一版拒絕；必須先由加簽人完成，或另規劃管理員取消加簽。

### 15.5 申請人補件

`APPLICANT_CORRECTION` 必須由表單 Owner 補件，不屬一般簽核責任，不允許管理員改派給其他員工。

### 15.6 Incident

有 `FLOWMINT_INCIDENT:{incidentId}` category 的 Task 必須導向 `/operations/incidents`，沿用既有 Retry／Reassign／Terminate，避免兩套功能同時關閉或改寫 Incident。

## 16. 安全與併發防線

- 精確限制 Tenant + process instance + task ID。
- Task 必須仍 active，流程必須仍 `RUNNING`。
- 正式操作重新檢查權限、目標人員與所有狀態。
- 使用 idempotency key 防止連點及網路重送。
- 處理 bill 同時核准、另一管理員同時改派、流程被終止等競態。
- Flowable assignee 更新成功但快照／Action 失敗時必須回滾。
- 不接受前端傳入 previous assignee 作為可信資料。
- Options 與 Preview 都不是授權結果，POST 仍需完整驗證。
- API log 不輸出 JWT、Cookie、附件內容或完整敏感表單 JSON。
- 原因及 Action context 進行長度、格式及輸出 escape。

## 18. 驗收案例

### 18.1 基本成功

1. 流程正常指派給 bill。
2. bill 的 Task Policy 為 `ALLOW_TRANSFER=N`，bill 看不到自行轉派。
3. 具 `FLOWMINT_REASSIGN` 的管理員在流程監控找到該流程及 Task。
4. 管理員選擇 fm00830、原因分類與詳細原因。
5. Preview 顯示原 bill、新 fm00830 及政策警告。
6. 正式改派成功，Task ID、流程節點及 due date 不變。
7. bill 失去 Task 存取與操作權。
8. fm00830 取得待辦並可正常核准。
9. 流程歷程顯示 `ADMIN_REASSIGN`，原／新帳號、管理員及原因完整。
10. 雙方收到正確通知且沒有重複寄送。

### 18.2 權限與資料邊界

- 一般使用者直接呼叫 API 被拒絕。
- 只有流程查詢權、沒有改派權的營運人員被拒絕。
- 跨 Tenant Task 或目標帳號被拒絕。
- 停用、過期、無 membership 的帳號不出現在 options，直接提交也被拒絕。
- 前端偽造原 assignee、管理員 account 或 Tenant 不影響後端判斷。

### 18.3 狀態與競態

- Task 已完成後改派被拒絕。
- bill 與管理員同時操作，只有一個合法狀態轉換成功。
- 兩位管理員同時改派，只有一筆生效，另一筆收到衝突。
- 相同 idempotency key 重送回傳同一結果，不重複建立 Action 或通知。
- 同 key 改成不同 target／reason 被拒絕。

### 18.4 多人模式

- `ALL` 三人會簽只替換 bill 那一張 Task，其他兩張不變。
- `ALL` 不可改派給同節點另一位 active assignee。
- `SEQUENTIAL` 只改派當前 active Task，不改變未來順序。
- 未 claim candidate 改派後清除候選並設定唯一 assignee。

### 18.5 阻擋案例

- Incident Task 引導使用既有 Incident Reassign。
- Delegation pending、循序加簽、申請人補件拒絕。
- 非 RUNNING 流程拒絕。
- 不允許改派給自己或相同帳號。

## 20. 結論

「流程簽核改派」應建立在流程監控的精確 active Task 上，由專用管理權限執行，且與使用者自行轉派、工作代理及 Incident Reassign 清楚分離。第一版支援一般 assignee、candidate、`ALL` 及目前 active 的 `SEQUENTIAL` Task；代理、加簽、補件及 Incident 使用既有專用語意或明確拒絕。

此功能的核心不是單純呼叫 Flowable `setAssignee`，而是確保權限、Tenant、流程版本、Task 狀態、多人模式、併發、Snapshot、Action、通知及 SLA 都能留下可追溯且不可變的企業稽核證據。
