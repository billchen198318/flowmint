# FlowMint 正式會簽配置與實作指南

## 1. 文件目的

本文件說明如何使用 FlowMint **目前已實作**的能力，設計、發布及驗收正式會簽流程。內容涵蓋產品語意、Approval Group、BPMN User Task、Task Policy、Assignment Rule、Resolver Preview、發布驗證、Flowable Runtime、權限、稽核、異常處理及測試案例。

本文件所稱「正式會簽」是：同一個 BPMN User Task 解析出多位正式簽核人，每位簽核人都有自己的待辦及核決責任，全部完成後流程才離開該 User Task。

## 2. 先釐清三種多人處理模式

FlowMint 的 `assignmentMode` 有三種容易混淆的多人模式：

| 模式 | 畫面名稱 | Runtime 語意 | 是否正式會簽 |
|---|---|---|---|
| `CANDIDATE` | 候選人承接 | 多人看見同一張候選 Task，其中一人完成即可 | 否 |
| `ALL` | 全員會簽 | 每位解析結果各有一張平行 Task，全員完成才離開節點 | 是 |
| `SEQUENTIAL` | 依序簽核 | 依解析順序逐一建立 Task，前一人完成才輪到下一人 | 屬多人正式簽核，但不是平行會簽 |

另外還有 Runtime「循序加簽」及規劃中的「平行加簽」。這兩者完成後都回到原簽核人，由原簽核人核決，不等同本文件的正式會簽。

## 3. 正式會簽的 BPMN 模型

### 3.1 BPMN 只拉一個 User Task

假設採購流程需要財務、法務及資訊安全共同核決，設計圖可以是：

```text
申請
  ↓
部門主管
  ↓
跨部門正式會簽（User Task，ALL）
  ↓
總經理
  ↓
結束
```

不需要為每位會簽人各畫一個 User Task，也不需要自行畫三條 Parallel Gateway 分支。FlowMint 會在發布時把 `ALL` User Task 轉為 Flowable parallel multi-instance。

### 3.2 Runtime 展開結果

若該節點解析出三個帳號：

```text
fm_finance
fm_legal
fm_security
```

Runtime 會形成：

```text
                     ┌─ fm_finance 的 Task ──完成─┐
進入正式會簽 User Task ├─ fm_legal 的 Task ─────完成─┼→ 全部完成 → 下一節點
                     └─ fm_security 的 Task ───完成─┘
```

三張 Task 具有相同 BPMN `taskDefinitionKey`，但各自有不同 Flowable Task ID 及 assignee。任一人完成自己的 Task，不會讓另外兩人的 Task 消失，也不會讓流程提前離開節點。

## 4. 建議配置方式：Approval Group

固定跨部門成員的正式會簽，建議先建立 Approval Group，再由流程的 Assignment Rule 引用。這比在每個流程版本重複選擇固定帳號容易治理。

### 4.1 建立群組

進入簽核群組 Program `FM_PROG003D0001`：

1. 選擇正確 Tenant。
2. 新增簽核群組。
3. 設定不可變的群組代碼，例如 `PURCHASE_CROSS_REVIEW`。
4. 輸入群組名稱，例如「採購跨部門會簽」。
5. 「處理方式」選擇「全員都要處理」，資料值為 `ALL`。
6. 狀態設為 `ACTIVE`。
7. 儲存群組。
8. 加入所有正式會簽成員，並設定有效期間及優先順序。

### 4.2 群組成員要求

每位成員必須同時符合：

- 與流程相同 Tenant。
- 對應有效 FlowMint Employee。
- 具有 QIFU4 登入帳號。
- 具有有效 Tenant membership。
- 員工、群組成員及有效期間在 Task 建立當下皆有效。

群組名稱只是顯示文字；流程關聯使用不可變的 Approval Group ID／code，不能使用可能被修改的名稱作為關聯鍵。

### 4.3 群組變更的 Runtime 邊界

流程版本固定保存 Assignment Rule 及所引用的群組識別。實際進入 User Task 時，Resolver 會取得當下有效的群組與成員，並將實際解析結果保存為 Assignment Snapshot。因此：

- 修改群組不會改寫已經建立的會簽 Task 或歷史快照。
- 尚未進入該節點的流程，未來到達節點時會使用當下有效成員。
- 正式環境調整群組成員應走受控變更流程，並評估仍在執行但尚未到達會簽節點的流程。

## 5. 在 BPMN 流程中建立會簽 User Task

進入流程設計 Program `FM_PROG004D0001`：

1. 開啟流程的 `DRAFT` 版本；已發布版本不可直接修改。
2. 在 BPMN Designer 拉入一個 User Task。
3. 設定清楚且穩定的節點 ID，例如 `crossDepartmentReview`。
4. 設定節點名稱，例如「跨部門正式會簽」。
5. 將前一節點的 Sequence Flow 接入該 User Task。
6. 將該 User Task 接到下一節點。
7. 不要在 Designer 手動加入 Flowable multi-instance collection、element variable 或 Assignment Listener；這些由 FlowMint 發布程序受控產生。

節點 ID 發布後會成為 `taskDefinitionKey`，Task Policy、Assignment Rule、快照、歷程及報表都依賴它。建立新版本時應保留語意相同節點的 ID，避免無必要地切斷跨版本分析。

## 6. 設定 Task Policy

選取會簽 User Task，在右側 Task Policy 設定：

### 6.1 必要設定

| 設定 | 正式會簽建議值 | 說明 |
|---|---|---|
| 派送方式 | `ALL`／全員會簽 | 使 Runtime 建立 parallel multi-instance |
| 自簽政策 | 依公司治理決定 | 申請人同時是會簽成員時的處理方式 |
| 重複簽核政策 | 依流程治理決定 | 同帳號由多條規則命中或曾在前關核准時的處理方式 |
| 意見必填 | `ALWAYS` 或 `ON_REJECT_RETURN` | 正式審查通常建議 `ALWAYS` |
| 處理期限 | 依 SLA 設定 | 1～8760 小時；目前以曆時小時計算 |
| 提前提醒 | 小於處理期限 | 未設定處理期限時不可設定提醒 |

### 6.2 動作政策

依流程治理決定是否允許：

- 駁回。
- 退回。
- 轉派。
- 循序加簽。

多人會簽的駁回／退回語意必須在正式上線前以實際 Flowable E2E 驗證。若公司規定任何一位不同意就終止整案，BPMN、Task action 與流程終止政策必須一致；不能只靠畫面文字表達。

### 6.3 欄位政策

透過節點表單欄位政策設定 `HIDDEN`、`READ` 或 `EDIT`。正式會簽通常建議業務資料唯讀，只開放明確需要補充的欄位；後端會再次驗證欄位變更，不能只依賴 Form.io disabled 狀態。

如果附件在此關卡不可修改，應設定為唯讀。前端為顯示檔名、大小與下載 URL 所建立的 Form.io File 物件，後端會正規化為正式附件 ID 比較；同一附件不應被誤判為修改。

## 7. 設定 Assignment Rule

每個正式會簽 User Task 至少需要一條 `ACTIVE` Assignment Rule。沒有啟用規則，或所有規則都無法解析出帳號，Runtime 不能建立會簽。

### 7.1 使用 Approval Group

在「簽核人規則」設定：

1. 解析方式選擇「簽核群組」，資料值為 `APPROVAL_GROUP`。
2. 選擇前面建立且模式為 `ALL` 的群組。
3. 設定「最多結果數」，確保上限不小於預期有效成員數。
4. 狀態設為 `ACTIVE`。
5. 儲存草稿。

發布驗證會要求：

```text
User Task assignmentMode = ALL
Approval Group assignmentMode = ALL
```

若群組是 `CANDIDATE` 或 `SEQUENTIAL`，發布會被拒絕，不會悄悄降級成其他語意。

### 7.2 使用固定帳號

解析方式也可選擇 `FIXED_ACCOUNT`，按住 Ctrl 選取多個帳號，再將 Task Policy 設為 `ALL`。這適合極少數、真正固定且只在單一流程使用的人員。

長期使用、跨流程共用或需要業務管理員維護成員時，仍建議 Approval Group。

### 7.3 使用其他多人 Resolver

`MANAGER_CHAIN`、`LEVEL_HEAD_CHAIN`、`ORG_TITLE`、`ORG_DUTY`、`APPROVAL_AUTHORITY` 或多條 Assignment Rule 也可能解析出多位帳號。FlowMint 會依規則順序執行，合併全部成功解析結果，使用 `LinkedHashSet` 去重並保留首次出現順序。

需要注意：

- 每一條啟用規則都必須成功解析；不能假設其中一條失敗會自動忽略。
- 合併後至少要有一個有效帳號。
- `maxResults` 不應誤截斷必要會簽人。
- 多條規則合併時 Assignment Snapshot 的 resolver type 會記為 `COMPOSITE`，並保存每條規則的解析路徑。

## 8. Resolver Preview

發布前應使用流程設計器的 Resolver Preview：

1. 選擇測試申請人。
2. 若 Resolver 依賴表單條件，填入相符的測試表單變數。
3. 執行 Preview。
4. 確認會簽 User Task 解析出所有預期帳號。
5. 檢查解析路徑、群組、組織或核決條件是否符合預期。
6. 使用至少兩種申請人／組織情境測試，避免只對管理員帳號成立。

Preview 與 Runtime 共用 Resolver 核心，但 Preview 仍不能取代正式發布後的 MariaDB／Flowable 多帳號 E2E。

## 9. 發布流程

### 9.1 發布前檢查

- BPMN XML 合法，User Task ID 不重複。
- 每個 User Task 都有 Task Policy。
- 會簽節點的派送方式為 `ALL`。
- 至少一條啟用 Assignment Rule 對應該節點。
- Approval Group 存在、啟用、有有效成員且模式為 `ALL`。
- Resolver config 是合法 JSON，必要識別欄位存在。
- 綁定表單已發布，欄位政策只引用有效欄位。
- 自簽、重複簽核、退回、駁回及 SLA 政策已明確決定。

### 9.2 必須透過正式 Publish

不得只用 SQL 把流程版本狀態改成 `PUBLISHED`。必須透過 FlowMint `FmProcessDefLogicServiceImpl.publish()` 對應的正式發布功能，因為發布過程會：

1. 執行 BPMN、Task Policy、Assignment Rule、表單及群組一致性驗證。
2. 讀取原始 BPMN XML。
3. 為 User Task 注入 `${fmTaskAssignmentListener}` create listener。
4. 對 `ALL` 建立 `MultiInstanceLoopCharacteristics`。
5. 設定 collection expression：

```text
${fmTaskAssignmentListener.multiInstanceAccounts(execution, 'taskDefinitionKey')}
```

6. 設定 element variable：

```text
flowmintAssignee
```

7. 設定 `sequential=false`，形成 parallel multi-instance。
8. 將 Runtime BPMN 部署到 Flowable，並保存發布版本及 deployment 關聯。

原始設計 BPMN 保持可讀且不需要手寫 FlowMint Listener；Runtime BPMN 由發布程序產生。

## 10. Runtime 內部流程

流程 token 進入 `ALL` User Task 時：

1. Flowable 評估 `multiInstanceAccounts(...)`。
2. Listener 從流程變數取得 Tenant、process definition、固定版本號、申請人、主要組織、form data ID 與表單資料。
3. 依該流程實例固定版本讀取 Task Policy 及所有 `ACTIVE` Assignment Rule。
4. Resolver 逐條解析帳號；任一規則失敗即視為整體解析失敗。
5. 使用有順序的 Set 合併及去重帳號。
6. Flowable 依帳號數建立 parallel multi-instance executions 及 User Tasks。
7. 每張 Task 的 `flowmintAssignee` 必須存在於解析結果，Listener 才設定 assignee。
8. 系統建立 Assignment Snapshot、due date 及 Task Assigned 通知。
9. 每位會簽人完成自己的 Task。
10. Flowable 等待所有 instance 完成後才離開 User Task。

FlowMint 沒有設定「完成百分比」或「一人完成即通過」的 completion condition；`ALL` 的核心語意就是全部 instance 完成。

## 11. 會簽人的操作與權限

每位會簽人登入後：

- 在我的待辦看到自己的 Task。
- 只能操作自己被指派或依法可處理的 Task。
- 可查看發布版 Form.io 表單、送單資料、正式附件、Task Policy、流程進度及歷次動作。
- 可依政策核准、駁回、退回、轉派或循序加簽。
- 每次正式動作建立不可變表單快照及 `fm_task_action`。
- 附件下載會重新檢查 Tenant、流程／Task 與操作者權限。

只知道其他人的 Task ID 不足以載入或操作該 Task；後端會從 Spring Security Context 取得操作者並重新驗證。

## 12. 自簽、重複人員與代理

### 12.1 自簽政策

如果申請人也被 Resolver 解析為會簽人，依 Task Policy 處理：

- `ALLOW`：保留申請人的正式會簽 Task。
- `SKIP_TO_NEXT`：略過並繼續處理其他解析結果。
- `REQUIRE_ALTERNATE`：必須解析出替代人，否則失敗。
- `INCIDENT`：建立 Assignment Incident，交由營運處理。

實際語意需以目前 Resolver 實作及目標流程 E2E 確認，不能只看選項名稱推測複雜主管鏈結果。

### 12.2 重複簽核政策

- `KEEP_EACH_LEVEL`：不同節點仍保留同一人的核決責任。
- `MERGE_CONSECUTIVE`：合併連續重複簽核人。
- `SKIP_ALREADY_APPROVED`：略過已在前面核准的人員。

同一會簽節點內，多條規則解析到同帳號會先去重，不會為同一帳號建立兩張平行 Task。

### 12.3 工作代理

工作代理和 Approval Group 成員是兩個不同概念。群組定義原始核決責任人；有效代理授權負責在 Runtime 將可處理權交給代理人。代理範圍、原 owner、實際操作者及 Action 必須保留稽核。

## 13. 失敗與 Incident

下列情況應在發布時提早拒絕，或在 Runtime 建立／呈現明確異常：

- 沒有 Task Policy。
- 派送方式不是 `ALL`。
- 沒有啟用 Assignment Rule。
- Approval Group 不存在或停用。
- 群組模式與 Task Policy 不一致。
- 群組沒有當下有效成員。
- 員工或 Tenant membership 無效。
- Resolver config 格式錯誤。
- Resolver 沒有解析出帳號。
- Multi-instance 的 `flowmintAssignee` 不在受控解析結果。

Resolver 失敗不得把 `ALL` 降級成 `CANDIDATE` 或單一 assignee。Assignment Incident 應保存流程、Task、節點、錯誤碼、訊息與解析 context，營運人員再以 Retry、Reassign 或 Terminate 受控處理。

## 14. 申請追蹤與 BPMN 顯示

正式會簽進行時，申請詳情應：

- 將 BPMN 會簽 User Task 標示為目前進行中節點。
- 在目前簽核摘要列出該節點的所有 active assignee／candidate。
- 每位成員完成後，歷程新增其獨立 Action。
- 仍有任一平行 Task 未完成時，BPMN 不應把該 User Task 標為完成。
- 最後一位完成後，節點轉為已完成並標示下一個 active User Task。

BPMN 圖仍只有一個 User Task 圖形；多位會簽人是該節點的 multi-instance，不需要在圖上複製多個節點。

## 15. 完整配置範例

### 15.1 需求

所有資訊設備請購都要由資訊、資安及財務三人共同核決，全部處理後才交總經理。

### 15.2 Approval Group

```text
Group Code: IT_PURCHASE_JOINT_REVIEW
Group Name: 資訊設備共同會簽
Assignment Mode: ALL
Status: ACTIVE
Members:
  fm_it
  fm_security
  fm_finance
```

### 15.3 BPMN

```text
departmentApproval
  ↓
itPurchaseJointReview
  ↓
generalManagerApproval
```

### 15.4 Task Policy

```text
taskDefKey: itPurchaseJointReview
assignmentMode: ALL
selfApprovalPolicy: INCIDENT
duplicatePolicy: KEEP_EACH_LEVEL
commentRequired: ALWAYS
allowReject: Y
allowReturn: Y
allowTransfer: N
allowAddSign: N
dueHours: 24
reminderBeforeHours: 4
```

### 15.5 Assignment Rule

```json
{
  "taskDefKey": "itPurchaseJointReview",
  "ruleSeq": 1,
  "resolverType": "APPROVAL_GROUP",
  "resolverConfig": {
    "approvalGroupId": "IT_PURCHASE_JOINT_REVIEW"
  },
  "maxResults": 10,
  "status": "ACTIVE"
}
```

實際資料關聯應使用系統保存的 Approval Group 識別值；上例以可讀代碼說明，不代表可繞過畫面或正式 API 直接寫入資料庫。

## 16. 多帳號 E2E 驗收腳本

### 16.1 基本成功案例

1. 建立三人 `ALL` Approval Group。
2. 建立 `ALL` User Task 並引用該群組。
3. Resolver Preview 確認三個帳號。
4. 透過正式功能發布流程新版本。
5. 以申請人起單並使流程進入會簽節點。
6. MariaDB／Flowable 確認同一節點有三張 active Task。
7. 三位會簽人分別登入，確認只看到自己的待辦。
8. 第一人核准，確認流程仍停留在會簽節點。
9. 第二人核准，確認流程仍停留在會簽節點。
10. 第三人核准，確認會簽節點完成並建立下一關 Task。
11. 申請詳情確認目前簽核人、Action 時間軸及 BPMN 標色正確。
12. 驗證三人的表單快照、Assignment Snapshot、附件顯示與下載。

### 16.2 必要失敗案例

- Task Policy `ALL` 引用 `CANDIDATE` 群組，發布必須拒絕。
- 群組停用或沒有有效成員，發布或 Runtime 必須明確失敗。
- 同帳號由兩條規則命中，只建立一張 Task。
- 非會簽人以已知 Task ID 載入或核准，後端拒絕。
- 跨 Tenant 帳號、停用員工及失效 membership 不得成為簽核人。
- 第一位核准後不得提前建立下一關 Task。
- 兩位使用者同時完成最後兩張 Task，流程只能離開節點一次。
- 會簽進行中重啟後端後，active Task、流程 token 及進度仍正確。

### 16.3 政策案例

- 申請人也是群組成員時，逐一驗證四種自簽政策。
- 同一人已在前一關核准時，逐一驗證三種重複簽核政策。
- 驗證駁回、退回、轉派、代理、循序加簽與 SLA 通知在 `ALL` 節點的實際結果。
- 驗證有附件與無附件表單都能正常進入及完成會簽。

## 17. 表單讓申請人選擇會簽人的擴充方案

### 17.1 目前狀態

FlowMint 目前沒有正式的 `FORM_ACCOUNT_FIELD` Resolver。雖然表單可以建立人員選擇欄位，但不能只靠 Vue 把任意帳號直接塞入 Flowable multi-instance collection；這會繞過 Tenant、員工、membership、版本、上限及稽核驗證。

因此下列設定目前屬規劃，不可在文件或驗收報告標示為已支援：

```text
表單選擇會簽人
→ FORM_ACCOUNT_FIELD Resolver
→ 後端驗證帳號陣列
→ ALL User Task
```

### 17.2 建議資料格式

表單欄位例如：

```json
{
  "countersignAccounts": [
    "fm00830",
    "fm00800",
    "fm00800e01"
  ]
}
```

建議 Resolver config：

```json
{
  "fieldPath": "form.countersignAccounts",
  "minResults": 1,
  "maxResults": 10,
  "allowApplicant": false
}
```

### 17.3 必要後端防線

未來實作必須：

- 發布時確認 `fieldPath` 存在於綁定的已發布表單。
- 限定欄位型別為受控人員選擇或帳號陣列。
- Runtime 只接受字串帳號陣列並去重。
- 驗證同 Tenant Employee、QIFU4 Account 及有效 membership。
- 驗證最少／最多人數及是否允許申請人本人。
- 防止跨 Tenant、任意 JSON object、URL 或顯示名稱被當成帳號。
- 保存原表單值、正規化帳號及 Resolver 路徑到 Assignment Snapshot。
- 起單後依欄位政策鎖定選人欄位，防止後續關卡任意替換正式會簽人。
- Preview 與 Runtime 使用同一套 Resolver 驗證。

此擴充完成後仍應使用 BPMN `ALL` User Task；差別只是簽核人來源由固定群組改為已驗證的表單欄位。

## 18. 不建議的做法

- 不要為每位固定會簽人各畫一條平行 BPMN 分支，除非各分支確實有不同後續流程。
- 不要把 `CANDIDATE` 當作全員會簽；它只需要一人完成。
- 不要在資料庫直接把草稿狀態改為已發布。
- 不要手寫 Flowable assignee expression 繞過 FlowMint Resolver。
- 不要從 Vue 直接提交未驗證帳號作為 multi-instance collection。
- 不要在已發布版本直接修改 Task Policy、Assignment Rule 或 BPMN XML。
- 不要因 Resolver 失敗就降級成單一簽核人或管理員帳號。
- 不要只測第一位會簽人能否核准；真正關鍵是最後一位完成前流程不得前進。

## 19. 結論

FlowMint 已能使用一個 BPMN User Task、`ALL` Task Policy 及多人 Assignment Rule 實作正式全員會簽。固定跨部門成員以 `ALL` Approval Group 最容易配置及治理；發布程序會受控產生 Flowable parallel multi-instance，Runtime 再依固定流程版本解析、去重、指派、通知及保存快照。

「申請人在表單選擇會簽人」是合理的下一階段能力，但必須新增受控 `FORM_ACCOUNT_FIELD` Resolver，不能直接把前端 User ID 塞入 Flowable。完成該 Resolver 之前，正式環境應使用 Approval Group、固定帳號或現有組織 Resolver 建立會簽人名單。
