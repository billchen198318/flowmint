# 使用 FM_PROG006D0002 說明

## 1. 功能用途

`FM_PROG006D0002` 是 FlowMint 的版本化 Data Action 設計程式，用來將受控 SQL 封裝成可供 FlowMint、Form.io 或其他前端功能呼叫的共用 API。

主要使用流程如下：

```text
建立 DataSource Pool
  → 建立 Data Action 草稿
  → 設定 Request Mapping
  → 建立一個或多個 SQL Step
  → Preview 測試
  → 發布版本
  → 透過正式 Execute API 呼叫
```

Data Action 並不是讓呼叫端直接傳入 SQL。SQL 由管理者預先設計並發布；呼叫端只能傳入定義好的業務參數，藉此降低任意 SQL、字串拼接和跨 Tenant 存取的風險。

## 2. 使用前準備

### 2.1 建立 DataSource Pool

先在 `FM_PROG006D0001` 建立目標資料庫的 DataSource Pool，並完成連線測試。第一版支援：

- MariaDB
- Oracle
- Microsoft SQL Server

DataSource Pool 至少需要設定：

- Tenant
- Pool Code 與名稱
- 資料庫類型
- JDBC URL
- 資料庫帳號與密碼
- HikariCP 連線數與 Timeout
- 驗證 SQL
- 啟用狀態

只有同 Tenant、狀態有效的 Pool 才能在 Data Action 畫面選取。

### 2.2 建立資料表與註冊程式

環境必須套用 `flowmint.sql` 內的 Data Action／DataSource Pool 資料表與 Program 定義。`doc`
不再提供獨立 Program register SQL；既有環境差異必須由正式 migration 或 QIFU4 管理功能處理。

註冊 SQL 只建立 `tb_sys_prog` 程式資料，不會自動配置角色權限。如系統有啟用程式角色控制，仍需由管理者配置使用權限。

### 2.3 Tenant membership

正式 API 會取得目前登入帳號，並檢查該帳號是否為 `X-FlowMint-Tenant` 指定 Tenant 的有效成員。帳號不屬於該 Tenant，或 membership 並非 `ACTIVE`，均不能執行。

## 3. 進入程式

Query 頁面路由：

```text
#/fm_prog006d0002
```

程式包含：

- `FM_PROG006D0002Q`：查詢
- `FM_PROG006D0002A`：新增
- `FM_PROG006D0002E`：編輯、Preview 與發布

Query 頁可依 Tenant、Action Code、名稱或狀態尋找既有 Data Action，再進入 Edit 頁維護草稿版本。

## 4. 建立 Data Action

### 4.1 基本欄位

| 欄位 | 說明 |
|---|---|
| Tenant | Data Action 所屬 Tenant；建立後不可更換 |
| Action Code | 正式 API 使用的穩定代碼；建立後不可更換 |
| Action 名稱 | 顯示給設計者看的名稱 |
| DataSource Pool | SQL 實際執行的資料庫連線池 |
| Action Type | `QUERY`、`COMMAND` 或 `TRANSACTION` |
| 已發布版本 | 目前正式 API 預設執行的版本 |
| 目前草稿 | 現在可修改、Preview 與發布的版本 |
| Request JSON Path Mapping | 將 Request Body 欄位映射成 SQL Named Parameter |
| 說明 | Action 用途、呼叫時機或注意事項 |

### 4.2 Action Type

#### QUERY

只用於讀取資料，SQL Step 只能選擇：

- `SELECT_ONE`
- `SELECT_LIST`

若 QUERY Action 包含 `INSERT`、`UPDATE` 或 `DELETE`，儲存或發布檢查會拒絕。

#### COMMAND

用於新增、修改或刪除資料，通常使用：

- `INSERT`
- `UPDATE`
- `DELETE`

#### TRANSACTION

用於多個 SQL Step 必須共同成功的情境。所有 Step 依執行順序使用同一 DataSource Transaction；任一 Step 發生錯誤，整個 Action 回滾。

## 5. Request JSON Path Mapping

Request Mapping 是一個 JSON Object，Key 是 SQL 參數名稱，Value 是 Request Body 的 JSON Path。

例如：

```json
{
  "employeeNo": "$.employeeNo",
  "amount": "$.formData.amount",
  "reason": "$.formData.reason"
}
```

呼叫端傳入：

```json
{
  "employeeNo": "E001",
  "formData": {
    "amount": 1500,
    "reason": "購買辦公用品"
  }
}
```

SQL 即可使用：

```text
:employeeNo
:amount
:reason
```

目前 JSON Path 支援從 `$` 開始的物件欄位路徑，例如 `$.formData.amount`。第一版不支援陣列索引、filter 或複雜 JSONPath expression。找不到路徑時，對應參數值為 `null`。

如果 Request Mapping 留空，系統會將 Request Body 第一層欄位直接當作 SQL 參數。

### 5.1 Server Context 參數

系統會在 Server 端固定加入：

| 參數 | 內容 |
|---|---|
| `:tenantId` | 經過 membership 驗證的 Tenant ID |
| `:loginAccount` | 目前登入帳號 |
| `:now` | 伺服器目前時間 |

這些值不接受 Request Body 覆蓋。SQL 應優先使用 `:tenantId` 建立 Tenant 條件，不要相信呼叫端自行傳入的 Tenant ID。

## 6. 設定 SQL Step

一個 Data Action 至少要有一個 SQL Step。多個 Step 依「順序」由小到大執行。

| 欄位 | 說明 |
|---|---|
| 順序 | Step 執行順序，建議使用 `10`、`20`、`30`，方便日後插入 |
| Step Code | Step 的穩定識別代碼 |
| Step 名稱 | 顯示名稱 |
| Statement | SQL 操作類型 |
| Execution Mode | 第一版只有 `ONCE` |
| SQL | 單一 Named Parameter SQL |
| Result Key | 此 Step 在整體回應中的欄位名稱 |
| Result Mode | `OBJECT`、`LIST`、`AFFECTED_ROWS` 或 `NONE` |
| 預期異動筆數 | 實際筆數不符時視為錯誤並回滾 |
| Timeout 秒數 | 此 Step 的 Query Timeout |
| 最大回傳筆數 | 限制 SELECT 回傳資料量；未設定時預設 1000 |

### 6.1 Statement 與 Result Mode 建議搭配

| Statement | 用途 | 建議 Result Mode |
|---|---|---|
| `SELECT_ONE` | 查詢零或一筆資料 | `OBJECT` |
| `SELECT_LIST` | 查詢多筆資料 | `LIST` |
| `INSERT` | 新增資料 | `AFFECTED_ROWS` |
| `UPDATE` | 修改資料 | `AFFECTED_ROWS` |
| `DELETE` | 刪除資料 | `AFFECTED_ROWS` |
| 任一 Statement | 不需輸出該 Step 結果 | `NONE` |

不同 Step 的 Result Key 不應重複。例如：

```text
employee
assignments
updatedRows
```

## 7. 完整查詢範例

以下建立 `GET_EMPLOYEE`，依員工編號查詢員工。

### 7.1 Data Action

| 欄位 | 範例值 |
|---|---|
| Tenant | `T001` |
| Action Code | `GET_EMPLOYEE` |
| Action 名稱 | 查詢員工 |
| DataSource Pool | 選擇已測試成功的 Pool |
| Action Type | `QUERY` |

Request Mapping：

```json
{
  "employeeNo": "$.employeeNo"
}
```

### 7.2 SQL Step

| 欄位 | 範例值 |
|---|---|
| 順序 | `10` |
| Step Code | `FIND_EMPLOYEE` |
| Step 名稱 | 查詢員工資料 |
| Statement | `SELECT_ONE` |
| Execution Mode | `ONCE` |
| Result Key | `employee` |
| Result Mode | `OBJECT` |
| Timeout 秒數 | `10` |
| 最大回傳筆數 | `1` |

SQL：

```sql
SELECT EMPLOYEE_NO,
       DISPLAY_NAME,
       EMAIL,
       STATUS
  FROM fm_employee
 WHERE TENANT_ID = :tenantId
   AND EMPLOYEE_NO = :employeeNo
```

SQL 最後不要加分號。

### 7.3 Preview Body

```json
{
  "employeeNo": "E001"
}
```

結果會依 Result Key 組裝，概念如下：

```json
{
  "employee": {
    "EMPLOYEE_NO": "E001",
    "DISPLAY_NAME": "王小明",
    "EMAIL": "user@example.com",
    "STATUS": "ACTIVE"
  }
}
```

實際 HTTP 回應外層仍會使用 QIFU4／FlowMint 的標準 Controller Result 封裝。

## 8. 完整異動範例

以下建立 `UPDATE_EMPLOYEE_EMAIL`，更新同 Tenant 員工 Email。

### 8.1 Data Action

```text
Action Code：UPDATE_EMPLOYEE_EMAIL
Action Type：COMMAND
```

Request Mapping：

```json
{
  "employeeNo": "$.employeeNo",
  "email": "$.email"
}
```

SQL Step：

```text
Statement：UPDATE
Result Key：updatedRows
Result Mode：AFFECTED_ROWS
預期異動筆數：1
```

SQL：

```sql
UPDATE fm_employee
   SET EMAIL = :email,
       UUSERID = :loginAccount,
       UDATE = :now
 WHERE TENANT_ID = :tenantId
   AND EMPLOYEE_NO = :employeeNo
```

Preview Body：

```json
{
  "employeeNo": "E001",
  "email": "new-address@example.com"
}
```

若 SQL 實際更新筆數不是 1，系統會將這次執行視為失敗並回滾。這可避免條件錯誤時更新零筆或意外更新多筆。

## 9. 儲存、Preview 與發布

### 9.1 儲存草稿

按「儲存草稿」保存目前設定。新增完成後進入 Edit 頁，才會出現 Preview 與發布功能。

儲存草稿不會改變正式 API 正在使用的已發布版本。

### 9.2 Preview

在 Edit 頁的「測試 JSON Body」輸入 JSON，按「執行 Preview」。

Preview 特性：

- 執行目前草稿版本。
- 使用實際選定的 DataSource Pool。
- 預設強制 Rollback。
- 可測試 SELECT 與異動 SQL。
- 顯示每個 Result Key 組裝後的結果。

雖然異動 Preview 預設 Rollback，仍建議連接測試資料庫，避免資料庫本身的非交易行為或特殊 Procedure 造成不可預期影響。

### 9.3 發布版本

確認 Preview 正確後按「發布版本」。發布時系統會：

- 驗證 Action、Request Mapping 與所有 SQL Step。
- 正規化內容並計算 SHA-256。
- 將草稿狀態改為 Published。
- 鎖定該版本內容。
- 將其設為目前正式版本。

已發布版本不能直接修改。後續調整會建立新的草稿版本；新草稿發布前，正式 API 仍執行舊的 Published 版本。

## 10. 正式 Execute API

### 10.1 執行目前發布版本

```http
POST /api/fm/data-actions/GET_EMPLOYEE/execute
X-FlowMint-Tenant: T001
Content-Type: application/json
```

Request Body：

```json
{
  "employeeNo": "E001"
}
```

### 10.2 指定已發布版本

需要固定呼叫特定版本時，加上：

```http
X-FlowMint-Action-Version: 1
```

若不提供此 Header，系統使用目前發布版本。

正式 Execute API 只允許執行 Published 版本，不能直接執行 Draft。

### 10.3 查詢可用 Action

```http
POST /api/fm/data-actions/options
X-FlowMint-Tenant: T001
```

此 API 可供前端取得同 Tenant 已發布的 Data Action 選項。

### 10.4 取得 Metadata

```http
POST /api/fm/data-actions/GET_EMPLOYEE/metadata
X-FlowMint-Tenant: T001
```

Metadata 可供前端或 Form.io 整合時讀取 Action 的參數與版本資訊。

## 11. SQL 安全限制

目前每個 Step 只允許一段 Named Parameter SQL，例如：

```sql
WHERE EMPLOYEE_NO = :employeeNo
```

禁止：

- SQL 結尾分號。
- 一個 Step 內放多段 SQL。
- `--` SQL comment。
- `/* ... */` SQL comment。
- `${employeeNo}` 文字替換。
- 使用 Request Mapping 與 Server Context 均未定義的 Named Parameter。
- QUERY Action 內使用異動 Statement。

不要這樣寫：

```sql
WHERE EMPLOYEE_NO = '${employeeNo}'
```

應寫成：

```sql
WHERE EMPLOYEE_NO = :employeeNo
```

Named Parameter 會以 JDBC 參數方式綁定，不應自行加引號或拼接字串。

## 12. 交易與錯誤處理

- 同一 Action 的所有 Step 使用同一 DataSource。
- Step 依 execution order 執行。
- 任一 Step 發生 SQL 錯誤，整個 Action 回滾。
- 預期異動筆數不符，整個 Action 回滾。
- SELECT 超過最大回傳筆數時視為錯誤，不會靜默截斷成看似成功。
- Query Timeout 應依 SQL 複雜度設定，不建議無限制等待。
- 正式執行前會確認 Action 與版本已發布。
- 正式 API 會檢查登入帳號的 Tenant membership。

## 13. 常見問題

### DataSource Pool 下拉沒有資料

檢查：

1. Pool 是否屬於目前選取的 Tenant。
2. Pool 是否啟用。
3. `FM_PROG006D0001` 是否已成功儲存。
4. 登入帳號是否有該 Tenant 的管理範圍。

### Preview 按鈕不能按

Preview 只在 Edit 頁且存在草稿版本時啟用。請先儲存草稿；若目前只有已發布版本，先修改並儲存以建立新草稿。

### 顯示未定義 Named Parameter

例如 SQL 使用 `:employeeNo`，Request Mapping 必須包含：

```json
{
  "employeeNo": "$.employeeNo"
}
```

`tenantId`、`loginAccount`、`now` 除外，這三個由 Server Context 提供。

### Preview 有資料，正式 API 無法執行

檢查：

1. 草稿是否已發布。
2. API 使用的 Action Code 是否正確。
3. `X-FlowMint-Tenant` 是否正確。
4. 登入帳號是否為該 Tenant 的有效成員。
5. 指定的 `X-FlowMint-Action-Version` 是否為 Published 版本。

### UPDATE 回報異動筆數不符

檢查 Tenant 與業務條件是否能唯一找到資料。如果允許零筆更新，不要設定預期異動筆數為 1；但涉及唯一業務資料的更新，建議保留 1，以便及早發現條件或資料問題。

### SQL 可以使用資料庫特有語法嗎

可以使用所選 DataSource 對應資料庫可接受的單一 SQL，但 Action 會因此與該資料庫綁定。若同一 Action 需要跨 MariaDB、Oracle、MSSQL 使用，應避開各資料庫特有語法或分別建立 Action。

## 14. 第一版尚未支援

目前尚未實作：

- Execution Audit 程式已完成；本機 `flowmint` MariaDB 已套用當時的一次性 migration，完整結構已併入 `flowmint.sql`。其他部署環境仍必須各自套用正式 migration。
- Form.io 視覺化 Request／Response Binding 已支援；Metadata 可提供 Result Key、Generated Key、Batch 與分頁等已知巢狀路徑及類型候選。SQL 查詢的自訂回傳欄位仍可手動輸入。
- 複雜 JSONPath expression。

`FOR_EACH`／JDBC Batch、Insert Generated Key、前一步結果引用及進階 Continue Condition 已完成程式實作。Continue Condition 支援 `${request...}`、`${steps...}`、存在判斷、`==`、`!=`、`>`、`>=`、`<`、`<=`、`&&`、`||`，值類型包含數值、ISO 日期時間、布林、字串與 `null`；`&&` 優先於 `||`，目前不支援括號。前一步結果與目前項目必須在 Request Mapping 使用 `${steps.<resultKey>...}`、`${item...}` 定義成 SQL Named Parameter。正式上線前仍須以 MariaDB、Oracle、MSSQL 實際 Driver 驗收 Generated Key 與 Batch 行為。

套用 Execution Audit migration 後，回傳的 `executionId` 可對應 `fm_data_action_execution_audit.EXECUTION_ID`。稽核只保存執行中繼資料，不保存完整 Request／Response。

`FM_PROG006D0002` 查詢頁右上方的「執行紀錄」可依 Tenant、Execution ID、Action Code、帳號及成功／失敗狀態查詢。查詢 API 會再次檢查登入者的 Tenant membership。

Data Action 預設依 `Tenant + Action + 登入帳號` 限制每分鐘 60 次，Preview 與正式 Execute 都會計算。部署時可用 `FM_DATA_ACTION_RATE_LIMIT_PER_MINUTE` 調整全域門檻。

個別 Action 覆寫已完成：編輯畫面的「每分鐘呼叫上限」留空沿用全域值，填入 1～100000 則覆寫。本機 `flowmint` MariaDB 已新增欄位；一次性 migration 檔案已在執行後刪除，其他部署環境請依 `flowmint.sql` 的 `RATE_LIMIT_PER_MINUTE` 結構升級。

`SELECT_LIST` 如需分頁，Request 必須同時傳入 `page` 與 `pageSize`。Response 對應 Result Key 的內容會是 `{ items, page, pageSize, total, totalPages }`；未傳分頁參數時仍回傳原本的陣列。`pageSize` 不可超過該 Step 的 `maxRows`。

因此第一版適合：

- 固定參數查詢。
- 單筆新增、修改或刪除。
- 固定數量、依序執行的多 Step Transaction。

第一版不適合：

- 需要完整執行稽核軌跡的高風險操作。

## 15. 建議設計原則

- 一個 Action 只處理一個清楚的業務目的。
- Action Code 使用穩定且可讀的英文大寫代碼。
- 每個 SQL 都要包含必要的 `:tenantId` 條件。
- 查詢設定合理的最大回傳筆數與 Timeout。
- 單筆更新設定預期異動筆數為 1。
- Result Key 使用穩定、具業務意義的名稱。
- 先在測試資料庫 Preview，再發布至正式使用的 Pool。
- 發布前同時測試正常值、查無資料、null、邊界值與非法值。
- 不要把資料庫管理、DDL 或任意 SQL 能力包裝成公開 Data Action。
