# 36 組織人員資料檢查規劃

日期：2026-09-22  
狀態：第一版單頁即時檢查已完成；排程、通知與結果保存列為後續階段

## 1. 目的與程式定位

新增獨立程式 `FM_PROG002D0007`「組織人員資料檢查」，主動找出會使主管鏈、組織樹或代理解析不可靠的主資料，警告具權限的 IT／FlowMint 管理人員進行調整。

本功能處理的是尚未進入流程前的主資料品質問題，不等同 Runtime 的 Assignment Incident。健檢不得建立假流程、不得自動指派簽核人，也不得直接修改組織或代理資料。

### 1.1 第一版實作範圍（2026-09-22）

- 已完成 `FM_PROG002D0007Q` 單頁及 `POST /api/FM_PROG002D0007/inspect` 即時檢查 API。
- 已完成四個固定區塊、Tenant membership 驗證、問題數摘要、關鍵字篩選及既有維護程式導向。
- 第一版直接讀取目前有效主資料，不建立掃描批次或問題保存資料表。
- 第一版不包含每日排程、Workspace 主動通知、匯出、單筆重檢與 `OPEN／RESOLVED` 歷程；相關章節屬後續規劃。
- 已完成的核心檢查包含：缺少／多位／無效部門主管、無法解析／自我／循環直屬主管、重複主要任職、多根／自我／無效／循環組織樹，以及自我／雙向／循環代理。
- 表格中其餘進階規則（membership 完整性、版本重疊、代理人重疊、範圍有效性、期間合法性及禁止再代理）仍屬後續補強，不得視為第一版已完成。

## 2. 第一版檢查規則

| 代碼 | 嚴重度 | 檢查條件 | 修正入口 |
|---|---|---|---|
| `ORG_HEAD_MISSING` | `WARNING` | 有效且非虛擬的部門，在檢查基準時間找不到有效 `HEAD`；`ACTING_HEAD` 或 `DEPUTY_HEAD` 不視為已配置正式部門主管 | `FM_PROG002D0005` |
| `ORG_HEAD_MULTIPLE` | `ERROR` | 同一部門在同一時間存在兩位以上有效正式 `HEAD` | `FM_PROG002D0005` |

| `DELEGATION_SELF` | `ERROR` | 被代理人與代理人為同一帳號 | `FM_PROG003D0002` |

全部規則歸入四個 UI 區塊，並以 Tenant 時區與使用者指定的「檢查基準時間」判斷有效期間。不得以資料列存在取代有效狀態、有效期間及 Tenant 邊界檢查。`ERROR` 代表可能造成錯誤解析、循環或跨 Tenant 等結構性問題，須優先處理；`WARNING` 代表資料缺漏或高風險配置，仍須由 IT 確認與調整。

### 2.1 部門主管

- 檢查 `ROOT`、`DEPARTMENT` 等需要主管的有效組織節點；`VIRTUAL` 預設排除。
- 正式主管必須是有效 `HEAD`，並連結同 Tenant 的有效員工、帳號 membership 與有效部門任職。
- 若只有代理主管或副主管，畫面可顯示現況，但仍列出「缺正式主管」警告。
- 同時存在多位有效 `HEAD` 必須列為 `ERROR`，不可任選其中一人視為正常。
- `HEAD` 必須具有該部門的有效任職、有效員工狀態、有效 Tenant membership，且不得引用其他 Tenant。
- 主管配置的有效期間必須與部門及主管任職期間有交集；已失效主管不得使本區顯示正常。

### 2.2 員工直屬主管

- 逐筆檢查有效的主要及兼任任職；畫面必須顯示是哪一筆任職缺少主管，不能只顯示員工姓名。
- `ORG_HEAD`、`PARENT_HEAD`、`EXPLICIT` 必須依正式 Resolver 規則實際解析，不能只檢查來源欄位非空。
- `EXPLICIT` 指向自己、無效任職、其他 Tenant 或已失效主管，均視為無法解析。
- 第一版將 `NONE` 視為使用者明確表示「此任職不配置直屬主管」，因此不列缺少主管警告；組織管理者應只對最高負責人或經核准的例外使用。後續若增加最高負責人角色標記，再由後端限制一般員工使用 `NONE`。
- 最高部門的任職若設定 `PARENT_HEAD`，系統必然無法解析上級部門主管；問題說明應直接指出該部門是最高部門，並建議最高負責人改設 `NONE`，否則改用 `EXPLICIT`，不得要求 IT 自行從 UUID 或組織關係推理。
- 同一員工在相同時段只能有一筆有效 `PRIMARY` 任職；重複主要任職列為 `ERROR`。
- 使用 visited-set 沿主管任職鏈完整檢查，不只找 A → B → A，也要找 A → B → C → A 等多層循環。
- 主管鏈節點的員工、任職、帳號 membership 及 Tenant 任一無效，均列出實際失效原因。

### 2.3 部門上級與組織樹

- 每個 Tenant 在同一基準時間只能有一個最高組織節點；該節點可無父節點。
- 其他有效部門的父節點為空、父節點不存在、已失效或屬於其他 Tenant，均列警告。
- 健檢同時回傳部門代碼、名稱、目前版本與問題父節點，方便 IT 由組織樹修正。
- 自己指向自己、二層或多層父子循環均列為 `ERROR`，並顯示完整循環路徑。
- 同一 Tenant 同時存在多個無父節點的有效組織時，全部相關根節點列在同一問題組合中，不得任選一個當作合法根。
- 同一組織版本有效期間重疊，導致同一基準時間出現多種父子關係時列為 `ERROR`。

### 2.4 工作代理

設代理 A → B 為 `d1`，B → A 為 `d2`。符合下列全部條件即警告：

1. `d1`、`d2` 屬於同一 Tenant 且狀態皆為 `ACTIVE`。
2. `max(d1.EFFECTIVE_FROM, d2.EFFECTIVE_FROM) < min(d1.EFFECTIVE_TO, d2.EFFECTIVE_TO)`；邊界是否包含須與既有代理 Runtime 契約一致。
3. 代理範圍有交集，例如 `ALL` 與任何範圍、相同 Process，或相同 Approval Group。

結果以無方向的人員組合及重疊區間去重，A／B 只顯示一筆警告。若兩筆期間不重疊或範圍確定不相交，不得誤報。新增或修改代理時也應執行即時預檢並警告，但第一版仍允許具權限管理者確認後保存，避免把歷史上合法的緊急安排直接阻斷；是否改為硬性禁止另案決策。

除雙向互相代理外，本區還必須檢查：

- 被代理人與代理人相同。
- 同一被代理人在有效期間及相交範圍配置多位代理人。
- 代理關係形成 A → B → C → A 等多層循環；循環檢查只沿實際期間及範圍可同時命中的邊。
- 被代理人或代理人的員工、帳號、Tenant membership 已失效或不屬於相同 Tenant。
- `PROCESS`／`APPROVAL_GROUP` 範圍引用不存在、停用或其他 Tenant 的目標。
- 代理期間不合法，或 `ALLOW_REDELEGATE=N` 時仍形成下一層代理。

### 2.5 配置操作文件

本文件只定義資料檢查條件、問題呈現與後續處理方向。部門建立、人員任職、最高部門、最高負責人、多部門主管及四種直屬主管來源的實際設定步驟，請參閱 [37 部門人員與主管配置操作說明](37-部門人員與主管配置操作說明.md)。

## 3. 畫面與操作

本功能只有一個頁面 `FM_PROG002D0007Q`，不建立新增頁、編輯頁或第二層明細頁。進入頁面後直接以四個固定區塊呈現目前 Tenant 的檢查結果：

1. 部門主管問題。
2. 員工直屬主管問題。
3. 上級部門與組織樹問題。
4. 工作代理問題。

每個區塊的標題分別顯示 `ERROR` 與 `WARNING` 筆數，預設依嚴重度及問題代碼排序。有問題時直接展開清單；沒有問題時仍保留該區塊並顯示「檢查正常」，不可把整個區塊隱藏，以便 IT 確認四個區塊皆已執行。

### 3.1 問題說明與調整建議

每筆問題必須提供下列內容，不得只顯示錯誤代碼：

| 欄位 | 說明 |
|---|---|
| 嚴重度 | `ERROR` 或 `WARNING` |
| 問題名稱 | 使用者可理解的中文名稱 |
| 問題說明 | 哪一筆人員、任職、部門或代理設定不符合規則 |
| 可能影響 | 例如找不到簽核人、主管鏈循環、錯誤代理或流程形成 Incident |
| 判定依據 | 檢查基準時間、有效期間、關聯資料及必要的循環路徑 |
| 建議處理 | IT 應檢查及調整的資料方向，避免只顯示「請聯絡管理員」 |
| 修正入口 | 對應既有維護程式的「前往調整」按鈕 |
| 重檢操作 | 修正後重新檢查該筆或該區塊 |

建議文字由後端依問題代碼產生受控模板，前端只負責顯示，不得依自由文字猜測修正方式。建議可以指出候選處理方向，但不得自行選定主管、父部門或代理人，也不得提供會直接改寫正式資料的一鍵修正。

使用者可見內容必須優先顯示「姓名／員編」及「部門代碼／名稱」。UUID、任職 ID、`HEAD`、`PARENT_HEAD`、`ALL` 等技術值只能作為內部追查資料；畫面應分別顯示為正式主管、上級部門主管、全部流程等中文名稱。只有找不到對應主檔時，才以「未知員工（識別碼：…）」或帳號作為備援。

第一版建議範例如下：

| 問題 | 問題說明範例 | 建議處理範例 |
|---|---|---|
| 缺少部門主管 | 生產課在檢查時間沒有有效正式主管 | 前往「部門主管與代理主管」，配置一位具有效部門任職及 Tenant membership 的正式 `HEAD` |
| 多位正式主管 | 財務部同時存在兩位有效 `HEAD`，有效期間重疊 | 核對實際主管及生效日期，調整為同一時間僅一位正式 `HEAD`；需要代理時改用 `ACTING_HEAD` |
| 缺少直屬主管 | 王小明的主要任職無法依 `ORG_HEAD` 解析主管 | 確認所屬部門已配置有效 `HEAD`；若不依部門主管，改用有效的 `EXPLICIT` 主管任職 |
| 主管鏈循環 | A → B → C → A，主管鏈無法到達最高負責人 | 核對三筆任職的主管來源，至少修正其中一筆，使主管鏈能向上終止；不得任意由系統替換主管 |
| 缺少上級部門 | 品保課不是最高部門，但目前沒有有效父節點 | 前往組織樹，配置同 Tenant 的有效上級部門，並確認生效期間涵蓋子部門 |
| 組織樹循環 | 生產部 → 製造處 → 生產部 | 核對實際組織層級並修正其中一個父節點；修正前依賴主管鏈的流程可能無法正確解析 |
| 雙向互相代理 | A → B 與 B → A 在指定期間及流程範圍重疊 | 確認真正的被代理關係，停用其中一筆或調整期間／範圍，避免工作在代理鏈中循環 |
| 多位代理人重疊 | A 在相同期間及範圍同時代理給 B、C | 保留實際負責代理人，或拆分為不重疊的期間／流程範圍 |

頁面共用功能如下：

- 頂部摘要：四區 `ERROR／WARNING` 總數、最後掃描時間及檢查基準時間。
- 區塊內篩選：部門、員工或關鍵字；第一版不另做跨四區的複雜進階查詢頁。
- 修正導向：依問題類型開啟既有主管、員工任職、組織樹或工作代理程式；不在本頁直接修改主資料。
- 重新檢查：IT 修正後可重跑單一區塊或全部四項檢查；問題消失即標示 `RESOLVED`。
- 匯出：可分區或整頁匯出目前問題，供資料維護追蹤，不包含不必要的個資。

不得提供「忽略後永久不再檢查」。若業務確有合法例外，後續應增加具原因、有效期限與稽核的例外機制，不可只靠前端隱藏。

## 4. 警告與通知（後續規劃）

- 登入 Workspace 對具 `FLOWMINT_ORG_HEALTH` 權限者顯示未解決警告數及連結。
- 每日排程依 Tenant 執行完整掃描；單一 Tenant 失敗不阻斷其他 Tenant。
- 同一問題使用穩定 fingerprint 去重；未修正前不得每日重複建立相同通知。
- 新問題通知 IT／FlowMint 管理角色；持續未修正可依設定再次提醒。
- 通知只揭露問題摘要，完整員工與組織資料必須進入受權限保護的頁面查看。

## 5. API 與權限

第一版已實作 API：

```text
POST /api/FM_PROG002D0007/inspect
```

摘要、掃描批次及單筆重檢 API 待結果保存機制實作後再新增。

- Tenant 只接受 `X-FlowMint-Tenant` 並由 Security Context 驗證 membership，不接受 body 覆寫。
- 查詢需 `FLOWMINT_ORG_HEALTH`；手動全量掃描需 `FLOWMINT_ORG_HEALTH_SCAN` 或系統管理員。
- API 只提供偵測與重檢，不提供通用資料修正入口。
- 所有手動掃描、重檢及狀態轉換保存操作者、時間與結果摘要。

## 6. 保存策略（後續規劃）

第一版建議保存掃描結果，而非每次查詢即時計算全部資料：

- `fm_org_health_scan`：Tenant、基準時間、起訖時間、狀態、各類數量及觸發來源。
- `fm_org_health_issue`：問題代碼、嚴重度、穩定 fingerprint、對象類型／ID、摘要、首次／最後發現時間、狀態及解決時間。

狀態使用 `OPEN`、`RESOLVED`；同一 fingerprint 再次發現時更新最後發現時間，不新增重複問題。詳細 Context 必須受限長度且不得保存密碼、Token 或無關個資。正式建表前須依資料庫規範審核並更新 `flowmint.sql`，不得在 `doc` 留一次性 SQL。

## 7. 驗收條件

- 四類問題皆能正確列出，Tenant A 不得看到 Tenant B 的結果。
- 唯一最高部門不因無父節點被誤報，第二個無父部門必須警告。
- `ORG_HEAD` 實際無法解析時，即使來源欄位有值仍須警告。
- 同期間多位有效 `HEAD`、無效主管任職或 membership 必須列為 `ERROR`。
- 明確設定 `NONE` 的任職不誤報；在尚未建立最高負責人角色標記前，由組織管理者確認 `NONE` 僅用於最高負責人或核准例外。
- 自我主管、重複主要任職、二人與多層主管鏈循環皆能正確列出。
- 組織自己指向自己、跨 Tenant／失效父節點、父鏈循環及版本期間重疊皆能正確列出。
- A → B 與 B → A 期間及範圍有交集時只產生一筆警告；無交集時不警告。
- 自我代理、同範圍多代理人、多層代理循環、無效代理人、無效範圍、錯誤期間及禁止再代理違規皆能正確列出。
