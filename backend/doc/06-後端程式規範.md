# 06 後端程式規範

> **所有 Java、SQL、XML、JSON 與設定檔均須遵守 [19 原始碼排版與交付規範](19-原始碼排版與交付規範.md)。禁止把正式程式壓縮成單行；編譯成功不代表排版驗收通過。**

## 1. 技術基準

- Java 21。
- Spring Boot 與 QIFU4 現有版本一致。
- Flowable 8。
- MyBatis／QIFU4 BaseService。
- MariaDB 10.11+。
- Maven multi-module 現況不任意重組。

實作前應以專案實際 `pom.xml` 鎖定版本，本文件不授權直接升級框架。

## 3. 命名

- Entity：資料表 PascalCase，例如 `FmOrgUnit`。
- Mapper：`FmOrgUnitMapper`。
- Service：`IFmOrgUnitService`／`FmOrgUnitServiceImpl`。
- Logic：`IFmOrgUnitLogicService`／`FmOrgUnitLogicServiceImpl`。
- Controller：`FMPROG002D0002Controller`。
- Command：動詞加名詞，例如 `MoveOrgSubtreeCommand`。
- View：用途加 `View`，不得直接把 Entity 當 API response。

## 4. Entity

- 欄位名稱對應 UPPER_SNAKE_CASE。
- OID 使用 QIFU4 既有 UUID 機制。
- 不在 setter 內執行業務邏輯。
- 不用 JPA relationship lazy load。
- JSON longtext 對外轉成有型別 DTO，不在 Controller 操作字串 JSON。

## 5. Mapper

- 基本 CRUD 可沿用 BaseMapper。
- 跨表、樹查詢、待辦與報表使用明確 XML。
- 所有 SQL 明列欄位，禁止 `SELECT *`。
- Update 必須帶 OID／Business ID、Tenant 及 optimistic version。
- LIKE 查詢需 escape `%`、`_`。
- 大清單使用分頁，不允許無上限全表查詢。

## 6. Logic 與 Transaction

- Mutation 方法加 `@Transactional(rollbackFor = Exception.class)`。
- 驗證順序：identity → permission → tenant → existence → state → relation → mutation。
- Business exception 應使用穩定 Error Code，不以中文字串作判斷；目前多個 Service 仍直接拋出中文 `ServiceException` 訊息，不能把此項視為全案已完成。
- 捕捉例外後若不能恢復必須重新拋出，禁止吞例外後回成功。

## 7. API Result

沿用 QIFU4 `DefaultResult<T>` 與標準 response helper。現行多數 Program Controller 的 `DefaultControllerJsonResultObj<T>` 錯誤封裝範例如下；`success` 是 `Y`／`N` 字串，欄位驗證結果放在 `checkFields`：

```json
{
  "success": "N",
  "message": "找不到有效的部門主管",
  "checkFields": {},
  "value": null
}
```

共用封裝目前沒有通用 `errorCode`／`fieldErrors` 欄位；若 API 需要機器可讀的穩定錯誤碼，須先明確定義並實作契約，不得把它寫成所有現行 Controller 已回傳的欄位。外部系統 API 使用獨立的 `FmExternalResponse` 契約。

不得輸出 stack trace、SQL、token 或內部路徑。

## 8. 狀態與代碼

- Java 使用 enum／constant，DB 保存規格定義的英文 Code。
- Controller 不接受未知 Code。
- DDL Check、Java enum、前端 option 與測試資料必須同步。
- Error Code 前綴：`FM_AUTH_`、`FM_ORG_`、`FM_FORM_`、`FM_PROCESS_`、`FM_TASK_`、`FM_ASSIGN_`。

## 9. 時間與並行

- Service 使用注入的 `Clock`，測試不可依賴系統現在時間。
- DB 寫入 UTC。
- 部門 master、表單資料使用 optimistic locking。
- 任務處理先確認 Flowable task 仍 active 且 actor 有權。
- 重複 request 以 business key／action idempotency key 防止重複送出。

## 10. 測試

- Domain rule：unit test。
- Mapper、transaction、constraint、Flowable：integration test。
- Controller identity／permission／validation：API test。
- Resolver Preview 與 Runtime 使用相同 fixture 比對。
- 每次 bug fix 必須先加入可重現測試。
