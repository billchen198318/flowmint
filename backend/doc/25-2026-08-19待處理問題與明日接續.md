## 2. 已確認、尚未修正

### FM-REM-001：Custom JavaScript 卸載期間仍可能回寫已銷毀表單（P1）

相關程式：`useFormCustomJavascript.ts`、`workspace.vue`、`tasks/[id].vue`、`requests/[id].vue`。

目前 `run()` 只在生命週期開始前檢查 `destroyed`。已開始的非同步 hook 在 API 或 Promise 完成後，仍能呼叫 `setValue`、`setSelectOptions`、`setComponentDisabled` 或 `redraw`。而 `detach()` 是先等待 `onDestroy`，再設 `destroyed=true`；兩次並行 detach 也可能都進入 `onDestroy`。

風險：舊 runtime 操作已卸載 Form.io instance、舊資料回寫新畫面、重複執行銷毀副作用或產生未處理錯誤。

建議修法：

- 狀態拆成 `destroying`／`destroyed`，detach 一開始即原子性標記。
- 每次 attach 建立 generation token；所有畫面寫入 helper 在執行前及 `await` 後驗證 token。
- `onDestroy` 僅執行一次，且不再允許一般畫面寫入。

驗收：慢速 onFormLoad 中切頁不回寫；同時 detach 兩次只執行一次 onDestroy；卸載後完成的 hook 無未處理 rejection。需以 deferred Promise 測試。

### FM-REM-002：非同步 `onFieldChange` 期間的後續變更會被丟棄（P1）

相關程式：`frontend-v-nx/composables/useFormCustomJavascript.ts`。

目前 `handlingChange=true` 時新 change event 直接 return。若 hook 有慢速查詢，等待期間的欄位修改不會進入 hook，衍生欄位或連動選項可能停在舊狀態。

建議改為「單一執行者 + latest pending event」：執行期間保留最新 submission，前次結束後再處理一次，同時維持 script 自身 `setValue` 的遞迴防護。

驗收：第一個 hook 未完成時連續輸入，至少處理第一筆與最後狀態；script setValue 不形成無限 loop；detach 後 pending event 不執行。

### FM-REM-003：Data Action Bridge 卸載後，進行中的請求仍可回填（P1）

相關程式：`frontend-v-nx/composables/useFormioDataActionBridge.ts`。

detach 只移除 listener，沒有 disposed/generation 狀態。已送出的請求完成後仍會 mapping、寫狀態、redraw 及呼叫 success/error lifecycle。

建議加入 disposed/generation token，並在請求完成、mapping、redraw、lifecycle 前檢查；可再用 AbortController 中止網路請求，但即使不能中止也必須忽略過期回應。

驗收：慢速 Action 執行中 detach，回應後不得寫欄位、redraw 或觸發 lifecycle。

### FM-REM-004：表單發布未確認綁定的 Data Action／版本仍可執行（P1）

相關程式：`FmFormDesignValidator.java`、`FmFormDefLogicServiceImpl.java`、`FmDataActionLogicServiceImpl.java`。

目前只驗證 binding JSON、按鈕 event、表單欄位路徑與 mapping 格式，沒有在表單發布時查詢 Data Action catalog。因此 actionCode 拼錯、Action 未發布、指定 actionVersion 不存在、request parameter 或 response source 與 metadata 不一致，都可能發布成功後才在 runtime 失敗。

建議將純 JSON 驗證與 DB catalog 驗證分離。發布時強制驗證同 tenant 的 Action、指定版本發布狀態、request keys／required keys／response keys；草稿保存要採警告或拒絕則需明確定義。

驗收：上述錯誤在發布時回報 bindingId 與具體欄位；正確綁定可發布；不可誤用其他 tenant 同名 Action。

### FM-REM-005：response source 不存在時會把 target 寫成 `undefined`（P1）

相關程式：`frontend-v-nx/composables/useFormDataAction.ts`。

`getPath()` 找不到來源會回傳 `undefined`，後續仍寫入 target，可能清掉原本有效值。必須區分「路徑不存在」與「值確實是 null」，並在任何寫入前預驗證整批 mapping。

驗收：來源缺漏時所有 target 保持原值；null 依契約回填；錯誤包含 actionCode、bindingId 與 source path。

### FM-REM-006：response、status、error target 碰撞會互相覆寫（P1）

相關程式：`FmFormDesignValidator.java`、`useFormDataAction.ts`、`useFormioDataActionBridge.ts`。

目前只禁止同一 responseMapping 內 target 重複，尚未禁止 response target 與 statusTarget、response target 與 errorTarget、statusTarget 與 errorTarget 相同。例如 response 寫入業務值後，status 再寫 `SUCCESS`，業務值即被覆蓋。

建議由後端發布驗證、editor 即時驗證及 runtime 防禦共同拒絕三類碰撞。

驗收：三類碰撞均不可發布；舊錯誤資料在 runtime 也不可開始 Action；訊息列出欄位及衝突用途。

### FM-REM-007：Custom JavaScript hook 無 timeout，可能永久鎖住操作（P2）

相關程式：`frontend-v-nx/composables/useFormCustomJavascript.ts`。

所有 hook 都直接 await。若客製 script 等待永不完成的 Promise，beforeSubmit、Task Action 或 detach 可能永久停住。

這不是執行隔離問題，也不應限制客製能力；它是非同步可用性保護。建議提供可設定 timeout：beforeSubmit timeout 阻止送出；afterSubmit timeout 僅警告；顯示型 hook 記錄錯誤後繼續。文件需說明 timeout 只能停止等待與忽略過期結果，無法終止同一 JavaScript realm 已執行的程式。

驗收：永不 resolve 的 hook 不會永久鎖住 UI，且不同 lifecycle 保持正確交易語意。

## 4. 產品決策：不列為 bug

### FM-DEC-001：Custom JavaScript 不做真正執行隔離

依 2026-08-19 決策，Custom JavaScript 是受信任管理者使用的客製擴充能力，需要保留瀏覽器端彈性；未採 iframe、Web Worker 或獨立 realm 隔離不再列為 bug。

- `READ_ONLY` 是表單操作模式，不代表 JavaScript sandbox。
- 後端 tenant、身分、權限、Data Action 類型與資料存取驗證仍不可信任前端。
- 發布權限、版本、audit、錯誤記錄與 rollback 仍是必要治理。
- timeout 與卸載後禁止過期回寫是穩定性控制，不是隔離或客製限制。

### FM-DEC-002：同一 Form.io event 是否允許多個 Data Action

目前 button event 與 bindingId 各自唯一，但未禁止多個 binding 指向同一 event。若只允許一個，editor／發布需拒絕；若允許多個，需定義順序、失敗是否中止、部分成功、status/error 及 lifecycle 次數。決策前不認定為 bug。
