# FM_PROG006D0002 補強項目

## 1. 文件目的

本文件定義 `FM_PROG006D0002` 建議補充的共用 Data Action、統一 API 契約、安全邊界與分階段實作順序。

> **文件定位（2026-08-25 核對）**：本文件是補強建議與待辦規劃，不代表所列能力皆已實作。Executor 已完成 `ONCE`、`FOR_EACH`／JDBC Batch、Generated Key、前一步結果引用、Continue Condition 與 SELECT_LIST 統一分頁，尚待跨資料庫整合驗收；Execution Audit、全域 Rate Limit 與個別 Action 配額均已完成並套用本機 MariaDB；Streaming 尚未完成。

`FM_PROG006D0002` 不應成為任意資料表 CRUD 或任意 SQL 的公開入口。它應優先提供穩定、Tenant-safe、可供 Form.io、FlowMint 頁面及其他內部功能重複使用的：

- Context API
- Option API
- Lookup API
- Validation API
- 少量受控的業務 Data Action

會改變 FlowMint 核心狀態、涉及流程引擎或需要複雜權限與稽核的操作，仍應由正式 Logic Service／Domain Service API 負責。

## 2. 核心設計原則

### 2.1 Tenant 隔離

- 每個共用 Action 都必須依 `:tenantId` 查詢。
- `:tenantId` 必須由 `X-FlowMint-Tenant` 經 Server 驗證後提供。
- 不接受 Request Body 覆蓋 `tenantId`。
- 執行前必須確認目前登入帳號是指定 Tenant 的有效成員。
- 不得回傳其他 Tenant 的資料。

### 2.2 登入者身分

- 目前登入帳號使用 `:loginAccount`。
- `:loginAccount` 由 Server Context 提供，不接受 Request Body 指定。
- 查詢「本人」資料時，不應額外接受 account 參數。
- 查詢其他人員時，必須使用 Employee ID 等穩定識別值，並另行檢查資料權限。

### 2.3 最小資料輸出

共用 Action 只回傳使用情境真正需要的欄位。一般員工選項不應包含：

- 密碼或密碼相關欄位
- 私人聯絡資料
- 身分證件資料
- 不必要的稽核欄位
- 其他敏感人事資訊

### 2.4 穩定契約

- Action Code 發布後視為穩定 API 識別碼。
- Request、Response 與 Result Key 應有固定命名。
- 不應直接把資料表完整 Row 當作長期 API 契約。
- 欄位調整應建立新版本並保持舊版本相容。

### 2.5 SQL 安全

- 只允許 Named Parameter。
- 禁止接收 table name、column name、order by 片段或 SQL 片段。
- 動態條件應使用固定 SQL 與允許的參數控制。
- 搜尋、分頁、最大筆數及 Timeout 必須有明確上限。

## 3. 建議 Action 分類

| 分類 | 用途 | 典型情境 |
|---|---|---|
| `CONTEXT` | 取得登入者及 Tenant Context | 表單預設申請人、目前部門 |
| `OPTION` | 提供下拉選項 | 部門、職稱、群組清單 |
| `LOOKUP` | 依穩定識別值取得資料 | 員工、部門詳細資料 |
| `VALIDATION` | 送出前業務驗證 | 員工是否在部門有效任職 |
| `COMMAND` | 受控資料異動 | 非核心、低風險業務資料異動 |

建議在 `fm_data_action` 增加 Action Category，或至少建立對應 Metadata，以便前端依用途篩選。

## 4. 登入者與 Tenant Context API

此類 Action 幾乎可供所有 Form.io 表單共用，應列為最高優先。

| Action Code | 用途 | 輸入 | 建議輸出 |
|---|---|---|---|
| `FM_GET_CURRENT_USER` | 取得目前登入帳號 | 無 | account、displayName、email |
| `FM_GET_CURRENT_EMPLOYEE` | 取得登入者對應員工 | 無 | employeeId、employeeNo、displayName |
| `FM_LIST_MY_TENANTS` | 取得登入者可用 Tenant | 無 | Tenant Option List |
| `FM_GET_CURRENT_TENANT` | 取得目前 Tenant | 無 | tenantId、tenantCode、tenantName、timezone |
| `FM_GET_MY_PRIMARY_ASSIGNMENT` | 取得本人主要任職 | 無 | 部門、職稱、主管來源、有效期間 |
| `FM_LIST_MY_ASSIGNMENTS` | 取得本人所有有效任職 | 無 | 主要及兼任任職清單 |

此類 Action 不接受其他帳號或 Employee ID，固定使用 `:loginAccount` 解析本人資料。

## 5. 員工共用查詢 API

| Action Code | 用途 | 主要輸入 | 建議 Result Mode |
|---|---|---|---|
| `FM_GET_EMPLOYEE` | 依 Employee ID 取得員工 | `employeeId` | `OBJECT` |
| `FM_GET_EMPLOYEE_BY_NO` | 依員工編號取得員工 | `employeeNo` | `OBJECT` |
| `FM_SEARCH_ACTIVE_EMPLOYEES` | 搜尋有效員工 | `keyword`、分頁參數 | `LIST` |
| `FM_LIST_EMPLOYEES_BY_ORG` | 取得部門有效員工 | `orgUnitId` | `LIST` |
| `FM_GET_EMPLOYEE_PRIMARY_ORG` | 取得員工主要部門 | `employeeId` | `OBJECT` |
| `FM_LIST_EMPLOYEE_ASSIGNMENTS` | 取得員工有效任職 | `employeeId` | `LIST` |
| `FM_GET_EMPLOYEE_MANAGER` | 取得員工直屬主管 | `employeeId` | `OBJECT` |

員工搜尋建議只回傳：

```json
{
  "employeeId": "EMP-001",
  "employeeNo": "E001",
  "displayName": "王小明",
  "orgUnitId": "ORG-001",
  "orgUnitLabel": "11000／生產部",
  "titleLabel": "MGR／經理",
  "status": "ACTIVE"
}
```

`FM_SEARCH_ACTIVE_EMPLOYEES` 必須限制最大回傳筆數。資料量較大時應採分頁或至少要求有效 keyword，不應一次載入整個 Tenant 的所有員工。

## 7. 統一 Option 契約

所有提供下拉選單的 Action 建議統一回傳：

```json
[
  {
    "value": "ORG-001",
    "label": "11000／生產部",
    "disabled": false,
    "meta": {
      "unitCode": "11000",
      "levelCode": "DEPARTMENT"
    }
  }
]
```

欄位定義：

| 欄位 | 必填 | 說明 |
|---|---:|---|
| `value` | 是 | 實際保存的穩定識別值 |
| `label` | 是 | 使用者可辨識的「代碼／名稱」 |
| `disabled` | 是 | 是否禁止選取 |
| `meta` | 否 | 額外顯示或級聯查詢需要的資料 |

Form.io、Vue Select、一般 HTML Select 與未來共用 Picker 都應使用同一格式。

| Action Code | 用途 | 主要輸入 |
|---|---|---|
| `FM_GET_ORG_HEAD` | 取得指定部門主管 | `orgUnitId`、`headType` |
| `FM_GET_PARENT_ORG_HEAD` | 取得上層部門主管 | `orgUnitId` |
| `FM_LIST_ORG_HEADS` | 取得 HEAD／DEPUTY／ACTING | `orgUnitId` |
| `FM_GET_DIRECT_MANAGER` | 取得員工直屬主管 | `employeeId` |

這些 Action 僅適合：

- HEAD、DEPUTY_HEAD、ACTING_HEAD

| Action Code | 用途 | 主要輸入 |
|---|---|---|

## 11. 表單業務驗證 API

| Action Code | 用途 | 主要輸入 |
|---|---|---|
| `FM_VALIDATE_EMPLOYEE_ACTIVE` | 員工是否有效 | `employeeId` |
| `FM_VALIDATE_ORG_ACTIVE` | 部門是否有效 | `orgUnitId` |
| `FM_VALIDATE_EMPLOYEE_IN_ORG` | 員工是否在部門有效任職 | `employeeId`、`orgUnitId` |
| `FM_CHECK_BUSINESS_KEY_EXISTS` | 業務編號是否已存在 | `businessKey` |
| `FM_CHECK_DUPLICATE_REQUEST` | 是否存在重複申請 | 業務識別欄位 |
| `FM_GET_APPROVAL_LIMIT` | 取得核決額度資訊 | 員工、流程或金額條件 |

Validation Action 建議統一回傳：

```json
{
  "valid": false,
  "code": "EMPLOYEE_NOT_IN_ORG",
  "message": "所選員工目前不在指定部門任職",
  "details": {}
}
```

欄位定義：

| 欄位 | 說明 |
|---|---|
| `valid` | 是否通過驗證 |
| `code` | 穩定且可供前端判斷的結果代碼 |
| `message` | 使用者可理解的訊息 |
| `details` | 需要時提供額外資訊 |

特定業務模組的驗證應使用模組 Prefix，例如：

```text
PURCHASE_VALIDATE_VENDOR
LEAVE_CHECK_OVERLAP
EXPENSE_CHECK_BUDGET
```

不應將所有特定表單邏輯都命名為平台共用的 `FM_*` Action。

## 13. 不應做成通用 Data Action 的項目

以下操作應保留在正式 Logic Service／Domain Service API：

- 建立或修改 Tenant。
- 建立帳號、停用帳號或重設密碼。
- 建立或修改員工任職。
- 搬移組織樹。
- 指派或變更部門主管。
- 發布表單或 BPMN。
- Submit、Approve、Reject、Return、Resubmit。
- Claim、Transfer、Delegation、Add Sign。
- 正式解析 Workflow 簽核人。
- 管理員 Reassign 或 Terminate 流程。
- 任意資料表查詢。
- 接收 table name、column name、order by 或 SQL 片段。

原因是這些操作需要一項或多項能力：

- 細粒度權限檢查
- 複雜業務驗證
- optimistic locking
- Flowable runtime 同步
- Form／Assignment Snapshot
- 完整 Audit
- Incident
- 冪等控制
- 多 Aggregate 交易一致性

單純 SQL Data Action 不足以安全承擔這些責任。

## 14. 平台能力補強

### 14.1 Request Schema

目前 Request Mapping 主要描述參數來源，建議補充：

- 參數型別
- 是否必填
- 最大長度
- 最小值與最大值
- Regex
- Enum 白名單
- 預設值
- 是否允許 null

概念格式：

```json
{
  "employeeNo": {
    "path": "$.employeeNo",
    "type": "STRING",
    "required": true,
    "maxLength": 30
  }
}
```

### 14.2 Response Schema

建議定義穩定的 Response Schema，用於：

- Form.io 視覺化 Binding
- 前端設計時欄位提示
- Metadata API
- 發布前契約檢查
- API 文件產生
- 版本相容性檢查

### 14.3 分頁契約

清單型 Action 建議統一輸入：

```json
{
  "keyword": "王",
  "page": 1,
  "pageSize": 20
}
```

統一輸出：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0
}
```

必須設定伺服器端最大 pageSize，不能完全相信呼叫端傳入值。

### 14.4 權限碼

目前 Tenant membership 只能證明帳號屬於 Tenant，不代表帳號可讀取所有共用資料。建議每個 Data Action 可設定：

- 是否只需 Tenant membership
- 所需 Role
- 所需 Permission Code
- 是否限本人資料
- 是否允許查詢其他員工

### 14.5 資料分級

建議增加：

| 等級 | 說明 |
|---|---|
| `PUBLIC_INTERNAL` | Tenant 內一般選項資料 |
| `RESTRICTED` | 需要特定權限的資料 |
| `SENSITIVE` | 原則上不應由通用 Action 公開 |

### 14.6 Cache

低變動選項可設定 Cache TTL，例如：

- Tenant 職稱
- 簽核層級
- 共通代碼
- 語系與時區

Cache Key 必須包含：

```text
tenantId + actionCode + versionNo + request parameter hash
```

員工搜尋、主管狀態、有效期間資料不宜使用過長 Cache。

### 14.7 Execution Audit

建議至少記錄：

- Tenant
- Action Code 與版本
- 登入帳號
- 執行時間
- 成功或失敗
- 執行耗時
- 回傳筆數或異動筆數
- 錯誤代碼
- Correlation ID

Audit 不應保存明文密碼、Token 或敏感 Request Body。Request／Response 是否保存應依資料分級決定。

### 14.8 Deprecated 與下架

建議增加版本狀態或 Metadata：

- `ACTIVE`
- `DEPRECATED`
- `RETIRED`

Deprecated 時 Metadata 應提供替代 Action Code 與停止支援日期。

### 14.9 Rate Limit 與資源限制

建議增加：

- 每帳號／Tenant 呼叫頻率限制
- 最大 pageSize
- 最大回傳列數
- 最大 Request Body
- 最大 SQL 執行時間
- 同一 Action 最大 Step 數
- Circuit Breaker 或 Pool 保護

## 15. 建議實作順序

### Phase A：契約與唯讀 Action

1. 定義 Option、Lookup、Validation 統一格式。
2. 補上 Request 參數型別與必填驗證。
3. 建立 P0 十二個唯讀 Action。
4. 為清單 Action 加入分頁及最大筆數限制。
5. 建立 Metadata 說明與範例。

### Phase B：權限與稽核

1. 增加 Action Permission Code。
2. 增加資料分級。
3. 實作 Execution Audit。
4. 增加 Correlation ID、耗時及錯誤代碼。
5. 增加 Rate Limit 與資源保護。

### Phase C：Form.io 整合

1. 建立 Action 選擇器。
2. 依 Metadata 顯示 Request 欄位。
3. 建立 Request／Response 視覺化 Mapping。
4. 支援 Option 與 Validation Action 快速綁定。
5. 發布表單時檢查所引用 Action 是否存在且已發布。

### Phase D：進階執行能力

> 目前狀態：第 1～4 項已完成程式實作並通過編譯與相關單元測試，仍待跨資料庫整合驗收；第 5 項的 Execution Audit 已完成程式與 migration，重試政策仍未完成。

1. `FOR_EACH`／JDBC Batch。
2. Generated Key。
3. 前一步結果引用。
4. Continue Condition。
5. 完整執行稽核與重試政策。

## 16. 驗收案例

每個共用 Action 至少驗證：

- 正常輸入。
- 必填參數缺少。
- 參數型別錯誤。
- 查無資料。
- null 與空字串。
- 最大長度及邊界值。
- 最大回傳筆數。
- 非 Tenant 成員呼叫。
- 使用其他 Tenant ID 呼叫。
- 其他 Tenant 的 Employee／Org ID。
- 停用資料。
- 尚未生效及已失效資料。
- Draft Action 不可正式執行。
- 指定不存在或非 Published 版本。
- Query Timeout。
- SQL 錯誤時 Transaction Rollback。

員工搜尋與組織選項另需驗證繁體中文、簡體中文及罕見姓名字元。

## 17. 最終建議

`FM_PROG006D0002` 應優先發展為「受控且可治理的共用資料能力目錄」，而不是一般 SQL Console。

第一階段應集中在唯讀的 Context、Option、Lookup 與 Validation Action，先滿足 Form.io 最常見的申請人、員工、部門、職稱、職務與簽核群組需求。

凡是會改變 FlowMint 核心狀態、影響 Flowable runtime、需要 Snapshot／Incident／冪等或複雜權限判斷的操作，應繼續使用正式 Logic Service／Domain Service API，不應以 Data Action 取代。


## 18. P0 Action 實際 SQL

以下 SQL 依目前欄位撰寫，以 MariaDB 為基準。每個 Action 均為 `QUERY`、`ONCE`；貼入畫面時不要加結尾分號。Server Context 提供 `:tenantId`、`:loginAccount`、`:now`。

### 18.1 `FM_GET_CURRENT_EMPLOYEE`

`{}`／`SELECT_ONE`／Result Key `employee`／`OBJECT`／maxRows `1`

### 18.2 `FM_GET_MY_PRIMARY_ASSIGNMENT`


## 19. SQL 實作注意事項

- 上述 SQL 使用 MariaDB `CONCAT(...)`；Oracle、MSSQL 需建立相應 Dialect 版本。
- JDBC Driver 可能調整欄位 Label 大小寫，發布前應以實際 Pool Preview 檢查 Response Key。
- `orgUnitId`、`parentOrgUnitId`、`approvalGroupId` 等參數，在 Request Schema 必填驗證完成前應由呼叫端先檢查。
- 搜尋 Action 目前以 `maxRows` 保護，正式大量使用前仍應完成統一分頁契約。
- `FM_GET_ORG_PATH` 回傳目前保存的 `PATH`；如需完整部門名稱路徑，應由專用 Domain Service 組裝。
